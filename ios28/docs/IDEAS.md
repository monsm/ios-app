## 0. 先看结论

### 0.1 三个产品判断

1. **从「能开锁」到「可证明地开锁」。** 这个 App 的差异化不是功能数量，而是每个动作都有回执、每个失败都有解释、每条数据都有出处。可信度是第一条产品线。
2. **从「一把锁」到「一个家」。** 多锁、多成员、多凭证在数据层已经存在，但界面仍是单锁叙事。把「家」做成第一等对象，是最大的结构性机会。
3. **从「设置齐全」到「日常顺手」。** 20 个目的地已经够多。下一步不是再加页面，而是让开门、发临时码、看谁来过这三件事各少一步。

### 3.4 不建议做 / 反功能

- **云端账号与远程开锁**：与「完全离线、无账号」的产品定位冲突；远程开门还会把协议的安全弱点暴露到公网。
- **假进度、假成功**：镜头必须只在真实回执后走满；这是品牌承诺，不是动效细节。
- **后台常驻 BLE 扫描**：耗电且无必要；用 App Intents / Widget 解决快捷入口。
- **社交、排行榜、家庭动态流**：与「安静的工具」气质冲突。
- **把未验证的协议能力包装成「支持」**：布防回读、DFU 签名、网关云能力都要如实标注边界。
- **用低对比浅灰当高级感**：已由对比度闸门拦住，不要回退。
- **在空壳里显示任何「空壳」字样**：包括错误文案、帮助文本、通知。
- **把备份校验和说成防篡改**：FNV 只是完整性检查，真正安全来自信封 HMAC。

## 5. 需要真机 / 协议验证的点

这些点子在落地前必须先确认协议或真机行为，不能只靠 DesignLab 与静态闸门：

| 点子 | 需要确认什么 |
|---|---|
| B14 setAndVerify / 布防回读 | 锁是否真的提供可回读的布防状态；目前只知道 rc=0 |
| F16 开锁后「保持开门」 | 协议没有独立上锁命令；只能改 cmd24 间隔，语义需真机确认 |
| B20 网关抽象 | cmd30/32 是厂商云能力，本版未使用；不要包装成已支持 |
| B37 DFU 回滚 | 协议不提供签名；回滚依赖 bootloader 行为，需真机验证 |
| B9 多锁并发 | BLE 单链路；多锁只能串行，后台切换策略需实测 |
| F12 iPad/横屏 | 当前只支持竖屏 iPhone；布局与安全区要真机看 |
| F48 AX5 | 令牌已按动态字体缩放，但极端字号下的中文度量要看真机 |
| F30 触觉/材质 | DesignLab 是 HTML 镜像，手感、折射、PingFang 度量都验不了 |
| F42 指纹录入中断 | 锁的 15 秒窗口过期后如何恢复，需要真锁复现 |
| B39 长日志续读 | 锁端约 2000 条滚存；20 页上限后的断点续读需真机长跑 |

---

> 这份清单的原则：**先让「开门」和「数据」不可疑，再让「家」更好用。**
> 任何一条在落地时如果发现协议不支持，就如实降级为「说明 + 边界」，不要做成看起来支持的假功能。
