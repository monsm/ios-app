# AUDIT-ROUND-142 · 第一百四十二轮：一条指向"不存在的待办"的注释

> CI：`485ee7b` 已验证绿；`fdaa7f7` 待回执。本轮本地提交。

## 1. 起点：`AndroidPair` 的注释说"应该反向回填一条校验"

```swift
// 唯一的形态差异是 **Android 做了本仓没做的上界校验**（ekey ≤ 510 字节，
// 因为 KLV 长度字段只有 1 字节）。这条校验应该反向回填到本仓 ——
// 见 AUDIT-A F-42；改它需要同步 golden，故留待与 Android 一起改。
```

这句话会让下一个读者去做一件**没有意义的事**。核对后：

| 端 | 角色 | 为什么不需要那条校验 |
|---|---|---|
| 本仓 | **生成侧** | `buildEkeyOpen` 产出 AES 加密结果（16 字节明文 → **32 hex 字符**），长度**结构上固定** |
| Android | **解析侧** | 要接受任意输入，所以必须有上界防御 |

本仓**没有"解析他人 ekey"这条路径** —— 那条校验无处可用。

## 2. 修法

把注释改成实话，并说明为什么那条待办不存在：

> 2026-11-01 更正：原文写「…应该反向回填到本仓」—— **这个结论错了**。核对后：
> · 本仓是生成侧，产出长度固定，不可能超过 510；
> · 那条上界是解析侧的防御，本仓没有解析他人 ekey 这条路径。
> 所以本仓不需要这条校验 —— 是注释的措辞在指一条不存在的待办。

## 3. 为什么这算缺陷

它不是代码 bug，但**是"注释里的承诺没有实现"这个元类的一条** —— 而本段已在这个形态上
抓到过 6 次真缺陷（死声明、幽灵开关、幽灵警告、假队列、假索引、DestroyKit）。

这次的差别在于：**它指的不是"没做"，而是"根本不需要做"**。
两种都误导，但后者更隐蔽 —— 因为没人会去验证"是否需要"。

## 4. 方法论

**注释里的 TODO 也要被审计 —— 尤其当它说"应该做 X"时，先问"X 真的需要吗"。**

| 注释形态 | 该怎么查 |
|---|---|
| "这里应该做 X" | 先问 X 是否**必要**（本轮的教训） |
| "这里做了 X" | 去找 X 的实现 |
| "X 不可能发生" | 去找能证明它发生的代码路径 |
