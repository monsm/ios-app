## 1. `DiagOp` / `DiagOps` 也是空的

注释写「156 本次会话操作序列」，实现有 `record(_:)` / `list()` / 开关 `kf_diag_ops_on`。
实测：**两个函数全仓零调用**，开关也**零写入** —— 这条"操作序列"从未记录过一条，也没被任何界面读过。
已删除并留说明。

## 2. 四处放在一起看，是同一个模式

| # | 位置 | 承诺 | 实际 |
|---|---|---|---|
| 1 | `CredentialOrg.quota()` | 凭证配额 | 零调用、键零写入 |
| 2 | `DiagFlags.silent` | 静默排查模式（还说"逐条对过行号"） | 零引用 |
| 3 | `struct Advice` | 358/505 整理建议中心 | 零生产者零消费者 |
| 4 | `DiagOp` / `DiagOps` | 156 操作序列 | 零调用 |

共同点：**结构、注释、字段都齐了，唯独"谁调用它"这一环从来没有过。**

这也解释了为什么它们能长期存在：读代码时每一处都"看起来是功能"，
只有把「引用计数」真的跑一遍才会露馅。

## 3. 顺带查到的：`kf_diag_log_retention` 也无人写

`DiagLogStore.retentionDays` 读这个键（"" 全部 / "365" / "90"），但没有任何界面写它 ——
所以按天裁剪永远不会发生。这不是 bug（日志仍受条数上限约束），
但它说明**诊断相关的 UI 整体没有落地**（本仓 `Features/` 里没有诊断页）。
这点已写在 `AUDIT-COVERAGE.md` 的"未覆盖"里，不另开修复。

## 4. 方法论

**"读起来像功能"和"运行时是功能"之间隔着一次引用搜索。**
这四处都不是我"读"出来的，而是"搜"出来的：先读注释建立预期，再去全仓数引用。

可复用的检查动作：**对任何带 `kf_` 键、或名字里有"中心/序列/模式/配额"的声明，
先数引用再决定要不要读实现** —— 顺序反过来会浪费大量时间读一段永不执行的代码。
