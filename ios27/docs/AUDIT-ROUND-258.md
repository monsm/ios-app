# AUDIT-ROUND-258 · 第 258 轮：**胁迫码没设上，界面却关掉了**

> CI：**`f03e367` build 全绿**；`c448dbe` / `0377f54` / `7039c33` 排队中。

## 1. 怎么发现的

扫「`_ =` 丢掉一个**返回 Bool** 的函数」的调用点（先收集 80 个 `-> Bool` 函数名，再找丢弃处）。
全仓只有 **2 处**，其中一处就是它。

## 2. 缺陷

    case .duress:
        _ = DB.setDuressCode(first)
    …
    dismiss()

而 `DB.setDuressCode` 有三条失败路径：

| 条件 | 返回 | 写入 |
|---|---|---|
| `nil` / 空串（清除） | true | 删键 ✅ |
| 不足 4 位 / 非数字 | **false** | **不写** |
| **与本机密码相同**（`verifyPasscode` 命中） | **false** | **不写** |

UI 只挡了「不足 4 位 / 非数字」（300-301 行），**没挡「与本机密码相同」**。于是：

| 用户操作 | 界面 | 实际 |
|---|---|---|
| 把胁迫码设成和本机密码一样 | 弹窗**关闭**，无任何提示 | **胁迫码根本没设** |

**这是安全功能：用户以为"紧急时输入这个码会进入空壳模式"，而那一刻不会发生任何事。**

## 3. 修法

接住返回值，失败时留在弹窗并说明原因：

    guard DB.setDuressCode(first) else {
        error = "胁迫码不能与本机密码相同；请换一个 4 位以上数字"
        return
    }

## 4. 顺带

`SecurityScreen:59` 的 `_ = DB.setDuressCode(nil)` 是**清除**，该分支恒 true ⇒ 丢弃无妨 ✅。

## 5. 方法论

**安全类功能最不能容忍"静默失败"—— 因为它恰恰在最需要生效的时刻被检验。**

| 失败类型 | 何时被发现 |
|---|---|
| 普通保存失败 | 下次打开页面就发现 |
| **胁迫码保存失败** | **只会在真正需要它的那一刻发现** |

判据：**凡是"平时不用、只在紧急/异常时生效"的功能（胁迫码、救援码、备份口令、离线凭证），
其写入路径必须把失败**当场**说出来，绝不允许静默。**
