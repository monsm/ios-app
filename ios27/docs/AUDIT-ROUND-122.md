# AUDIT-ROUND-122 · 第一百二十二轮：未知型号被显示成「智能门锁 (pid=…)」

> CI：`91a7f06` 全绿（`errors=0`、`warnings=0`）；`44d8807` 待回执。本轮本地提交。

## 1. 审了什么

`PidMap.swift`（55 行，PID → 型号映射）——「从未在报告里出现」差集里的文件，
而它直接决定用户在设备页看到的「型号」字段。

## 2. 发现：未知 PID 的兜底文案在撒谎

```swift
static func productName(_ pid: Int) -> String { productNames[pid] ?? ("智能门锁 (pid=\(pid))") }
```

**未知 pid 是预期场景**（代码自己的注释就写着：
"未知 pid (新品固件, 如实测 49408) 按 KX 家族放行"）—— 即"用户拿着一款比 App 新的锁"是设计内的正常情况。

那么这句兜底文案**会真的出现**，而它的问题在于：

1. **说它是「智能门锁」**—— 用户拿到的可能根本不是这个产品线（新产品可能是网关、指纹模块等）；
2. 把 pid 塞进括号是对的（支持人员要靠它定位），但前面的「智能门锁」是**编造的产品归属**。

## 3. 修法

```swift
productNames[pid] ?? "未收录的型号 (pid=\(pid))"
```

「未收录的型号」是**诚实的表述**（我们的表里没有），不冒充产品归属，且仍然带 pid 供定位。

## 4. 核对过但不用改的两处

| 疑点 | 结论 |
|---|---|
| `productNames` 没有 3 个网关的中文名 | **不可达**：网关走 `HardwareService.scanForPIDs(pids: PidMap.gws)` 配网路径，不进 `DeviceInfoScreen`；而 `canDefend`/`isLock` 都先排除网关 |
| `canDefend` 对未知 pid 放行 | 有意设计（新品固件先上市、App 表后更新），注释里写明了实测依据 |

## 5. 方法论

**兜底文案是"最常被忽略的界面"** —— 作者写它时只想"这不太会出现"，
而代码注释里明明写着"这会出现"。两者矛盾时，**以代码注释陈述的事实为准**。

判据：**凡是有"未知 X"兜底分支的地方，读一遍那句兜底文案** —— 问自己：
"用户看到这句话，能不能正确理解发生了什么？会不会被误导？"』
