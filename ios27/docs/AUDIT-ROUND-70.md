# AUDIT-ROUND-70 · 第七十轮：试了四版都没写对的一条闸门规则 —— 回退并记录

> CI：`ee4b04e` 已验证；`db94f4d` / `74bd21e` / `d62c9c8` / `2cf4700` 待回执。

## 1. 目标：修 `a11y` 第①条（图标按钮缺 label）的窗口缺陷

它的实现是「从 `Button` 行向后取 **30 行**」，判据三选：窗口内有 `Image(systemName:)`、
无任何文字、无 `accessibilityLabel`。

## 2. 实测：它错在两个方向，且**方向取决于上下文**

以 `KeysScreen.swift:355`（清空搜索的图标按钮）为例：

**（a）误判红（长 label 闭包）**：按钮闭包多行时，30 行窗口越界到**别的视图**，
那里的 `Text(` 会让规则认为"有文字"，从而**不报**——即漏判；
**（b）漏判（宽窗口）**：同一窗口把按钮**之后**外层视图的 `.frame(...)` 也算作"按钮本体"。

实测最有说服力的一个结果：

```
A) 只删掉 accessibilityLabel("清空凭证搜索")        → 闸门仍绿（漏判）
B) 删掉 label + 在闭包内插入 40 行注释               → 闸门仍绿（漏判）
```

也就是说：**这条规则对这类"闭包内只有 Image、label 写在闭包外"的常见写法，本来就抓不住** ——
不是因为窗口太窄，而是因为窗口太宽（把后面的 `Text(` 当成按钮内容了）。

## 3. 我试了四版，每版都有新漏

| 版本 | 思路 | 失败方式 |
|---|---|---|
| 1 | 行内括号配对 | `Button { act } label: {` 的第一个 `{}` 同行闭合 → 扫描当场结束 → 漏判 |
| 2 | 配对 + 修饰符链合并 | 链里出现 `Text(` → 把"只有图标"掩盖成"有文字" → 漏判 |
| 3 | 本体与链分开取 | 仍被第 1 版的同行闭合问题挡住 → 漏判 |
| 4 | 按语句范围（缩进 + 续行）取 | 语法错误修好后仍需逐例验证，时间成本已超过收益 |

## 4. 处置：回退

`git checkout -- ios27/Gates/a11y.js` 回到已提交版本，`allgates` 20/20 通过，工作区干净。

**为什么回退而不是继续改**：

- 这条规则的失败方向是**漏判**（假阴性），不是"把好代码判红"；
- 它已覆盖仓里绝大多数写法（那种一屏内写完的图标按钮）；
- 而"半成品规则"会让人以为它覆盖了全部 —— 那比"明知它有洞"更危险。

## 5. 留一条可执行的改进线索（给下一轮或后来人）

正确做法应当是：**先按缩进/语句边界取出"这一个按钮表达式"，再分别判定**
（`Image(systemName:)` 在本体内 + 本体与链上都没有 `Text(`/`Label(` + 本体或链上有 `accessibilityLabel`）。
难点在 `Button { action } label: { ... }` 这种"两个闭包"的形态 ——
第一个闭包是 action，扫描不能在那里停。

## 6. 方法论

**"改不对就先回退"也是审计的一部分。**
我前四版每版都比上一版"更正确"，但没有一版通过双向验证 —— 如果我把第三版提交了，
结果是：闸门仍然漏判，而 README/正控清单里会多一条"已验证"的假记录。

判据：**闸门改动的验收标准与业务代码不同 —— 业务代码"能跑就行"，
闸门必须"注入缺陷能红、移除缺陷能绿"两向都过**。过不了就回退，不要留半成品。
