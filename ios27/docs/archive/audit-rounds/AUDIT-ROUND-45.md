# AUDIT-ROUND-45 · 第四十五轮：文件头那张「存储键清单」有两条是假的

> CI：`e0b1b3f` 已验证；`2971b60`（含备份修复）已推送、待回执。本轮本地提交，不推送。

## 1. 核对方法

`CredentialOrg.swift` 开头列了 11 个 `kf_` 存储键，并逐一写用途。
我把每个键拿去全仓 grep，只数**非注释行**的命中：

| 键 | 代码命中 |
|---|---|
| `kf_chist_` `kf_cbin_` `kf_cstar_` `kf_calert_` `kf_clists_` `kf_cseq_` `kf_ccred_prefs` `kf_calias_display` `kf_csearch_hist` | 有（2–3 处） |
| `kf_cqueue_` | **0 —— 只有这一行注释** |
| `kf_cbin_reclaim_days` | **0 —— 只有这一行注释** |

两条假的是：

- **`kf_cqueue_<mac>`「下发状态队列」**：从未实现。这与 `CredentialOrgBatch.swift` 里
  「下发部分只入队 / 锁端删除入队」的注释是同一个坑 —— 那个队列不存在。
- **`kf_cbin_reclaim_days`「回收站保留天数（设置可改）」**：没有这个设置，也没有按天裁剪；
  回收站只受条数上限约束（`CredBinStore.maxItems`，第 23 轮加的，第 40 轮修过淘汰方向）。

## 2. 处置

重写文件头：把两条假的单独列出并写明"从未实现"，其余九条保留。
没有实现它们 —— 因为"下发队列"和"按天保留"都是产品级决定，不该由审计顺手加。

## 3. 这是第六处「注释比代码更用力」

前五处：`quota()`、`DiagFlags.silent`、`struct Advice`、`DiagOp/DiagOps`、`selfCheckWarning`。
本轮的特别之处是：**它写在文件头，读的人最多**，而且格式整齐（对齐的键名+编号+用途），
看起来比正文还可信。

## 4. 方法论

**整齐的格式会伪造可信度。** 一张对齐的表格、一份编号的清单，会让人默认它是核对过的；
而实际上它可能只是当年写计划时抄下来的。

判据：**任何列了"键名/文件名/函数名"的清单，都要能被一条命令复核**。
复核方式就一句：把清单里的每一项拿去 grep，数非注释命中。零命中的项，要么实现，要么删掉。
