# AUDIT-ROUND-205 · 第 205 轮：锁档案页并排显示「本机池 vs 锁端存量」

> 承接第 203/204 轮：rc=2 的两个候选根因都是「池子不一致」—— 那就把不一致直接显示出来。

## 1. 做了什么

`DeviceInfoScreen` 的「PIN 容量」行下面加一行对照：

| 情况 | 显示 |
|---|---|
| 本机 64 枚 = 锁端已用 64 | 「本机池 64 枚 · 与锁端一致」（灰） |
| 本机 20 ≠ 锁端 64 | 「本机池 20 枚 · 锁端已用 64 枚 —— 不一致，现签凭证会被拒（rc=2）」（**黄**） |
| 本机池为空 | 「本机池为空」 |
| 没读到锁容量 | 不显示（不假装知道） |

数据源：锁端 `pinStock`（cmd03 KLV#22，已用量 = capacity − stock）vs 本机 `kc.pins`。
两个数**早就都在**，只是从没被放在一起 —— 又一个「两套口径并存」的例子。

## 2. 与第 203 轮的判读表接上了

现在用户的排障路径是：

```
设备信息页看对照 →
  一致 ⇒ 池子没问题，rc=2 另有原因（把交互流水发来）
  不一致 ⇒ 池子被污染/两台 App 打架 ⇒ 重新配网
```

不用再等日志往返。

## 4. 方法论

**排障信息的第一形态不是日志，是"两个应该相等的数并排放着"。**

| 形态 | 谁能用 |
|---|---|
| 交互流水 | 会发日志的人 |
| **并排读数** | **所有人 —— 一眼看出"不一样"** |

同族还有「本机 pwd/fps 数 vs 锁端存量」（已有 `capacityText`），本轮只补了 PIN ——
因为 rc=2 的判据就是它。
