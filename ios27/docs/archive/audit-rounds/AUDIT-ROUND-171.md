## 1. 缺陷：文档写了，但索引里找不到

README 的「文档」表只列了 4 项：

```
DESIGN-CONTRACT.md / ARCHITECTURE.md / IMPLEMENTATION-BRIEF.md / PROGRESS-*.md
```

而 `docs/` 下实际有 **28 份**非轮次文档。其中 5 份是"后来者最需要"的：

| 文档 | 为什么重要 | 索引里有吗 |
|---|---|---|
| `DESIGN-CONFORMANCE.md` | iOS 27 符合性报告（本 objective 的产出） | ❌ |
| `AUDIT-METHOD.md` | 9 条找缺陷的判据 | ❌ |
| `AUDIT-COVERAGE.md` | 覆盖矩阵 + 逐文件台账 | ❌ |
| `AUDIT-CLOSING.md` | 做完了什么 / 还剩什么 | ❌ |
| `RESERVED.md` | 6 条保留未接 | ❌ |

**"写了但没人找得到"约等于没写** —— 与 ROUND-141 那条"死声明"是同一类问题，只是发生在文档层。

## 2. 修法

README 的表格加 5 行，每行一句"这份文档回答什么问题"。

不给"详细说明"这种空话 —— 每行都写**读者能据此判断要不要打开它**的信息，例如：

```
| docs/DESIGN-CONFORMANCE.md | iOS 27 设计符合性报告 —— 原生控件 / 液态玻璃七条清单 /
                              文字占用 / 布局，逐条带引用，含 4 条已知偏差与不修的理由 |
```

## 3. 顺带确认

`workflow.js`（第 6 道闸门）核对的是 README / CI yml / ARCHITECTURE / COMPLETION / AUDIT-COVERAGE
这 5 个文件里的**闸门数一致性**。本轮只加文档索引行，不动任何数字 —— 闸门仍然 22/22。

## 4. 方法论

**"可发现性"是文档的一部分，不是附加项。**

| 状态 | 后果 |
|---|---|
| 文件存在 + 索引里有 | 会被读 |
| **文件存在 + 索引里没有** | **不会被读**（新人只从 README 进） |

判据：**每新增一份"给后来者看"的文档，同一次提交里就要把它接进索引。**
事后补是几乎不会发生的 —— 因为文件已经"完成"了，人的注意力就走了。
