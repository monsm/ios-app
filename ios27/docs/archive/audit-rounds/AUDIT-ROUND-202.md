## 1. 存储栈的形状

```
enum DB                    ← 命名空间（台账 / 日志 / 状态投影）
 └ Store (UserDefaults)    ← @unchecked Sendable（UserDefaults 本身线程安全）

```

## 3. 两个特别值得肯定的设计

**（a）`clearAll()` 在第 92 批被删除而不是保留** —— 「一把删光所有 kf.* 键」没有调用点，
但留着它就是给未来某个「重置」按钮上膛。删除时还写清了理由：
「真要全清得先定清哪些键属于 App —— 那是设计不是一行删除」。

**（b）失败台账刻意没有清空口** ——
「加一个 `clearFailureLog()` 只会多一条零调用声明，而且给了"把证据抹掉但不告诉用户抹了什么"的按钮。」

**「不加 API」和「加 API」一样需要理由** —— 这两处是全仓最成熟的判断之一。

## 4. 方法论

**判断"这段并发代码对不对"，问的不是"有没有锁"，而是「这个动作由几步组成、这几步会不会被另一个线程看见一半」。**

| 步数 | 需要什么 |
|---|---|
| 1 步（`defaults.set`） | 不需要（单调用原子） |
| **≥2 步（读→改→写）** | **必须上锁或走队列** —— 两个线程各持旧快照时，后写者覆盖先写者 |

本仓所有 ≥2 步的写入都已收口。这条结论由本轮记录，下轮不用重查。
