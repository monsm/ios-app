# AUDIT-ROUND-278 · 第 278 轮：自查我新加的诊断屏 —— 无缺陷

> CI：`d287a34` build ✅；golden 仍停在 `1f84bca`（`d287a34` 的金标还在队列里）。

## 1. 为什么自查

`DiagStreamScreen` 是本会话为排障新建的。它有一个**内存数组** `rawTrace`（原始帧，含密钥），
这类「只增不减的缓冲区」是典型的内存增长点，必须确认有上限。

## 2. 核对结果

| 检查 | 结论 |
|---|---|
| `rawTrace` 有上限吗 | ✅ 300 条，超出丢最旧（`LockService.swift:90`） |
| `lines` / `events` 是快照还是每次重读 | ✅ **计算属性**，每次 body 求值都读最新 |
| 界面会不会刷新 | ✅ 打开「记录原始交互帧」后 `rawTrace` 增长 ⇒ 可观察属性变化 ⇒ 实时刷新 |
| 关闭原始帧时呢 | 无观察源，但页面自己写的流程是「去门页开一次门，再回来」—— 重新出现会重算 ✅ |
| `rawOn` 初值 | 从 `kf_debug_raw` 读一次；该键只有本屏写 ✅ |

**结论：无缺陷。**

## 3. 一个可以更好但不构成缺陷的点

屏幕没有「手动刷新」按钮。关闭原始帧时，若用户一直停在页面上（例如让别人去开门），
列表不会自动更新 —— 但页面文案已经写明流程是「开一次门再回来」，且重进即刷新，所以不算 bug。

## 4. 方法论

**「计算属性 vs 快照」决定了一个调试屏会不会给出过期数据 —— 这是自查的第一问。**

| 写法 | 刷新行为 |
|---|---|
| `@State` + `onAppear` 一次性加载 | 需要显式刷新点 |
| **计算属性（每次重读）** | **只要有任一观察源变化就自动新** ✅ |

判据：**调试类页面优先用计算属性读数据源；再确保页面至少有一个可观察依赖（否则连重算都不会触发）。**
