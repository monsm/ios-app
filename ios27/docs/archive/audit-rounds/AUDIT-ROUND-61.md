## 1. `struct Diff` —— 第五处「命名即承诺」

`CredentialOrg.swift` 里有一个 `struct Diff: Identifiable`（label/old/neu + 计算属性 `kind`），
注释写「489 修订着色 diff（删除红/新增绿/修改黄，逐字段对齐）」。

全仓搜索 `Diff`：只有声明本身、`CredentialModels.swift` 的文件头注释、以及一处**同名但无关**的
`digitDiff(old:new:)`（数字位差异，仍在使用）。

前者零生产者零消费者 —— 与 `quota()` / `DiagFlags.silent` / `Advice` / `DiagOps` 同一族。已删除，
并在原处写明「`digitDiff` 是另一个函数，不要一起删」（这类"同名不同物"是删除时最容易误伤的地方）。

## 2. `CredPackage`：只能导出，没有导入

`exportPackage(...)` 会加密打包所选凭证并返回密文 —— 这条是真的。
但全仓**没有任何 `importPackage`**：`CredPackage` 的唯一构造点就是导出。

也就是说：用户能把凭证包发出去，**却没有任何入口能把它装回来**（包括本机自己）。

UI 文案只写「凭证包导出（CredPackage 加密）」「导出所选凭证包」，**没有承诺导入** ——
所以这不是"假功能"，是**单向功能**。

## 3. 为什么不补导入

导入需要：解密 → schema 校验 → 别名冲突处理 → 与回收站/快照的交互 → 权限确认 ——
这是一个独立特性，不是审计能顺手加的。而且它涉及"把外部凭证写进本机"的信任边界，
应当与"校验和确认""恢复预演"同一套设计，不能随手拼。

所以本轮只**记录**这个缺口（已写进 `AUDIT-COVERAGE.md` 的未覆盖项）。

## 4. 方法论

**删除死代码时，最大的风险是"同名不同物"。**
`Diff`（结构体）与 `digitDiff`（函数）在 grep 里会一起出现，
如果按"看到 Diff 就删"的粗暴方式处理，就会删掉正在使用的数字位对比。

判据：**删之前先在原处写清"旁边的同名物是什么、为什么不能一起删"**，
这样下一个人（或下一次的我）不会重复踩。
