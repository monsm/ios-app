# AUDIT-ROUND-193 · 第 193 轮：**真机日志定位「手动开锁总是失败」**（用户提供流水）

## 1. 日志事实（60 行，MAC fbb993c5cc95）

| 观察 | 含义 |
|---|---|
| `cmd01 会话令牌` 正常 | 会话链路 OK |
| **`cmd03 加密状态 -> rc=0`** | **加密与 skey 完全正常**（这条最关键：排除了"密钥错"这一大类） |
| `cmd04 开锁 -> rc=2` × 6 次 | 锁明确回 **「无效的PIN码」** |
| 第 19 行与第 26 行 **TX hex 逐字节相同** | "自愈重试"发的是**同一帧** ⇒ 空转 |
| 共 6 次 cmd04（3 轮自动重试 × 2） | 自动重试把同一条命令连发了 6 次 |

## 2. 根因（能确定的部分）

`rc=2` 是锁端**解开了** ekey、但**里面那枚 PIN 不在它的 PIN 表里**。

不是密钥错（cmd03 已经 rc=0），不是帧格式错（否则会是 rc=1/11 解密失败或 rc=12 mac 错）。

### 为什么"自愈重试"没用

```swift
let pin = kc.pins.first(where: { !$0.isEmpty })   // ← 就是当初签存储 ekey 的那一枚
let fresh = signed(pin)                          // ← AES-ECB 无随机数 ⇒ 密文必然相同
```

AES-ECB 是**确定性**的：同样的 `(skey, mac, pin, 有效期, cmd)` 加密出来就是同一串字节。
所以"换一枚现签"实际换的还是同一枚 —— 日志里两帧 hex 一模一样就是证据。

## 3. 修法（两处，都由这份日志驱动）

**（a）`unlock` 的凭证回落改为「逐枚 PIN 试」**

```swift
var tried: Set<String> = [cred]                  // 记住已经发过的密文
for (idx, pin) in kc.pins.enumerated() where !pin.isEmpty {
    let fresh = signed(pin)
    if fresh.isEmpty || tried.contains(fresh) { continue }   // 与刚才那帧相同就跳过
    tried.insert(fresh)
    log("info", "…改用本机 PIN 池第 \(idx + 1) 枚现签重试")
    r = try await exec(...)
    if r.rc == 0 || r.rc == 22 { break }
    if ![1, 2, 6, 11].contains(r.rc) { break }   // 非凭证类就别再换
}
```

**（b）凭证类失败不再自动重试**

`runUnlockChain` 原来对 `rc` 错误也会重试 3 轮；而 `rc=2` 是确定性的
—— 同一枚凭证再发必然同样结果。现在遇到 1/2/6/11 直接如实报错，不再连发。

## 4. 还需要用户确认的（本机做不到）

| 步骤 | 期望 |
|---|---|
| 「锁档案 → 开锁 PIN」选**第 2 / 3 枚**，再开一次 | 若某枚能开 ⇒ 第一枚是失效的那枚，本机 PIN 池与锁端不同步 |
| 若全都不行 | 说明本机 `kc.pins` 整体与锁端不一致 —— 需要重新同步 PIN（cmd08）或重新配对 |

**这条只能真机验证**：本机能确认的是"哪一段错了"，不能确认"哪枚 PIN 是对的"。

## 5. 顺带发现（未改）

日志第 1–4 行有两组「缓存 deviceId 直连失败（连接已取消 / 连接已断开）」——
说明**预热与开锁两条路径同时调了 `ensureConnected`**，互相把对方的连接打断了。
不致命（随后扫描解析成功），但会多花 2–3 秒。已记录，未改（需先确认预热与开锁的时序意图）。

## 6. 方法论

**真机日志能把"猜"变成"排除"。**

| 证据 | 排除掉的可能 |
|---|---|
| `cmd03 rc=0` | 密钥错、配对被破坏、加密实现错 |
| `rc=2`（不是 1/11/12） | 帧格式错、mac 错、解密失败 |
| **两帧 hex 相同** | "换了凭证" |

三条一排除，只剩一个方向：**这枚 PIN 不在锁里**。
这正是上一轮做「交互流水」的目的 —— 没有它，只能在"可能的地方"逐个猜。
