# AUDIT-ROUND-269 · 第 269 轮：界面显示「双击开锁」，实际**轻点一下就开**

> CI：**`345756d` build 全绿**（名册人数口径修复编译通过）；`6c20d1c` / `fb152c1` 排队中。

## 1. 缺陷

门页的手势是这样定的（`DoorScreen.effectiveGesture`）：

    第一行：if !holdConfirm { return "tap" }      ← 一票否决
    之后：按 gestureMode 取 hold / tap / double

而设置页（无障碍）的三个手势芯片**一直可点**，还会把「双击开锁」显示成已选中。于是：

| 用户设置 | 界面显示 | 实际行为 |
|---|---|---|
| 双击 + 关闭「按住确认」 | 「双击开锁」高亮 | **轻点直开** |

这不是「设置没生效」那么简单 —— **安全语义被悄悄改掉了**：
用户以为双击在防误触，实际上一次轻点就把门打开。

## 2. 修法：让界面说实话（不改行为）

行为本身是有意的（「按住确认」是总闸，它的说明文案也写着「关掉后退回轻点直开」），
所以**不动 `effectiveGesture`**，改界面：

| 改动 | 说明 |
|---|---|
| 芯片 `.disabled(!holdConfirm)` + 降透明度 | 关闭时不能选，也不冒充已生效 |
| 关闭时补一句说明 | 「按住确认开锁」关闭时，手势固定为轻点直开 —— 想用按住或双击，请先打开下面的开关 |
| 判禁用用 `SettingsStore.shared.holdConfirm` | 而不是本地 `@State`（安全页也能改这个开关，本地镜像会滞后） |

## 3. 方法论

**一个「总闸」式的开关，会让它下游的所有选项变成装饰 —— 界面必须把这件事说出来。**

| 形态 | 检查 |
|---|---|
| A 开关关掉后，B/C 选项是否仍然可选 | 若可，而逻辑上被忽略 ⇒ **界面在撒谎** |

判据：**凡是存在「一票否决」的判据（`if !X { return 固定值 }`），X 的所有同级选项都必须联动禁用或标注。**
查法：grep `return "` 与 `!xxx` 同时出现在一个计算属性里的地方。
