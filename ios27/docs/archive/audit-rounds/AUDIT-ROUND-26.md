# AUDIT-ROUND-26 · 第二十六轮：批量延期的「失败」只报了一半

> CI：`98d5fb6` 已验证编译通过（errors=0、build_ok=1）；金标在 `87ee8f8` 为 63 tests / 0 失败

## 1. 缺陷：两类失败被混成一个数字，其中一类从不显示

`batchExtend` 的返回是 `(done: [Int], failed: [Int])`，其中 `failed` 只表示
**本机台账里找不到这个编号**。但界面在循环里逐条下发 0B 到锁，**下发失败**是另一类：

```swift
var ok = 0
for alias in r.done {
    if case .success = await app.setPasswordExpiry(...) { ok += 1 }
}
studioOutcome = "已延期 \(ok) 条（本机 \(r.done.count) 条，失败 \(r.failed.count) 条）"
```

于是「5 条本机改了、其中 3 条下发成功、2 条下发失败」会显示成：

> 已延期 3 条（本机 5 条，失败 **0** 条）

"失败 0 条"是**假**的：有 2 条锁端仍是旧有效期。用户以为全改完了，
到日期那天那两条按旧时间失效（或该失效的没失效）。

## 2. 修法

分开统计、分开表述：

- `r.failed` → 「本机找不到 N 条（编号 …）」
- `remoteFailed` → 「下发到锁失败 N 条（本机已改，锁端仍是旧有效期，请重试）」

两者都为 0 时文案保持简洁（只有"已延期 N 条"）。

## 3. 顺带更正：注释在承诺一个不存在的队列

`CredentialOrgBatch.swift` 头注释与两处函数注释写着「下发部分只入队」「锁端删除入队」
「到场后统一补发」。但本仓**没有**凭证操作的发件箱 —— `DiagKit` 里明确记着
旧的 `WriteQueue` 因**全库零写入方**已被删除。

事实是：批量停用只把条目移进回收站并删本机台账行，**锁端凭证仍能开门**，
直到用户单独在锁上删除。界面对此是诚实的（「锁端凭证不会自动删除」），
但注释会让人去找一个不存在的 flush 逻辑。已改成如实描述。

## 4. 方法论

**"失败数"这种聚合指标，一旦把不同成因混在一起，就会变成安慰剂。**
本轮的 `失败 0 条` 不是计算错误，是**口径错误** —— 它统计的是"找不到"，
却摆在"延期失败"的位置上。

可复用判据：**任何显示给用户的"失败/成功"计数，都必须说明它计的是什么事件**；
两种不同的事件不能共用一个数字。
