# AUDIT-ROUND-41 · 第四十一轮：还原回收站会静默覆盖同别名的新凭证

> CI：`c12c91d` 已验证（errors=0）；本轮**只本地提交、不推送**（攒批中）。

## 1. 缺陷链

三步都是既有设计，单独看都合理：

1. 别名（`alias`）由**锁端**分配 —— `LockService.pwdAdd` 返回槽位号；
2. 删除后该槽位会被下一把新钥匙**复用**；
3. `DB.addPwd` 的实现是 `l.pwds.removeAll { $0.alias == p.alias }; l.pwds.append(p)`。

于是这条路径没有任何一步"看起来错"，但结果是：

> 删掉 #3（进回收站）→ 新增一条（锁又给了 #3）→ 从回收站还原旧 #3
> ⇒ **新凭证被旧凭证静默覆盖，不可逆。**

而且还原按钮在失败时**什么都不显示**（`if restore { ... }` 没有 else），
用户连"没还原成功"都看不出来。

## 2. 修法

- `CredBinStore.restore` 先查同别名是否已被占用，占用即**拒绝还原**（不做不可逆覆盖）；
- 界面把原因说清楚：「编号 #N 已被其它凭证占用（锁端会复用删除后的槽位），请先在锁上处理那一条」。

## 3. 新增测试

`testBinRestoreRefusesAliasCollision`：台账里放"新凭证 #3"、回收站里放"旧凭证 #3"，
断言 `restore` 返回 false 且台账里仍是"新凭证"。

## 4. 方法论

**每个"便捷函数"都可能藏着一个覆盖语义。** `addPwd` 名字像"添加"，
实际是"先删同号再加" —— 对新增场景它是便利（幂等），对还原场景它就是数据丢失。

判据：**凡是 `removeAll { key == x }` 之后再插入的写法，都要问一句"这里的 key 冲突是错误还是预期"**。
新增时冲突=预期（覆盖旧草稿），还原时冲突=必须先拒绝。
