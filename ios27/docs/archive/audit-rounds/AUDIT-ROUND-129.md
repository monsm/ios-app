## 1. 为什么这条值得做闸门

上轮的缺陷是：ROUND-93 给 `KeyItem` 加了 `var createdAt: Double = 0`，
而三处「逐字段重建」没跟着加 —— **CI 全绿、21 道闸门全绿、82 个测试全过**，
没有任何自动化能发现。

这不是偶发：**"带默认值的字段"天然掩盖漏传**。只要有人再给别的结构体加默认值字段，
同样的事会再发生。所以它值得一条闸门。

## 2. `Gates/memberfill.js`

判据：对 `WATCHED` 里登记的类型/字段，**每一处 `TypeName(` 构造点都必须显式传该标签**，
除非构造点列在 `EXEMPT` 里（且写明理由）。

```js
const WATCHED = { KeyItem: ['createdAt'] };
const EXEMPT = [
  // 手机钥匙没有「创建时刻」这个概念 —— 保持默认 0 是对的。
  "App/Shell/AppModel.swift:189",
];
```

实现要点：

| 点 | 做法 |
|---|---|
| 跨行构造 | 从 `TypeName(` 起扫到配对的 `)`，最多看 20 行（本仓构造最长约 10 行） |
| 跳过注释 | 行首 `//` 不看 |
| 豁免 | `file:line` 前缀匹配，每条必须写理由 |

## 5. 这条闸门的诚实边界（已写进 ARCHITECTURE §5.1）

> 只查已登记类型（`KeyItem`）的已登记字段（`createdAt`）；其它类型/字段要手动加进 `WATCHED`。
> 它只看「有没有写这个标签」，**不检查值是否来自正确的源**。

也就是说它防的是"忘了传"，不防"传错了"。后者仍要靠人读。

## 6. 方法论

**"这次的回归能变成闸门吗" —— 修完缺陷后应当问一句。**

| 缺陷 | 能机械化吗 | 结论 |
|---|---|---|
| 带默认值字段漏传 | ✅ 能（形状规则） | **做成闸门 22** |
| `@escaping` 位置 | ✅ 能（但编译器已覆盖，不必重复） | 不做 |
| `createdAt` 值取错了源 | ❌ 不能（要类型/数据流） | 靠人读 |

判据：**"忘了做某事"型缺陷可机械化；"做错了某事"型不能。**
