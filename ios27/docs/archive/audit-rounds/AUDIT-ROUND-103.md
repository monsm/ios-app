# AUDIT-ROUND-103 · 第一百零三轮：一个我自己造成的遗漏

> CI：`539d4f7` 已验证（build + golden 均通过）；`cceceb7` / `4ea2c9f` 待回执。

## 1. 缺陷：CI 工作流的 job 名还写着 20 道

上一轮把闸门从 20 增到 21，我跑了 `git add -A ios27` —— 而 `.github/workflows/ios27.yml`
**在 `ios27/` 之外**（在仓库根的 `.github/`）。于是那次提交漏了它，工作区里留着一个未提交的修改：

```diff
-    name: 静态闸门（20 道）
+    name: 静态闸门（21 道）
```

## 2. 为什么这个遗漏值得记

它本身影响很小（只是 job 显示名），但**暴露了一个会重复发生的操作习惯问题**：

> 我用 `git add -A ios27` 作为"把本轮改动提交掉"的固定写法，
> 而审计对象**不总在 `ios27/` 里** —— `.github/`、仓库根的其它文件都不在覆盖范围。

后果有两种：

| 情形 | 结果 |
|---|---|
| 改动了 ios27/ 之外的文件 | **不会被提交**，但会被下一轮的 `git add -A ios27` 一直漏着 |
| 检查"工作区是否干净"时 | 我上一轮确实看到 `git status` 有 1 项未提交 —— 但没去看它是什么 |

第二条更要紧：**我看到过这个信号，却没读它。**

## 3. 修法

提交那一行改动，并把操作习惯改成：**提交前先看 `git status --short` 的全部输出**，
而不是只看"有几项"。

## 4. 方法论

**"我看到一个异常信号但没读它"，比"没看到"更危险** —— 因为它给了我"检查过了"的错觉。

本段前几轮我已经两次因为"没读 `test.log` 只看计数"而误判 CI 状态，
这次是同一形态的第三次（`git status` 只看条数、不看内容）。

判据：**任何"计数型"检查（有几项失败 / 几项未提交 / 几行错误）都必须跟一次"读内容"**，
否则它只是安慰剂。
