# AUDIT-ROUND-317 · 第 317 轮：空壳模式下新增凭证会「假成功」—— 空壳审计收尾

> CI：`07120168` build 全绿（errors=0）。

## 1. 缺陷：拒写是静默的，调用方以为成功

`saveLedger` 在空壳下做的事情（写得很好）：

    if isDecoy {
        BleTelemetry.recordEvent("空壳模式下拒绝台账写入 …", ok: false)
        return
    }

**但对调用方是静默的** —— 它返回 `Void`，没有任何「被拒」的信号。

于是这条链：

| 步骤 | 实际发生 |
|---|---|
| 空壳里点「新增凭证」（门页快捷格可达） | 表单正常打开 |
| 提交 → `AppModel.addPassword` → `pwdAdd` 下发成功 → `addPwd` → `saveLedger` | **被拒，什么都没写** |
| 界面 | **报「已添加」，还会出现在锁端** |
| 退出空壳后 | 本机台账里**没有这条** |

这是「假成功」—— 比直接失败更糟：用户以为加上了，下次开不了门才发现。

## 2. 修法：三处创建入口在空壳下返回真实失败

`addPassword` / `addTempCode` / `enrollFingerprint` 都返回 `Result` ⇒ 加一道：

    guard !DB.isDecoy else { return .failure(BLEErrorX.msg("当前无法保存，请稍后再试")) }

文案**中性**，不暴露「你处在空壳模式」（那等于告诉胁迫者这里有伪装机制）。

## 4. 一处**记录在案的设计后果**（不改，留给你决定）

门页恢复可用后，快捷格里的「动态码」与「分享二维码」也能取到真实 `skey` ⇒
**空壳下仍能生成可开门的动态码/二维码**。

| 视角 | 判断 |
|---|---|
| 与「门照样能开」一致 | ✅ 开门能力本来就该保留 |
| 但「把码发给别人」≠「自己开一次门」 | ⚠️ 多了一种可转发的凭据 |

要不要在空壳下把这两页也拦住，取决于你对「空壳下可以出示开门凭据」的接受度 —— **这一条我没擅自改**。

## 5. 方法论

**「拒绝写」必须让调用方知道 —— 静默拒绝 = 假成功，比报错更糟。**

| 写法 | 用户看到 |
|---|---|
| 静默 `return` | 「已添加」+ 实际没有 |
| **返回失败** | 「当前无法保存」+ 确实没有 ✅ |

判据：**凡是「守卫后直接 return」的写函数，都要问一句：调用方会因此报成功吗？会，就必须把拒绝变成可感知的失败。**
