# AUDIT-ROUND-250 · 第 250 轮：手动开锁会把「确定性失败」重试一遍

> CI：**`bf9a0b6` build 全绿**（死路由删除编译通过）。

## 1. 缺陷

`runUnlockChain` 的外层重试判据是：

    nonRetryable = [1, 2, 6, 11].contains(rc)

注释说这四条是「凭证类确定性失败」。但**另外三条同样是确定性的**，却没被排除：

| rc | 含义 | 重试的后果 |
|---|---|---|
| **3** | 命令已过期（锁钟漂） | 本路径**不会先校时**，原样重发必然再过期 |
| **5** | 次数用完（钥匙废了） | 必然同样失败，白耗电 |
| **26** | 防拆事件 | 锁主动拒绝，必然同样失败 |

（`25` 锁忙仍应重试 —— 等一下就好。）

## 2. 修法

    nonRetryable = [1, 2, 3, 5, 6, 11, 26].contains(rc)

并在注释里写清每一条**为什么**不可自愈。

## 3. 顺带核对：内层「多 PIN 回退」是对的

`LockService.unlock` 的逐枚重试有自己的跳出条件：

    if ![1, 2, 6, 11].contains(r.rc) { break }

`rc=3/5/26` 会立刻跳出 ✅ —— 也就是说**同一份判据在内层是对的、在外层是漏的**。

## 4. 方法论

**同一份「哪些 rc 可重试」的知识，出现在两个层次时，必须同时维护。**

| 层 | 判据 | 状态 |
|---|---|---|
| 内层（逐 PIN） | `[1,2,6,11]` 继续，其余跳出 | ✅ 一直是对的 |
| **外层（整体重试）** | `[1,2,6,11]` 不重试，其余重试 | ❌ **把 3/5/26 也重试了** |

判据：**看到一处「可重试 rc 白名单/黑名单」，就 grep 全仓同义判断，逐处对齐。**
（与 Round 243 的「修一处要 grep 同类构造点」是同一条纪律的另一个面。）
