# AUDIT-ROUND-31 · 第三十一轮：门页那句「将在 2 小时内到期」有两个错

> CI：`2d38982` 已验证（errors=0、build_ok=1）；`d1bf3b5` / `5136831` / 本轮提交待回执

## 1. 错一：把**已过期**的条目说成「将在 2 小时内到期」

`dueSoonPwds` 的窗口是 `[now-1h, now+2h]` —— 起点在过去，
也就是**包含已过期 1 小时内**的凭证（这是有意的：刚过期还值得提一句）。

但门页文案一律写：

> 有 N 条凭证将在 2 小时内到期（最近一条 #x）— 需要续期请到凭证页

对那几条已过期的，这句话是**假的**：它们早就不放行了，
用户按"还有 2 小时"去安排会误事。

**修法**：按名单里最近一条的到期时刻判断，分别说
「已过期 … 锁端已不再放行」或「将在 2 小时内到期 …」。

## 2. 错二：「最近一条」其实不是最近的

`DB.listPwds(mac)` 返回的是**台账顺序（按别名）**，不是时间顺序。
直接取 `due[0]` 得到的是"别名最小的那条"，不是"最接近现在的那条" ——
所以「最近一条 #x」这句话从一开始就是假的。

**修法**：函数内按 `|到期时刻 − 现在|` 升序排序再返回。
用绝对距离而不是"最早到期"：窗口里可能同时有已过期与将到期的条目，
「最近」在两种情况下都应是离此刻最近的那条。

## 3. 新增测试

`testDueSoonWindowAndNearestOrdering`：造三条（-30 分钟 / +10 分钟 / +5 小时），断言

- 名单只含前两条（+5 小时在窗口外）；
- 第一条是 **+10 分钟**那条（离现在最近），而不是别名更小的 -30 分钟那条。

## 4. 方法论

**文案里的每个限定词都是一个断言。**「最近一条」断言了排序，「2 小时内到期」
断言了窗口方向。两处都与实现不符，而且都不会崩、不会报错 ——
只有把文案逐词对照代码才看得见。

判据：**写用户可见文案时，把每个形容词/数量词回读一遍代码**：
「最近」= 按什么排的序？「2 小时内」= 窗口两端在哪？「共 N 条」= N 算的是哪一批？
