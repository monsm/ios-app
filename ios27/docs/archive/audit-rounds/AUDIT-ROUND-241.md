# AUDIT-ROUND-241 · 第 241 轮：**「先归档一位再建新人」—— 归档根本不腾位置**

> CI：`f19322d` build 全绿；`ac0e3ed` / `5b50460` / `42e5134` 排队中。

## 1. 缺陷

`HouseholdScreen` 的提示文案写得很明确：

> 已到本机成员上限 15 位 —— **先归档一位再建新人**（归档不删历史）。

而判定是 `app.members.count >= HHStats.memberLimit`，其中 `app.members` **包含已归档的成员**
（`HHStats.active` 才是过滤后的）。于是：

| 状态 | 显示 | `atLimit` |
|---|---|---|
| 14 在册 + 1 归档 | 「成员 14 位」 | **true**（15 ≥ 15） |
| 用户照文案归档一位 | 「成员 13 位」 | **仍 true**（15 ≥ 15） |
| 用户继续归档 | 数字一路降 | **永远 true** |

**这是一条死路**：文案给了一个明确可行的建议，而代码让它无效。

## 2. 修法

两处 `atLimit`（`HouseholdScreen` / `MemberCreateScreen`）都改成只数**在册**成员：
`HHStats.active(app.members).count >= HHStats.memberLimit`。

这样**显示的数字、上限判定、提示文案**三方一致。

## 3. 方法论

**当一句提示文案给出「可操作的建议」时，它其实是一个契约 —— 必须验证那个操作真的有效。**

| 文案类型 | 要不要验证 |
|---|---|
| 解释性（「这是本地数据」） | 不必 |
| **可操作建议（「先归档一位再建」）** | **必须** —— 用户会照做 |

判据：**凡是文案里出现「请先…」「…再…」「去…即可」的，都要真的走一遍那条路径。**
本轮的路径走一遍就露馅：归档 → 数字变了 → 按钮还是灰的。
