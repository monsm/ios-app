# AUDIT-ROUND-253 · 第 253 轮：刚显示出来的失败原因，会被下一次刷新**悄悄清掉**

> CI：**`8beeb83` build 全绿**（重试策略修复编译通过）。

## 1. 缺陷（Round 252 修法的下一步）

Round 252 让门页显示 `app.lastError` 里的失败原因。但 `lastError` 是**跨功能共用的单一错误槽**：

    func refreshStatus() async {
        lastError = nil        // ← 开工先清槽
        …
    }

于是开锁失败后，只要发生**任何一次状态刷新**（回到前台、下拉重扫、别处触发），
那条原因就会被清掉，卡片随之消失。

| 时刻 | `lastError` | 用户看到 |
|---|---|---|
| 开锁失败 | 「无效的PIN码…」 | 原因卡片 ✅ |
| 一次 `refreshStatus()` 后 | `nil` | **卡片消失，原因没了** |

## 2. 正确归属

这次失败真正的归属地是 **`dialPhase`**：

    dialPhase = .failed(msg)     // 与 lastError 同一个 msg，但只由开锁流程改写

而 `DialPhase.failed(String)` 的关联值此前**零消费**（`progress` / `word` / `isFailed` 都不读它）。

## 3. 修法

失败链改为：

1. 优先取 `dialPhase` 的关联值（开锁专属，不会被别的刷新清掉）
2. `lastError` 仅作兜底

顺带让那个「死关联值」有了用途 —— 不是删掉它，而是**把它放回正确的消费点**。

## 4. 方法论

**「单一共享槽」的读法必须考虑**谁会清它**；写进去只是第一步。**

| 设计 | 风险 |
|---|---|
| 一个全局 `lastError` 给所有功能用 | 任何一个功能的"开工清槽"都会清掉别人的 |
| **把结果挂在它自己的状态上**（`dialPhase.failed`） | 生命周期与功能一致，不会被误清 |

判据：**错误信息应该跟着「产生它的那个操作的状态」走，而不是跟着一个全局槽走。**
本仓这条 `lastError` 已经被 Round 381 行注释承认是"跨功能共用"，本轮才算把**开锁**这条迁到正确归属地。
