# AUDIT-ROUND-256 · 第 256 轮：横幅说「链路已断开」，而它从没断开过

> CI：**`f370626` build 全绿**（开锁错误显示编译通过）。

## 1. 缺陷

配网失败时 `AddLockScreen.rollback(_:)` 被调用，横幅文案是：

> 已中止：**链路已断开**，锁没有被改一半就留着。

而函数体只有四行：

    steps = []
    picked = nil
    banner = reason
    phase = .ready

**没有 `LockService.disconnect()`。链路真的还连着。**

| 文案断言 | 实际 |
|---|---|
| 链路已断开 | ❌ 仍连着 |

后果：用户再点一次配网会撞上"已有连接"（`ensureConnected` 的单飞逻辑会等一个已经没人在等的连接），
而界面上写的是"已断开"—— 用户完全无从理解。

## 2. 顺带纠正原 TODO 的一个错误方向

原 TODO 写着：

> 真实回滚还要断开链路并**清掉半成品台账与 lastDevice 指针**。

但 `DB.clearPendingPair` 的注释恰恰说明**不能清**：

> 只清钥匙串本身。**不动**未完成的配网记录: 配网尾链失败时 UI 的 rollback 会调到这里,
> 而那一份记录正是"**再点一次配网就能接着配完**"的依据（2026-10-17 真机截图里的承诺就是它）。

`lastDevice` 同理 —— 它指向的是**已配好的**锁，不是半成品。

所以本轮只补「断开」，**不清** pendingPair / lastDevice，并把这条理由写进注释（免得下一个人照着旧 TODO 去清）。

## 3. 方法论

**TODO 也会写错方向 —— 尤其当它与另一处注释的**设计承诺**冲突时。**

| 依据 | 说什么 |
|---|---|
| 旧 TODO（一行） | 要清 pendingPair |
| `clearPendingPair` 的注释（带真机截图出处） | **不能清**，那是"接着配完"的依据 |

判据：**动手前先看被改的那一行的**调用方注释**——它往往记录了"为什么故意不这么做"。**
本仓的 `【保留未接】` / 「⚠ 核实」注释都属于这类高价值依据，优先级高于一行 TODO。
