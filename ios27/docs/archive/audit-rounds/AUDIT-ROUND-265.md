# AUDIT-ROUND-265 · 第 265 轮：写钥匙串钥匙，成功失败都没反应

> CI：**`d8fc80d` build 全绿**（MAC 归一化文档轮）；`ef58e21` 排队中。

## 1. 缺陷

`HardwareScreen.write(_:)`（把当前锁的钥匙写进钥匙串，cmd41）原本是这样收尾的：

    成功：只落库，不提示
    失败：catch { }  —— 空块，只有一句注释「失败已在按钮文案/状态中体现」

而实际上**什么都没体现** —— 唯一变化是 `writingId = nil`，转圈停了。

| 用户操作 | 界面 |
|---|---|
| 点「写入钥匙」→ 成功 | 转圈停 → **无任何提示** |
| 点「写入钥匙」→ 失败 | 转圈停 → **无任何提示** |

同页另外五个动作全都有反馈：吊销（errorText）、读状态（errorText + toast）、
查钥匙（errorText）、写假钥匙（errorText + toast）、解绑（toast）—— **只有写入这一处是哑的**。

写钥匙是**安全相关**操作：用户必须知道这把锁的钥匙到底写进去没有。

## 2. 修法

| 分支 | 现在 |
|---|---|
| 成功 | `AppToast.shared.show("钥匙已写入钥匙串", tone: .ok)` |
| 失败 | `errorText = "写入失败：…"` |

并把开头补 `errorText = nil`（与同页其它动作同款：开工清槽）。

## 3. 顺带扫描

扫全仓「空 catch（体内只有注释）」—— 6 处命中**全是假阳性**
（`} catch { return .failure(error) }` 这种同一行带代码的写法，脚本只读了后续行）。
**没有第二处静默失败** ✅。

## 4. 方法论

**同一个页面里的同类按钮，反馈方式必须一致 —— 不一致本身就是缺陷信号。**

| 检查手法 | 效果 |
|---|---|
| 逐个函数看「有没有反馈」 | 容易漏（写的人总觉得别人也这样） |
| **把同页同类动作列成表对比** | **一眼看出只有一个哑** |

判据：**把一组同类操作的「成功反馈 / 失败反馈」列成两列表，空格的那个就是 bug。**
