# AUDIT-ROUND-67 · 第六十七轮：CSV 防公式注射的顺序错，以及一个更深的漏

> CI：`f5c5238` 已验证；`610681d` / `045b73c` / `ee4b04e` 待回执。本轮本地提交。

## 1. 顺序错：先加防护引号，再规整 `\r`

```swift
// 旧实现
if let first = v.first, ["=", "+", "-", "@", "\t", "\r"].contains(String(first)) {
    v = "'" + v
}
v = v.replacingOccurrences(of: "\r", with: " ")   // ← 在加引号之后
```

输入 `"\r=x"` 的结果是 `"' =x"`：防护单引号被**留在中间**，既不再是合法防护形态，
内容还被多改了一个字符。顺序应当是**先规整、再判断**。

## 2. 修的过程中发现更深的漏：前导空格

改成"先去 `\r` 再判"之后，`"\r=x"` 变成 `" =x"` —— 首字符是空格，不触发防护。
但我写测试时意识到：**Excel / Numbers 打开 CSV 时会先 trim 前导空格再解析单元格**，
所以 `" =1+1"` 仍可能被当公式。

于是加了第二层：判断时**跳开前导空格**（`v.drop { $0 == " " }`），`\t` 仍算危险字符。

这一层不在原报告里 —— 是修第一个 bug 时顺带发现的，性质上属于**同类绕过**。

## 3. 一个闸门的脆弱性（值得记）

改完后 `privacy` 第 8 条判红：它检查"函数体内 10 行窗口里出现 `v = "'" + v`"。
我把注释写长了，那行被推到窗口之外 —— **闸门按固定行数扫描，注释一多就失效**。

这次我选择**缩短注释**让它回到窗口内（而不是改闸门），因为：
注释长度不该影响安全检查的有效性。但这也说明该规则应当改成"整个函数体"而不是"前 10 行"。
已记入下一轮的闸门改进项。

## 4. 新增测试

`testCSVEscapingNormalisesCarriageReturnFirst`：覆盖

- `"\r=1+1"` → `"' =1+1"`（`\r` 规整后仍被防护）；

- `"=1+1"` / `"+cmd"` / `"-2"` / `"@x"` → 逐个前缀都防住；
