## 1. 「超过 30 天未校时」提醒的数据源

怀疑：`DoorScreen` 用 `DB.syncTime(mac)` 与 Unix 毫秒比较，若它存的是**协议秒**，
则 `nowMs - lastSync` 恒大于 30 天 ⇒ 提醒**永远显示**（本会话已经栽过一次同类）。

核对写入点：

| 写入点 | 值 |
|---|---|
| `LockServiceOps:177`（引擎层，所有校时路径都经过） | `Date().timeIntervalSince1970 * 1000` ✅ 毫秒 |
| `SyncTimeScreen:253`（界面层补写） | 同一个 `now`（毫秒）✅ |

**两条路径都写毫秒，读侧同口径** ✅ 无缺陷。

## 2. 记录页「本次读取 N 条」的显示

| 检查 | 结论 |
|---|---|
| 用的是本次实际条数还是缓存总数 | ✅ `fetched?.read`（本次），与缓存总数不等时补一句「（记录页共 N 条）」 |
| `remaining` 什么时候提 | ✅ 仅 `> 0` 时提「锁端还有 N 条更早的记录未读」 |
| 锁端未回时刻的行 | ✅ 单独说明「另 N 条无法定位到某一天」 |

**无缺陷** —— 这正是本仓反复出错的「数字不实」一类，此处做对了。

## 3. 「还剩 N 天」的取整方向

`KeysState.daysLeft` 两端都 `startOfDay` 后取日历日差 ⇒ **不受小时影响** ✅。

| 边界 | 显示 |
|---|---|
| `days == 0` | 今天到期 |
| `days == 1` | 明天到期 |
| `days < 0` | 已过期 |

**无 off-by-one** ✅。（到期按自然日判断是既有取舍：当天 14:00 到期、15:00 看仍显示「今天到期」——
与到期月历同口径，注释已写明，不是缺陷。）

## 4. 方法论

**「数据源单位」是这类 bug 的第一嫌疑 —— 但结论必须来自读写入点，不能来自命名。**

| 只看名字 | 结论 |
|---|---|
| `syncTime` | 像秒 |
| **读写入点** | **实际是毫秒** ✅ |

判据：**凡是「时间/金额/坐标」这类带单位的数，核对时必须找到写入点看表达式，不看字段名。**
