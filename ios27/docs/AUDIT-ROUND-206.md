# AUDIT-ROUND-206 · 第 206 轮：写放大排查 —— 29 个写入点全部「操作后一次写」

> CI：`b2c6e05`（三方对比）已验证绿；`3308443` / `ce73de4` 排队中。

## 1. 为什么查这个

UserDefaults 的键值是**整键覆盖写**：`kf_keychains`（全部锁的字典）或 `kf_ledger_<mac>`
每保存一次就是一整份 JSON 重写。若有调用点在**循环里**或**每次刷新**触发，
闪存写入会被放大 —— 这是移动 App 隐性性能债的头号来源。

## 2. 全部 29 个调用点分类

| 类别 | 处数 | 判定 |
|---|---|---|
| 用户操作后写一次（加/删凭证、改名、校时） | 18 | ✅ 每次操作一次写，正常 |
| 配网/恢复批量写 | 3 | ✅ 一次性 |
| `removeMember` 内循环写 | 每把锁**最多一次**且有 `if changed` 守卫 | ✅ |
| 引擎内部（配对尾链、令牌刷新） | 4 | ✅ 会话事件级 |
| `readLogs` 日志缓存 | **循环外一次** `DB.writeLogs(mac, collected)` | ✅（不是每页写） |

**没有发现循环写/高频写。** 唯一潜在的高频路径（读日志最多 20 页）确认是聚合后一次落盘。

## 3. 顺带确认了 418 行附近三处修过的口径

`readLogs` 的尾部现在是：

```swift
DB.writeLogs(mac, collected)                       // 聚合一次写
DB.store.set("kf_logsync_" + DB.normalizeMac(mac), String(...))   // 归一化键 + 毫秒字符串
let remaining: Int? = pagesRead >= 20 ? lastSurplus : nil          // 只在截断时报告
```

三处历史修复（键归一化、值类型统一、surplus 消费）都在位 ✅。

## 4. 方法论

**「写放大」的判据不是"写了多少次"，而是「一次用户动作触发几次整表写」。**

| 模式 | 后果 |
|---|---|
| 循环内 `save(map)` | N 次全量 JSON 编码 + 闪存写 |
| 视图刷新里 `save(map)` | 每帧重写持久层 |
| **动作后一次写** | ✅ 本仓现状 |

本轮结论：无写放大。记录在案，下轮不重查。
