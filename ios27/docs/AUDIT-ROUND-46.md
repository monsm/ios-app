# AUDIT-ROUND-46 · 第四十六轮：删除成员只处理了一把锁

> CI：`9d6f645` 已验证；`7f87aef` / `2971b60` 待回执。本轮本地提交，不推送。

## 1. 缺陷：级联只走当前锁，提示只说一半

`MemberOpsStore.cascadeDelete(mac:memberID:)` 只遍历**当前这把锁**：
当前锁名下的凭证进回收站、台账行删除。

紧接着 `DB.removeMember(m.id)` 会把**所有锁**上该成员的 `owner` 清空 ——
于是其它锁上的凭证/指纹变成「无归属」，**锁端仍然有效**（指纹照样能开门）。

而界面只说：「已删除成员，N 枚凭证进入回收站」。用户会以为"这个人已经被处理干净了"。

## 2. 修法（两处）

**（1）`cascadeBinMember` 的签名去掉假承诺。**
原来：`@discardableResult static func cascadeBinMember(..., revokeLocks: Bool = false) -> Int`，
而实现里 `_ = revokeLocks` + `return 0` —— 一个"什么都不做"的参数，一个"恒为 0"的返回值。
形状本身就在承诺"撤销了锁端""返回了条数"。现在改成 `-> Void` 且没有该参数。

**（2）删除后的提示补上其它锁的数量。**

> 已删除成员，N 枚凭证进入回收站；另有 M 条在其它锁上，已转为无归属
> （锁端仍然有效，需要时请到那把锁上单独删除）

## 3. 为什么不做"跨锁全量级联"

因为那需要**逐把锁连接**才能删锁端凭证；离线 App 做不到"删了就一定生效"，
写一个"已撤销全部权限"的提示反而是安全承诺级别的假话（本仓在 D-57 上翻过同样的车）。
所以选择：**行为不变，把真相说全**。

## 4. 方法论

**多锁场景下，"删除"往往是"部分删除"。** 任何按 `mac` 分区的操作，都要问一句
「其它 mac 上的同类数据怎么办」—— 是级联、是保留、还是转无归属？
三种都可以，但**必须让用户知道是哪一种**。

这也是本轮把 `revokeLocks` 删掉的理由：参数名在替实现许愿，而实现根本做不到。
