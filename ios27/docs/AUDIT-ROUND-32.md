# AUDIT-ROUND-32 · 第三十二轮：一条永远不会出现的「数据自检异常」警告

> CI：`d1bf3b5` 已验证（errors=0、build_ok=1）；`5136831` / `2190e00` / 本轮提交待回执

## 1. 幽灵警告：只读不写的键

`BackupStudioKit` 里有一条「启动自检」：

```
static var selfCheckWarning: String? {
    DB.store.getBool("kf_bk_selfwarn") ? "数据自检异常， 去诊断" : nil
}
```

全仓搜索 `kf_bk_selfwarn` —— **只有这一处读，没有任何一处写**。
这条黄条永远不会出现：用户以为有个「启动时自动发现存储异常」的保护，其实没有。
而且 `selfCheckWarning` 本身**全仓零调用**（连界面都没读它）。

这是这栋代码库自己命名过的一类缺陷：**「命名即承诺」** ——
（`BackupStudioKit` 下面 `BkEvent` 的注释里就写着这个词，说的是「参数像有能力、实际什么都不记」。）

## 2. 为什么「补上写入」是错的

它想表达的是「上次备份后数据有变化」。但**那在正常使用中是常态** ——
改一条凭证、加一个人，指纹就变了。做成常驻黄条只会天天喊狼来了；
用户很快会无视它，真正的异常也就跟着被无视。

真正有用的入口已经有了：`BackupStudioScreen.runSelfCheck()` 按需比 `kf_bk_base` 基线、现算现报。
所以正确处置是**删掉幽灵**，而不是给它接线。

## 3. 顺带修正：三态被画成两态

那个按需自检的颜色原来是 `selfCheck.hasPrefix("一致") ? 绿 : 红`，
而它的文案有三种：一致 / 不一致 / **还没有备份基线**。
第三种是纯状态，却被涂成红色（=故障）。已改成三态三色：一致=绿、不一致=红、还没基线=中性。

## 4. 方法论

**「读得到但永远为假」的标志位，比没有这个标志位更危险** —— 它让人以为这条防线存在。

判据：**每加一个 `kf_xxx` 键，必须同时加一条「谁会写它」的检查；只读不写的键应在评审时判为缺陷**
（与「死令牌」「死开关」同一族）。
