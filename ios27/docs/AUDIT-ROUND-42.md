# AUDIT-ROUND-42 · 第四十二轮：第三处死代码（`Advice`），以及为什么不做「死类型」闸门

> CI：`c12c91d` 已验证（errors=0、build_ok=1）；本轮本地提交，**不推送**（攒批）。

## 1. `struct Advice` 是第三处「命名即承诺」

`CredentialOrg.swift` 里有个 `struct Advice`，注释写着「358/505 整理建议中心」，
字段是 `id/title/sub/icon/action`（action 还列了五种取值）。

全仓搜索 `Advice`：**只有两处出现** —— `CredentialModels.swift` 的文件头注释，和这个声明本身。
零生产者、零消费者。所谓「整理建议中心」从未建成，但结构体留着，让人以为有这套功能。

这与前两处（`quota()`、`DiagFlags.silent`）是同一族。已删除并留下说明。

## 2. 试过做「死类型」闸门，结论是**不该做**

我写了一个扫描器：顶层类型若在**其它文件**零引用，就列为候选。结果 **66 个**，
而逐个看下去绝大多数是**同文件内使用的私有视图/修饰符**（`DialPressStyle`、`BusyRow`、`ToastTone` …），
它们完全正常。

要把它变成能用的闸门，需要解析访问级别 + 同文件引用计数 + SwiftUI 预览宿主等特例 ——
误报会远多于真阳性。**一个经常误报的 warn-only 闸门，比没有更糟**（会训练人忽略它）。
所以我放弃这条，只在报告里记录方法。

## 3. 方法论

**「能自动检查」不等于「值得自动检查」。** 前面几轮我一直在给自己加判据，
这一轮要反过来：判据的维护成本（误报、特例、解释负担）必须低于它挡住的损失。

死代码检测的正确答案是**类型检查器 + 死代码分析**（编译器已有），不是自制的正则扫描。
这三处能被我抓出来，靠的是"读注释 → 搜引用"的人工路径，而不是扫描器。
