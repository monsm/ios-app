# AUDIT-ROUND-229 · 第 229 轮：**我上一轮引入的回退** —— 清理放错层，回收站还原会丢状态

> CI：`651da0f` 全绿；`51233b1` / `3b231a8` 排队中。

## 1. 我错在哪

Round 227/228 我把「派生状态清理」放进了 `DB.delPwd` / `delFp`，理由是"它们是全仓删除的唯一落点"。

**这个理由是错的。** 查调用者：

| 调用者 | 语义 |
|---|---|
| `CredentialOrg.cascadeBinMember` | 删成员 → 凭证**移入回收站** |
| `CredentialOrgBatch.batchDisable` | 批量停用 → **移入回收站** |

**两个都是「移入回收站」，没有一个是永久删除。** 而回收站支持**整组还原**（`CredBinStore.restore`）。

所以我的改动会让：

| 操作 | 结果 |
|---|---|
| 批量停用一条带星标的凭证 | 星标被清 |
| 从回收站还原 | 台账行回来了，**星标/停用位/提前量/排序位置全没了** |

## 2. 正确层次

| 层 | 函数 | 该不该清派生状态 |
|---|---|---|
| 移入回收站 | `DB.delPwd` / `delFp` | ❌ **不该**（要能还原） |
| **彻底删除** | `CredBinStore.purge` / `clear` | ✅ **该清** |

修法：

```swift
// CredentialOrg
static func purgeDerivedState(mac: String, pwdAlias: Int?, fpBatch: Int?) { … }

// CredBinStore.purge / clear 各调一次（它们才知道 alias / batch）
```

`delPwd` / `delFp` 里的清理已撤回，并留注记说明**为什么不能在这里清**。

## 3. 方法论

**「唯一落点」这个说法只能用来确认"覆盖了所有路径"，不能用来确认"这个动作的语义"。**

| 判断 | 问题 |
|---|---|
| "这是唯一落点，所以放这里" | ❌ 落点唯一 ≠ 语义正确 |
| "这一步是删除还是移入回收站？" | ✅ 先定语义，再找落点 |

判据：**在"唯一落点"上做清理之前，先列出所有调用者各自的**业务语义**（而不是函数名）。**
我这次就是被 `delPwd` 这个名字骗了 —— 它实际做的是"移入回收站"，不是"删除"。

## 4. 顺带

Round 227/228 的结论（星标/排序/停用位/提前量必须随"彻底删除"清）**仍然成立**，
只是执行层从 `delPwd` 挪到了 `purge`。文档 `AUDIT-ROUND-227` / `-228` 的"修法"段落地位置以此轮为准。
