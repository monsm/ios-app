## 1. 试了两个角度，都没发现

**（a）`Calendar` 的使用是否绕过 `TimeFormat`**

```
grep "Calendar.current|Calendar(identifier:"  →  13 处
```

逐个核对：

| 位置 | 结论 |
|---|---|
| `WeekCal:25`（唯一一处 `Calendar.current`） | ✅ 注释写明"全仓唯一一处，取完立刻钉成公历" |
| `DateFormats` 4 处 `f.calendar = ...` | ✅ ROUND-126 刚修的 |
| `TimeFormat:24` / `ZKProtocol:28` | ✅ 都钉公历 |
| `ZKProtocol:29` 的 `cal.timeZone = TimeZone.current` | ✅ **正确** —— 协议秒必须用本地墙钟（注释 22-24 行写明理由） |
| `BackupStudioScreen:378` | ✅ ROUND-126 修的 |

**（b）`dropFirst`/`suffix(from:)` 的越界风险**

```
grep "suffix(from:|dropFirst([a-z]"  →  7 处
```

Swift 的 `dropFirst(n)` 在 `n > count` 时**返回空**（不越界），所以 7 处全安全；
`BackupStudioScreen:369` 还额外用了 `max(keepCount, 1)` 防 0。

## 2. 但有一个可沉淀的发现

这轮我用的搜索入口是**判据里的字面量**（`"2118"`、`365 * 86400`），
而上轮正是靠它抓到「永久有效判据被抄三份」。

**这个入口比"搜函数名"有效得多**，值得写进方法论。已在 `AUDIT-METHOD.md §1.1` 补一节：

| 搜什么 | 能找到 | 例 |
|---|---|---|
| **判据里的字面量** | 所有自己写了一遍判据的地方 | 搜 `"2118"` → 3 处绕过 `expiryDate`（ROUND-145） |
| **模式** | 同模式的实现（名字可能不同） | 搜 `Locked(` → 3 个诊断缓存（ROUND-143） |
| 符号名 | 同名实现（命中率最低） | 搜 `keepingAwake` → 3 处（ROUND-81） |

**为什么字面量比函数名有效**：判据的**内部实现**比它的**名字**更容易被抄 ——
抄的人往往是在写一段新逻辑、顺手把判据复制过来，而不是在调用一个已知函数。

## 3. 方法论

**"没发现缺陷"的轮次，产出应当是"方法"而不是"改动"。**

本轮如果硬找一个改动，最可能的结果是引入回归（本段已发生 5 次）。
而把"哪种搜索入口更有效"记下来，**下一轮就能少走一次弯路**。

这也是 `AUDIT-METHOD.md` 存在的意义：它记录的不是"我修了什么"，而是"**怎么找**"。
