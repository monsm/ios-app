# AUDIT-ROUND-323 · 第 323 轮：一条**没写下来的**契约，三个调用点依赖它

> CI：`d013a873` build 全绿（errors=0）。

## 1. 扫描：跨数组下标

规则：`for (i, x) in A.enumerated()` 之后用 `B[i]` 索引**另一个**数组 —— 两数组长度不一致就是数组越界。

| 结果 | 数量 |
|---|---|
| 原始命中 | 6 |
| 去重后的真实站点 | **3** |
| 会崩的 | **0** |

## 2. 三处都安全，但靠的是一条**没人写下来**的契约

| 站点 | 依赖的契约 |
|---|---|
| `StatsKit.lastWeekDigest` | `cls[i]` ↔ `week[i]` |
| `MemberHub` 两处 | `rows[i]` ↔ `logs[i]` |

它们成立的原因只有一个：`Attribution.classify` 内部是 `logs.map { … }` —— **与输入一一对应、保序**。
而这条契约此前**没有任何注释写过**。

## 3. 破坏它的方式看起来完全无害

    // 将来某人想让 classify 只返回「可归属」的行：
    return logs.filter { … }.map { … }   // ← 一行改动

⇒ 三个调用点立刻全部**数组越界或数据错位**，而且错位比崩溃更难查（显示的是别人的记录）。

## 4. 修法

| 改动 | 内容 |
|---|---|
| `Attribution.classify` | 加契约注释：**返回与 `logs` 一一对应、顺序相同**；要过滤请在调用方先过滤 |
| `StatsKit:81` | 补 `guard i < week.count else { continue }`（`RecordSearchBuild:48` 早就有同款，这边没有） |

## 5. 方法论

**「返回数组与输入一一对应」是隐式契约里最危险的一种 —— 破坏它的改动只有一行，而且看起来像优化。**

| 契约类型 | 破坏后表现 |
|---|---|
| 「返回非空」 | 崩溃，好查 |
| **「与输入一一对应」** | **数组越界（好查）或数据错位（难查）** |

判据：**凡是「A.map 的结果被按下标与 B 对齐」的代码，都要在 A 的文档里写死这条契约；否则下一个人加 filter 时不会知道自己破坏了什么。**
