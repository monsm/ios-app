# AUDIT-ROUND-252 · 第 252 轮：**开锁失败的真实原因，从来没显示过**

> CI：`bf9a0b6` build 全绿；`5a7fb1d` / `8beeb83` / `e8bccb8` 排队中。

## 1. 缺陷

`runUnlockChain` 失败时把原因写进 `app.lastError`：

    lastError = msg      // msg = StatusParser.rcFriendly(rc)，例如「无效的PIN码」+ 该怎么办

而门页的失败链**从头到尾没有读过 `lastError`**：

| 失败时用户看到的 | 实际有的信息 |
|---|---|
| 「再试一次，别着急」 | 真实 rc 与原因（在 `lastError` 里） |
| 一份静态自查清单（蓝牙/距离/电量） | 同上 |
| 「再试一次」按钮 | 同上 |

**结果是：用户点了圆盘、失败了，却不知道发生了什么。**
本会话最初那条「手动开锁总是失败」正是卡在这里 —— 连 rc 是多少都看不到，只能靠我自己加交互流水去捞。

## 2. 附带发现：`DialPhase.failed(String)` 的关联值是死的

    enum DialPhase { … case failed(String) … }

| 消费点 | 是否读那个 String |
|---|---|
| `progress` | ❌ 固定 0.72 |
| `word` | ❌ 固定「失败」 |
| `isFailed` | ❌ 只看是不是 failed |

**这个关联值全仓零读取。** 中心读数是**定宽词**（"换态只换词不换位置"），所以不该把长文案塞进 `word`；
正确做法是让失败链去读 `lastError`（本轮就是这么修的）。

## 3. 修法

`failureChain` 开头插入一张卡片：`app.dialPhase.isFailed` 且 `lastError` 非空时显示该文案。
只在**本次确实失败**时显示，避免把别处操作留下的旧错误挂到门页。

## 4. 为什么这条比前面几条都重要

Round 251 我刚给 `rc=2` / `rc=26` 补了「该怎么办」的 hint —— 但如果门页根本不显示 `lastError`，
**那些 hint 永远不会出现在用户眼前**。

| 层 | 状态 |
|---|---|
| 生成正确文案（`rcHint`） | ✅ Round 251 |
| **送达用户（门页失败链）** | ✅ **本轮** |

## 5. 方法论

**「写了错误文案」不等于「用户看得到」—— 必须验证**送达路径**。**

| 检查 | 本轮答案 |
|---|---|
| `lastError` 有被赋值吗 | ✅ 有 |
| `lastError` 有被读取吗 | ❌ **门页没有** |

判据：**给任何错误/提示补文案后，立刻 grep 那个承载变量的**读取点**，确认它在对应场景真的被渲染。**
（这与 Round 240 的「grep 底层字段找绕过者」是同一条纪律的另一面：一个是找绕过者，一个是找断点。）
