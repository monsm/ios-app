# AUDIT-ROUND-249 · 第 249 轮：`rc=5` 与 `rc=26` 是同一类永久失败，却只处理了一处

> CI：**`84f9d79` build 全绿**（钥匙串哨兵修复编译通过）。

## 1. 缺陷

自动开锁的 rc 分支里，两个**永久性**失败处理不一致：

| rc | 含义 | 原来的处置 |
|---|---|---|
| 26 | 防拆事件 | `armed = false` + 暂停 24h + 审计 |
| **5** | **次数用完（钥匙废了）** | **只写一条审计，不解武装** |

而 `rc=26` 那段的注释已经把这个形态说清楚了：

> 防拆事件 ⇒ 连「武装」一起解掉：否则后续每次靠近都会走到闸门被拒、刷一条审计。

`rc=5` 完全同理 —— 钥匙次数用完是**不可恢复**的（除非换钥），可它没解武装。于是：

| 现象 | 原因 |
|---|---|
| 用户每次走到门口，App 都尝试一次、失败一次 | `armed` 仍为 true |
| 审计里堆满 `rc=5` | 每次失败写一条 |

## 2. 修法

`case 5` 补 `armed = false`，审计文案改成如实说明「已关闭自动开锁，请换钥后再开启」。
（用户换钥 / 重新配网会重新武装 —— 与 rc=26 的语义一致。）

## 3. 方法论

**同一段 switch 里，两个分支如果「失败性质相同」，它们的收尾必须一致 —— 差别只能来自"能不能自愈"。**

| rc | 能否自愈 | 该不该解武装 |
|---|---|---|
| 3（锁钟漂） | ✅ 校时后重试 | 不解（已实现重试） |
| 25（锁忙） | ✅ 下次再说 | 不解 |
| **5（次数用完）** | ❌ | **解** |
| 26（防拆） | ❌ | 解 + 24h 暂停 |

判据：**给一个 switch 的每个 case 标注「可自愈 / 不可自愈」，不可自愈的必须停止重试。**
否则就是「每次靠近都失败一次」的静默消耗 —— 用户只看到"自动开锁时灵时不灵"。
