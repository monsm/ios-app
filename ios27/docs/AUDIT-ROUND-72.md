# AUDIT-ROUND-72 · 第七十二轮：一个封闭的死引用链（三个函数互相调用，对外零调用）

> CI：`d62c9c8` 已验证；`2cf4700` / `6801fa3` 待回执。本轮本地提交。

## 1. 发现方式：不是搜死代码，是**追调用点**

上一轮修 `ownerName` 时用的动作是"把会返回空串/可选的辅助函数，列出它的调用点清单"。
这轮继续用：`grep aliasName(` → 只有声明本身。再看它旁边几个同类显示辅助：

```
grep doubleLine(  → MemberHub:175（声明）+ 它自己内部一句
grep display(     → MemberHub:160（声明）+ doubleLine 里两次 + 一句注释里的提及
grep unnamedLabel → MemberHub:169（声明）+ display 里一次 + 一句注释里的提及
```

三者构成**封闭引用链**：`doubleLine` → `display` → `unnamedLabel`，而**簇外零调用**。

## 2. 为什么它们没被更早发现

因为它们**互相调用**。任何"零引用"扫描（只看单个符号被引用几次）都会看到"有人用"，
而那个"有人用"就在同一个死簇里。

这类结构比单个死函数危险：它看起来像一套完整的小工具集（名字兜底 + 截断 + 双层文本），
README 里也提过"成员名兜底"，但它对界面**完全没有影响** ——
真正生效的是 UI 层 `MemberCard` 那一套。

## 3. 处置

删掉 `display(_:)` / `unnamedLabel(_:)` / `doubleLine(_:)` 三件，并保留一段说明：
写明"这两条规则实际生效的是 UI 层实现"，避免下一个人以为删错了。
同步更正 `StoreModels.swift` 里那句"MemberHub.display 本来就有 unnamedLabel 兜底"。

## 4. 方法论

**死代码检测要看"可达性"，不是"引用数"。**

单个符号的引用计数无法区分这两种情况：

| 形态 | 引用数 | 实际 |
|---|---|---|
| 活代码 | >0 | 被外部可达路径调用 |
| **封闭死簇** | **>0** | **只被簇内互相调用** |

正确的做法是从"外部入口"反向做可达性分析（编译器就是这么做的）。手工近似：
**把一个符号的所有引用点也检查一遍"它们自己是否可达"** —— 递归到出现外部引用为止。

本轮的三个恰好只有两层，手工追完即可。更深的情况应该交给编译器（`-warn-unused` 之类）。
