# AUDIT-ROUND-35 · 第三十五轮：三个「开关」里只有一个是真的

> CI：`2190e00` 已验证（errors=0、build_ok=1）；`aeca8e4` 与两个文档提交待回执

## 1. 上轮列出的三个疑似，这轮全部查清

| 项 | 结论 | 处置 |
|---|---|---|
| `CredentialOrg.quota()` / `kf_ccred_quota` | 函数**零调用**，键**无人写** | 删除，留一段说明 |
| `DiagFlags.silent` / `kf_silent_trouble` | 全仓**零引用**；注释声称的 6 处消费点（`LinkSense.swift`）里出现次数是 **0** | 删除，留一段说明 |
| `debugRaw` / `kf_debug_raw` | 3 处真消费（产生 `TX hex=` 日志），但**无 UI 写入方** | **保留**（是引擎既有能力），把"当前无 UI 入口"写进注释 |

## 2. 最值得记的是第二个

`DiagFlags.silent` 的注释写着：

> 打开后暂停**自动连接 / 预热刷新 / 到场补发 / 自动重连 / 会话巡检 / 冷启动扫描**
> 这 6 处自动动作（消费点全在 `LinkSenseKit :75/:122/:150/:237/:309/:417` —— **第九十一批逐条对过行号**）

而实测：`LinkSense.swift` 里 `kf_silent_trouble` 与 `DiagFlags` 的出现次数 **都是 0**；
`DiagFlags` 全仓零引用。文件也不叫 `LinkSenseKit.swift`（是 `LinkSense.swift`）。

**这比没有这个开关更糟。** 出问题时按注释去"打开静默模式复现"，什么都不会发生，
而且人会以为复现环境已经干净了 —— 排查方向直接被带偏。
那句"逐条对过行号"尤其危险：它给了一个**假的可靠性信号**。

## 3. 第三个为什么不删

`debugRaw` 是真的被消费的（`HardwareService:203/215`、`LockServiceLink:246/258`），
只是没有 UI 写它。删掉会连带让诊断页的 `recentFrames`（原始帧环形缓冲）彻底失去生产者。
正确处置是**写明现状**，让人知道"原始帧列表恒为空"不是链路问题，而是开关没开。

## 4. 方法论

**注释里的"已核对"是最容易腐烂的断言。** 代码改一次、文件改个名，注释里的行号就全错，
而读者无法分辨"真的核对过"和"写过就算" —— 两者长得一模一样。

可复用判据：**凡是注释里出现具体行号 / 具体文件名的"已逐条核对"，都要能被一条静态检查复核**；
复核不了，就别写行号，改写成"在 X 机制里"这种不会过期的描述。

本轮删掉的两处，都是"注释比代码更用力"的典型 —— 代码什么都没做，注释却把话说满了。
