# AUDIT-ROUND-313 · 第 313 轮：伪装模式会**先闪一下真数据**

> CI：`a8b24bea` build 全绿（errors=0）。

## 1. 时序

用户输胁迫码 → 进入空壳模式，这条链被拆成了两步，中间隔着一个异步窗口：

| 时刻 | 发生了什么 |
|---|---|
| T0 | 门禁只置 `app.decoyMode = true`、`app.unlocked = true` |
| T0+ | `Shell()` 重建 → 首页 `.task` 异步跑 `app.reload()` |
| T1 | `reload()` 里才 `DB.setDecoy(true)` 并清空 `keys` / `members` / `entries` |

**T0 → T1 之间**：`app.keys / members / entries` 仍是**真实数据**（上锁时并没有清它们），
而 `DB.isDecoy` 仍是 false ⇒ 手机钥匙 / 回收站 / 版本历史这些 `DB.isDecoy` 守卫也照常返回真数据。

被胁迫者看到的正是这一屏 —— 恰好是空壳模式最不能发生的暴露。

## 2. 修法：进入那一刻就生效

在门禁的 `.decoy` 分支里立即：

    DB.setDecoy(true)      // 数据层守卫立刻返回空集
    app.keys = []          // 三张内存投影立刻清空
    app.members = []
    app.entries = []

三步都**幂等**：`setDecoy(true)` 再设一次无害；三张表在随后的 `reload()` 里还会被再清一次。

## 3. 为什么这类窗口值得专门修

| 普通 UI 缺陷 | 本轮的窗口 |
|---|---|
| 闪一下旧数据 | **闪一下真实凭证/成员/开门记录** |
| 用户会重试 | **被胁迫者已经看到了**，无法撤回 |

## 4. 方法论

**安全状态必须在「进入的那一刻」生效，不能依赖后续的异步刷新。**

| 判据 | 结论 |
|---|---|
| 「最终会一致吗」 | 会（reload 会清）✅ |
| **「进入后的第一帧是什么」** | **真实数据** ❌ |

判据：**凡是「切换安全状态」（进/出空壳、上/解锁、开/关只读）的代码，都要问「第一帧是什么」—— 不能等到下一次刷新才正确。**
