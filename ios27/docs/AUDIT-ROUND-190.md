# AUDIT-ROUND-190 · 第 190 轮：把「文案承诺 ↔ 代码判据」固化成闸门

> CI：**`c79c84c`（密码闸宽限）已验证绿**；`ea66e90`（文档）待回执。

## 1. 为什么做这个

ROUND-188 抓到的 bug：密码闸说明写「输对一次后 30 秒内不再重复询问」，
而 `needsGate` 只判 `lastUnlockSuccessAt` —— **承诺与判据各写各的，谁也不知道对方改了**。

这类缺陷的特征：

| 特征 | 说明 |
|---|---|
| 单次使用看不出 | 开门→弹密码→输对→开门，一路正常 |
| 只有**连续操作**才暴露 | 连开两次才发现"怎么又要密码" |
| **改动双方都不知道对方存在** | 改文案的人不会去读 `needsGate` |

ROUND-189 我把 16 条数字承诺逐条核对了一遍 —— 但那是一次性的，下次照样会漂。

## 2. 做法：加进 `workflow.js`（**不新增闸门数**）

`workflow.js` 本来就在做「跨文件一致性」对账（闸门数、工作流结构），
承诺核对与它同性质，所以加进去 —— **不需要改 6 个文件里的「22 道」**。

```js
const PAIRS = [
  { copy: '…/TailgateScreen.swift', text: '2–6 秒',
    code: '…/TailgateScreen.swift', anchor: 'ForEach(2 ... 6' },
  …
];
```

判据很窄：**两边都还在**。

| 情况 | 结果 |
|---|---|
| 文案被改 / 被删 | **判红**，提示"承诺或判据被改过，请重新核对这一对" |
| 代码锚点被改 / 被删 | 同上 |
| 两边都没动 | 绿 |

**它不判断对错**（那需要人读代码），只负责"别让任一侧悄悄改了"。

## 3. 首批 5 对

| 文案 | 代码锚点 |
|---|---|
| `TailgateScreen`「2–6 秒」 | `ForEach(2 ... 6` |
| `LinkSense`「5 / 15 / 30 / 60 / 90」 | `[5, 15, 30, 60, 90]` |
| `DeviceInfoScreen`「偏差超过 2 秒」 | `abs(drift) > 2` |
| `AboutScreen`「连点 10 次」 | `versionTaps >= 10` |
| `UnlockGateScreen`「30 秒内不再重复询问」 | `DoorScreen` 的 `app.gatePassedAt` |

最后一条正是 ROUND-188 那个 bug 的"已修好"状态 —— 以后谁把 `gatePassedAt` 删了，闸门会立刻红。

## 4. 双向验证

把 `versionTaps >= 10` 临时改成 `>= 11`：

```
workflow: FAIL — 1 处
  App/Features/Settings/AboutScreen.swift 里找不到「versionTaps >= 10」
  —— 承诺或判据被改过，请重新核对这一对
```

恢复后 `allgates` 22/22 全绿。

## 5. 方法论

**"一次性核对"会过期；"机制"不会。**

| 做法 | 效果 |
|---|---|
| 人工把 16 条核对一遍（ROUND-189） | 今天对；下次改文案就漂 |
| **把"两边都在"写成闸门**（本轮） | **任一侧改动都会立刻红** |

闸门不必理解语义 —— 它只要能在**人忘记的时候**把人叫回来。
这类"锚点对账"闸门的好处是**假红率为 0**（子串存在性检查），所以能长期开着。
