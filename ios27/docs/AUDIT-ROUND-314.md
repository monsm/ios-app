# AUDIT-ROUND-314 · 第 314 轮：空壳模式下**门开不了** —— 与设计正相反

> CI：`79a4d49f` build 全绿（errors=0）。

## 1. 设计写的是什么

`AppLock.swift` 头注（第 9-15 行）：

> ② 胁迫码 → `decoyMode = true`，进空壳模式（**门能开**、数据看不见），不报警不阻止
> 隐藏的是数据（凭证台账、成员、备份），**不是开锁能力 —— 门照样能开，这是保命的前提**。

## 2. 代码实际做了什么

`StoreKeychain.keychain(_:)` 里有一句：

    if isDecoy { return nil }

连锁后果：

| 环节 | 结果 |
|---|---|
| `AppModel.currentKeychain` → `DB.keychain(mac)` | **nil** |
| `app.lock` | **nil** ⇒ 门页显示「还没有添加门锁」 |
| `LockServiceOps.unlock` 取 `kc.skey` | **拿不到** ⇒ 抛「无钥匙串，无法开锁」 |

**⇒ 被胁迫者输完胁迫码，进到一个「没有锁」的 App，门打不开。**

## 3. 为什么这条特别严重

| 后果 | 说明 |
|---|---|
| 伪装当场穿帮 | 「你说你能开门，结果 App 里连锁都没有」 |
| **物理上被关在门外** | 这正是「保命的前提」所指的场景 |
| 与设计直接矛盾 | 不是模糊地带，是头注写死的语义 |

## 4. 修法：单把放行，列表仍隐藏

去掉 `keychain(_:)` 的 decoy 守卫；`keychains()`（锁清单）**保持** `if isDecoy { return [] }`。

| 入口 | 空壳下 | 理由 |
|---|---|---|
| `keychain(mac)`（单把） | ✅ 返回 | 开锁要 `skey`；这是「门照样能开」的唯一实现路径 |
| `keychains()`（列表） | ❌ 空 | 暴露锁名/锁数量 |
| `ledger` / `members` / `entries` / `mobileKeys` / 回收站 / 版本历史 | ❌ 空 | 各自治守 |

## 5. 方法论

**「安全过滤」最怕的是一刀切：把「敏感数据」和「完成核心功能所必需的凭据」一起藏掉。**

| 过滤对象 | 该不该藏 |
|---|---|
| 台账 / 成员 / 记录 / 备份 | ✅ 藏（这就是要保护的数据） |
| **开锁所需的 `skey`** | **❌ 不能藏（藏了功能就没了，而且伪装会穿帮）** |

判据：**给「空壳/降级模式」加过滤时，逐项问「藏掉它之后，这个模式还能不能完成它的核心动作」—— 不能，就是过滤加错了地方。**
