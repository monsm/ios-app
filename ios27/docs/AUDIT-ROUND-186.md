# AUDIT-ROUND-186 · 第 186 轮：交互流水「够用来排查」（含用户要求的原始载荷选项）

> 用户两点反馈：
> ① "你脱敏了还能查出来吗" —— 有道理，原来的脱敏只剩一个字节数，看不出帧结构；
> ② "先不要担心泄露，我们是本机调试" —— 他的设备、他的风险，给他原始载荷。

## 1. 脱敏升级：从「一个字节数」到**KLV 结构骨架**

```
旧：87003c04000000…(51 bytes 已脱敏)
新：87003c04000000 KLV[01:16 02:32] (51 bytes 已脱敏)
```

新增的 `KLV[字段号:长度 …]` 让**帧结构**可读：

| 能看出来 | 说明 |
|---|---|
| 缺字段 | 例如只有 `01:16` 没有 `02:32` —— cmd04 少了 ekey 段 |
| 长度错 | `02:16` 而 ekey 应是 32 字节 |
| 帧被截断 | 骨架以 `…` 结尾 |

**值一个字节都不留** —— 所以这份默认流水可以直接贴出来。

## 2. 新增「包含原始载荷」开关（默认关）

`LockService` 新增 **仅内存**的 `rawTrace`（300 行，进程退出即失），逐行存「时间 + 级别 + 原文」。

「交互流水」页新增开关「包含原始载荷（含密钥，勿外传）」：

| 开关 | 复制内容 | 来源 |
|---|---|---|
| 关（默认） | 脱敏流水 | `DiagLogs`（**持久**、按天保留） |
| 开 | **原始帧** | `LockService.rawTrace`（**仅内存**） |

红线没破：**落盘与导出的永远只有脱敏那份**（`DiagLogs` / `logs` / 导出中心 / 备份）。
原始载荷只可能从"用户当场点复制"这一条路出去。

## 3. 顺带补上一个"定义了从没被调用过"的 API

`BleTelemetry.recordAttempt`（连接尝试，300 条环形表）**零调用** —— 从来没被写过，
读端 `BleTelemetry.attempts` 也没人用。而"BLE 连不上 / 超时"正是开锁失败的头号原因。

现在接在 `LockService.ensureConnected`（所有锁操作的唯一漏斗）上：成功记 ok、失败记 reason。
（本来就连着的不记，否则每条命令都会刷一条。）

## 4. 方法论

**「脱敏」要脱得够用，不是脱得干净。**

| 脱敏策略 | 结果 |
|---|---|
| 整段替换成 `N bytes` | 安全，但**没法排查** —— 用户拿到的是一份没信息量的文件 |
| **保留结构（字段号 + 长度），遮掉值** | **安全且可诊断** |

这条对任何"要把现场发给别人"的功能都成立：**先问「对方需要看到什么才能判断」**，
再决定遮什么 —— 而不是先遮掉一切。

另一条：用户明确接受风险时（本机调试），**给开关、不给默认**。默认安全，选择权交给他。
