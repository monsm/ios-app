# AUDIT-ROUND-320 · 第 320 轮：台账读不出来时，用户永远不会知道

> CI：`3baa98a8` build 全绿（errors=0）。

## 1. 第三种「静默拒绝」

前两轮修的是「模式开关没拦全」；这一轮的形态不同 —— **守卫存在、也生效，但没人告诉用户**。

| 环节 | 行为 |
|---|---|
| `DB.ledger(mac)` 解码失败 | `markLedgerCorrupt(mac)`（内存 Set） |
| `saveLedger` | `guard !isLedgerCorrupt(mac) else { 记遥测; return }` —— **拒写** |
| 调用方（`addPassword` 等） | 拿到 `Void` ⇒ **报「已保存」** |
| 全仓 UI | **零处显示这个状态** |

结果：用户改了凭证、看到「已保存」、重启后改动消失。而且因为台账一直解不出，**再改一百次也一样**。

`StoreModels:81` 的注释其实已经承认了这一点：「触发 markLedgerCorrupt → 整个会话里所有凭证写入**被静默拒绝**」。
——它被记录下来了，但从未被解决。

## 2. 修法：把状态投影到界面上

| 改动 | 内容 |
|---|---|
| `AppModel` | 新增 `ledgerCorrupt`，在 `reloadKeys` 里 `DB.isLedgerCorrupt(m)` 投影 |
| `KeysScreen` | 顶部挂一张卡：「本机凭证台账读不出来 / 当前会话里对凭证的改动**不会保存** / 请先到备份工作室恢复」 |

文案刻意**不写「损坏」**这种断言（可能只是版本不兼容），只写清**后果**（改动不会保存）与**出路**（从备份恢复）。

## 3. 为什么「静默拒绝」特别难发现

| 检查方式 | 结果 |
|---|---|
| 查守卫是否存在 | ✅ 存在（`guard !isLedgerCorrupt`） |
| 查守卫是否生效 | ✅ 生效（写入真的被拒） |
| **查用户是否知道** | ❌ **不知道** ← 前两步都过也漏这个 |

## 4. 方法论

**一个「拒绝」要完整，必须同时满足三件事：拦住、让调用方知道、让**用户**知道。**

| 层次 | 缺了会怎样 |
|---|---|
| 拦住 | 数据被写坏 |
| 让调用方知道 | 假成功（Round 317 的空壳新增） |
| **让用户知道** | **假成功 + 用户不知道为什么、也不知道怎么办**（本轮） |

判据：**凡是「静默 return 的守卫」，都要问两层：调用方会不会报成功？用户会不会看到原因？两层都答「会」，这个拒绝才算做完。**
