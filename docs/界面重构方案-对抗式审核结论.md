## 一、子代理 D 的四条核心质询 —— 全部成立

### 质询 1：§4 说「P2 协议测试已完成」不成立

**子代理 D**：`SettingsView.swift:1088` 的 NavigationLink 仍在 `if eggShown`（需连点版本号 10 次）内，实际仍是彩蛋。

**Lead 复核**：✅ **成立**。

```
1082:  if eggShown {
1083:      LabeledRow("构建", ...)
1084:      LabeledRow("遥测", ...)
1088:      NavigationLink("协议测试（回声探测 / 附近设备）") { ProtocolTestView() }
1089:  }
```

`eggShown` 的定义（`:31`）与触发（`:1065-1066`，`versionTaps >= 10`）确认需要连点 10 次。

**而方案第三节又写「协议测试 → 设置-关于（直接可见）」** —— 与代码矛盾。**这是我的错**：上轮加这个入口时故意放在彩蛋里（注释写「不占正常用户版面」），方案却说要提到可见，两者从未一致。

### 质询 2：「锁能力 3 层 → 2 层」是反向的

**子代理 D**：现状是「设置 Tab 根屏 → 布防页」（同屏 Section 不算一层，**2 个屏幕**）；方案变成「设备页 → 新建锁详情 → 布防页」（**3 个屏幕**）。

**Lead 复核**：✅ **完全成立**。这是本方案最核心的论证错误。

| | 现状 | 方案 |
|---|---|---|
| 屏幕 1 | 设置 Tab（锁段是一个 Section，**同屏**） | 设备 Tab |
| 屏幕 2 | 点「布防」→ `DefendView` | 点 Hero 卡 → `LockDetailView` |
| 屏幕 3 | — | 点「布防」→ `DefendView` |
| **总屏幕数** | **2** | **3** |

**我把「Section 折叠」误算成了「一层导航」。** HIG 讲层级看的是**导航栈深度/屏幕数**，不是 Section 分组。方案不但没减少层级，**反而多了一层**。

### 质询 3：§4 承认真实价值只剩「锁档案 2 处合并」

**子代理 D**：而这两个入口就是 `SettingsView.swift:305` + `Sheets.swift:482`，后者是 `DeviceInfoView` 的自链接，**删一行即可**。

**Lead 复核**：✅ **成立**。

```
SettingsView.swift:305   NavigationLink("锁档案 (昵称/符号/色标/备注)") { LockProfileView() }
Sheets.swift:482         NavigationLink { LockProfileView() } label: { ... }   ← DeviceInfoView 内部
```

删掉 `Sheets.swift:481-484` 那一段就收敛了。

**而且要问一句**：`DeviceInfoView` 是「锁信息名片」（只读汇总），里面给一个「编辑档案」的入口**是合理设计**，不是重复。删掉反而让用户看到名片想改档案时没路走。**所以这条"收益"本来就不该算。**

### 质询 4：10,573 行 / 6 文件 + 约 16 个新文件 vs 15 行布防入口

**子代理 D**：建议按最小方案退回。

**Lead 复核**：✅ **成立，且实际情况比它说的更极端**。

**方案的成本**：
- 拆 6 个巨型文件：`CredentialStudio` 2425 + `RecordsView` 2204 + `CredentialsView` 1774 + `Sheets` 1467 + `DeviceHomeView` 1403 + `SettingsView` 1304 = **10,577 行**
- 新建：`LockDetailView` + `SettingsSections/*`（约 6 个）+ `PwdStudio`/`TempCodeStudio`/`FpStudio`/`CredentialDetailViews`/`CredentialStudioShared`（5 个）+ `AddDeviceView`/`GatewayView`/`MembersView`（3 个）+ `RecordsSheets` + `SyncTimeView` + `UnlockGateView` ≈ **16 个新文件**

**最小方案的成本**——**2 行**：

```swift
// App/Core/QuickPool.swift

// ① all 数组加一条（第 37 行 backup 之后）
QuickAction(id: "defend", icon: "shield.lefthalf.filled", label: "布防"),

// ② quickDestination 加一个 case（第 142 行 backup 之后）
```

**用户操作**：设置 → 外观 → 快捷格 → 勾选「布防」→ 设备页出现一格「布防」。

**如果还要更直接**（不用用户去勾选），在设备页 Hero 卡下方加一个条件按钮：

```swift
// App/UI/DeviceHomeView.swift，heroCard 之后
if PidMap.canDefend(app.current?.pid ?? 0) {
    NavigationLink("布防") { DefendView() }
}
```

**约 5 行。**

## 二、方案的真实价值重估

| 原宣称收益 | 复核结论 |
|---|---|
| 锁能力 3 层 → 2 层 | ❌ **反向**：2 屏 → 3 屏 |
| 「锁」功能 3 处 → 1 处 | ❌ 不成立：设置页锁段是「锁」的正确位置（HIG `settings.md`：**task-specific options 应在任务里** —— 但「布防」是**这把锁的策略**，不是"当前任务"，放锁详情也说得通；问题不在位置，在**用户找不到**） |
| 同一对象多入口收敛 | ❌ 只有锁档案 2 处，且那是设计不是重复 |
| 设置页瘦身 17→5 | ❌ 五组筛选 2026-10-14 已上线 |
| 协议测试可见化 | ❌ 仍是彩蛋，且方案说要改但没改 |
| 单文件 ≤600 行 | ⚠️ **唯一的真收益，但是开发者收益，用户无感** |

**结论：方案对用户的价值 ≈ 0。唯一的真收益（拆文件）是工程整洁度，与"用户找不到布防"无关。**

## 三、最小方案（建议采纳）

### 方案 M1：快捷格加「布防」（2 行）

| 改动 | 文件 | 行数 |
|---|---|---|
| `all` 加一条 `QuickAction(id: "defend", ...)` | `QuickPool.swift:37` 后 | 1 |
| `quickDestination` 加 `case "defend": DefendView()` | `QuickPool.swift:142` 后 | 1 |

**优点**：复用现有快捷格机制（用户已能编辑）；不改变默认界面（`defaultIds` 不含 `defend`）。
**缺点**：用户要自己去「设置-外观-快捷格」勾选才看得到。

### 方案 M2：设备页直接加条件按钮（约 5 行）—— **推荐**

```swift
// DeviceHomeView.swift，heroCard 之后
// 2026-10-29：布防入口 —— 原来只在「设置→锁段」，用户找不到（本次审核的起点）。
// 只在锁支持布防时出现（canDefend），与设置页那条并存（不删，避免打断老用户习惯）。
if PidMap.canDefend(app.current?.pid ?? 0) {
    NavigationLink {
        DefendView()
    } label: {
        Label("布防", systemImage: "shield.lefthalf.filled")
    }
    .buttonStyle(.bordered)
}
```

**优点**：设备页直接可见（1 屏），不用勾选，不用新建页面。
**缺点**：设备页多一个按钮。

### 方案 M3：M1 + M2 都做（约 7 行）

快捷格可配 + 设备页常驻，双保险。
