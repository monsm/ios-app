# TOKENS — 令牌层实测记账

> 单一事实来源：`App/Core/Theme.swift`。本文是它的**机器生成**镜像，不是手抄的第二份。
> 生成方式：从 Theme.swift 解析 `XPalette` 的明暗两臂 → 按 WCAG 2.1 相对亮度公式算 → 出表。
> 断言侧见 `tools/contrast.js`（110 条，判失败）；本文的数字与它同源。

**这一页的用途**：改一个色值之前先看它压在哪些底上；改完之后跑 `node tools/contrast.js --verbose` 对一遍。

## 0. 两句话前提

1. **深色档 = 设计范式本身**（Black Canvas / Glass Instrument）。它才是这个 App 的样子。
2. **浅色档不是「支持浅色主题」**，而是既有 `kf_theme` 真开关的等价映射。两档过同一条断言。

为什么不能直接砍掉浅色档，见 `DEVIATIONS.md` §1 —— 那不是审美取舍，是「别把真开关变成假开关」。

### 2.1 这张表抓到过什么（以及它自己怎么错过一次）

**第一次扩表（把语义色断言从 2 个底扩到 4 个底）当场红了三条：**

| 缺陷 | 原值 | 在哪 | 实测 | 修成 |
|---|---|---|---|---|
| 浅色 warn | `#A94E08` | `surfaceSunken`（表单错误行压在输入框底）| 4.15:1 | `#9A4708` → 4.79:1 |
| 浅色 danger | `#B3261E` | 通过 | — | — |
| 深色 danger | `#FF3B30` | `surfaceAlt`（卡内磁贴的告警字）| 4.35:1 | `#FF4A40` → 4.63:1 |

> 这几条的共同点：**不是「令牌选错了色」，而是「断言表没覆盖那个底色」。**
> 一条只验一半组合的断言表，会在自己看不见的地方一直绿着。

**第二次修表（本批）—— 它自己错了一次，而且错得很典型：**

三级灰原本被塞进「一律 4.5:1」那一档。为了达标，它被提亮到 `#8A8A92` ——
于是它与 `textSub`（`#8D8D93`）的**亮度只差 0.0116**，两级文字在屏幕上成了同一个灰。
**对比度达标了，字阶层级塌了。**

规范 §3.3 的原意一直是**两个对比度档**：
二级 `textSub` 是正文级 4.5；三级 `textTertiary` 是 **3.0 档，仅 ≥17pt 或 Bold**。
把每一档都推到 4.5，等于把层级抹平 —— 而层级才是这个设计要的东西。

**修法（两件，缺一不可）：**

1. 断言表按**档**断：`textTertiary` 用 3.0 阈值，而不是 4.5。
2. **新增一条「字阶层级自检」**：相邻两档的**亮度差**必须 ≥0.03（肉眼能分出两级的经验下限）。
   这条不是 WCAG 的东西，是本仓自己加的 —— 它防的正是上面那次塌陷复发。

> 这条自检**被注入探针验过**：把 `textTertiary` 改回 `#8A8A92`，
> 它立刻报 `dark textSub↔textTertiary 0.0116 < 0.03` 并 exit 1；
> 改回来即恢复 exit 0。

## 3. `hairline` 为什么不是范式给的 `rgba(255,255,255,0.08)`

范式 §3.1 写的是 `rgba(255,255,255,0.08)`。压到**纯黑画布**上，合成色约 `#141414`，对比度 **1.24:1** —— 而 `tools/contrast.js` 对分隔线的门槛是 1.2:1，几乎贴地，实际几乎看不见。

本仓取实色 `#3A3A40`，在 `surface`(#1C1C1E) 上是 **1.51:1**、在 `canvas` 上 1.86:1。

**这是对范式的有意偏离，理由是范式的语境不同**：范式描述的是「玻璃栏体上的 0.5pt 描边」，那层玻璃本身已经比画布亮很多；而本仓的 `hairline` 同时承担**卡片与画布之间的唯一分界**（卡片零投影，靠明度差分分层），所以它必须自己站得住。

记录在 `DEVIATIONS.md` §3。

### 4.1 间距（4pt 基数）

| token | 值 | 用途 | 范式依据 |
|---|---|---|---|
| `xxs` / `xs` / `s` / `m` / `l` / `xl` / `xxl` | 2 / 4 / 8 / 12 / 16 / 24 / 32 | 通用节奏 | §5.1 |
| `gutter` | **14** | 页边距 —— 卡片、Tab Bar、胶囊行**共用** | §5.1 实测 3.62% 屏宽 |
| `rowGap` | **8** | 卡片行间距（纵向堆叠）| §5.1 `s3` |
| `colGap` | **12** | 卡片列间距（网格）| §5.1 `s3h` —— **与 `rowGap` 是两个不同的数** |
| `section` | **28** | 区块之间 | §5.1 `s7` |
| `pageTop` | **40** | 页面顶部留白 | §5.1 `s8` |
| `card` | **16** | 卡片内边距 | §5.1 实测 15，±2 可接受 |
| `align` | **29** | **文字对齐线** = `gutter + card - 1` | §5.4 —— 大标题对齐卡片内文字，不是卡片边缘 |

**`rowGap` 与 `colGap` 为什么必须分开**：范式 §14 第 22 条与验收 L2 都单列了这一项 —— 合并成一个 token 会让纵向堆叠看起来比横向更松，而人眼读网格先读列距。

## 7. 改令牌的规程

令牌是**根**，一堆值是它的派生结果。改了根不重算派生，规范就会自相矛盾 —— 而且这种矛盾藏在不同章节里，肉眼扫不出来。

| 根 token | 改了它，必须同步重算 |
|---|---|
| `XSpace.gutter` | 卡片宽度 · 大环直径 · Tab Bar 宽度 · 双列单卡宽 · 文字对齐线 `align` |
| `XSpace.card` | 文字对齐线 `align` · 卡内可用宽 |
| `XRadius.card` | 卡内缩略图圆角（`inner` = card/2）|
| `DSFont.largeTitle` | 所有引用它的组件与 Canvas 构图 |
| `XPalette` 任一色 | `tools/contrast.js` 的 110 条断言 |

**交付前三步**：

```bash
node tools/contrast.js          # 色值断言（110 条）
node tools/apisig.js            # 令牌是否有零使用（声明了没人用 = 假令牌）
node tools/swiftcheck.js        # 括号平衡
```

> 真实教训（本批）：改页边距 16→14 之后，`XSpace.align` 必须跟着从 31 变成 29；
> 而「大环直径 = 屏宽 − 2×gutter」这条公式在 `HomeConsole` 里是硬写 220 的，不受影响 ——
> 但下一次若有人把它改成公式，就必须回到这张表。
