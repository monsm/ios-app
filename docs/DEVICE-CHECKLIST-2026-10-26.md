# 真机验证清单：布防 / 手机钥匙 / 固件升级

> 这三项是 2026-10-26 补齐的「原版 APK 有、iOS 无」功能，**全部没有真机验证过**。
> 本文是给上真机的人看的操作卡：每一步「做什么 / 看什么 / 怎么判失败」。
>
> 前置：真锁一台（KX 8098 或 V1_Pro 7858，**布防只支持这两族**）、iOS 真机、Xcode 能装 debug 包。
> DFU 另需一个**已知版本**的官方固件包（从厂商渠道拿，本仓不提供）。

---

## 0. 三项的共同风险

| 风险 | 说明 |
|---|---|
| 无编译证据 | 本仓从未执行过 XCTest，也没有 Mac 编译；只过了静态闸门（括号/形状/语法形状） |
| 无协议回读 | 布防的锁端状态帧**不带布防字段**，所以「布防成功」只能靠 cmd25 的 rc=0 + 本地配置；这不是真回读 |
| DFU 会变砖 | 中途断电/断链可能让锁停在 bootloader；本仓**没有**固件签名校验能力 |

## 1. 布防（cmd25）

### 1.1 入口与门禁

| 步骤 | 期望 |
|---|---|
| 设备页 → 齿轮 → 「门锁」段 | 只有 `PidMap.canDefend(pid)` 为真才出现「布防」行 |
| 用 K1 / V1 / JZ / 网关 | **不应出现**该行（canDefend 只放行 KX / V1_Pro / 未知 pid） |
| 布防行右侧 | 显示 `DefendKit.summary`：未设置时是「当前无布防」 |

**判失败**：不支持布防的型号也出现了入口 → `PidMap.canDefend` 的 pid 表有问题。

### 1.2 三档下发

| 操作 | 看什么 | 期望 |
|---|---|---|
| 选「不定期布防」→ 执行布防 | 日志 | `布防已下发 (25): control=1 start=0 end=0` |
| 同上 | toast | 「布防成功」 |
| 选「时段布防」22:00–07:00 → 保存 | 日志 | `control=2 start=158400 end=50400`（**半秒刻度**：22×3600×2 / 7×3600×2） |
| 选「撤防」→ 执行撤防 | 日志 | `control=0 start=0 end=0` |

**判失败**：
- `start/end` 是 `79200`/`25200`（秒）而不是 `158400`/`50400`（半秒）→ 换算漏了 `×2`
- rc≠0：`rc=13` 大概率是漏令牌；`rc=16` 是参数超范围（时段越界）

### 1.3 与自动开锁的联动（**最关键**）

这是唯一能证明布防真的生效的检查：

| 步骤 | 期望 |
|---|---|
| 布防 22:00–07:00，把手机时间调到 23:00（或用系统时间） | 自动开锁**不应**触发 |
| 站到 1 米内，等 15 秒 | 日志出现 `F4 布防时段内, 一票否决` |
| 把时间调到 12:00，再靠近 | 自动开锁**应**正常触发 |
| 撤防后靠近 | 自动开锁正常 |

**判失败**：时段内仍自动开锁 → 本地 `kf_defend_<mac>` 没写对，或 `protoSec` 与 `defendActive` 不是同一把尺。

### 1.4 失败路径

| 操作 | 期望 |
|---|---|
| 断开蓝牙后点执行 | toast「布防失败: …」，**本地配置不应变化**（重进页面仍是旧状态） |
| 时段设成 08:00–08:00 | 按钮禁用 + 红字「结束时间不能等于开始时间」 |
| 时段设成 18:00–08:00（同日内逆序） | 红字「结束时间必须大于开始时间」 |

## 2. 手机钥匙（41/43/44 + cmd08 delPins）

### 2.1 发放

| 步骤 | 期望 |
|---|---|
| 设置 → 家人与钥匙 → 「手机钥匙」 | 进得去；显示「PIN 池 N 个 · 本机已发 0 把」 |
| 选成员 + 永久 → 发一把 | toast「已给「X」发一把手机钥匙」 |
| 列表 | 出现一行：`∞ X pin <pin>` + 「永久有效」 |
| 再发一把 | pin **变成下一个**（线性取第一个未占用） |
| 把 PIN 池发满（如果锁有 64 个 pin，就得发 64 次，可先用 3 个的测试锁） | toast「这把锁的 PIN 池已用尽…」，**不应**回落到默认 PIN |

**判失败**：
- 两把钥匙拿到同一个 pin → `availablePin` 的 taken 集合没生效
- 池空仍"发放成功" → 违反 fail-closed（参考 `HardwareService.writeDongleKey` 的同类纪律）

### 2.2 撤销（**这一步必须验**）

| 步骤 | 期望 |
|---|---|
| 左滑一行 → 撤销 → 确认 | toast「已撤销」；列表少一行 |
| 日志 | `已删除 1 个 PIN (08 delPins)` |
| **用那把已撤销钥匙的手机去开门** | **必须开不了** |

**判失败**：撤销后仍能开门 → `deletePins` 没真的发出去，或 `cmd08` 的 delPinsCount/delPins 顺序错了。
这是本功能唯一有安全后果的检查点。

### 2.3 别人发的钥匙（离线限制）

| 步骤 | 期望 |
|---|---|
| 用原版 APK 给同一把锁再发一把手机钥匙 | iOS 侧「本机已发」计数**不变**（本机看不到别人的） |
| 再看 iOS 的手机钥匙页顶部 | 若 `pinInfoBinding > 本机已发数`，出现 warn 色提示「差额可能是别人发的手机钥匙」 |

**判失败**：没有任何提示 → `foreignKeyHint` 的 `app.status.pinInfoBinding` 没读到（要先读一次 03）。

## 3. 固件升级 DFU

> ⚠ **这一项风险最高**。建议第一次用一台可以接受的测试锁，且全程插电。

### 3.1 准备

1. 从厂商渠道拿一个**版本高于当前**的固件 zip
2. 确认包里有 `manifest.json` + `bin` + `dat`
3. 把锁的当前固件版本记下来（设备页 → 锁信息名片）

### 3.2 选包与降级闸

| 操作 | 期望 |
|---|---|
| 设置 → 工具 → 「固件升级」→ 选包 | 显示固件主体/init packet 大小 + 包内版本 |
| 包内版本 < 锁内版本 | 立即报「包内固件版本 X 低于锁内版本 Y，已拒绝降级」，**不能**进到"开始升级" |
| 包内版本 = 锁内版本 | 允许（同版本重刷是合法的救砖路径） |
| 选一个坏包（改一个字节） | 报 CRC 校验失败 |

### 3.3 进 DFU

| 步骤 | 期望 |
|---|---|
| 点「开始升级」→ 确认 | 先下发 cmd22，日志 `已下发 22 进 DFU: param=0（随后断链属预期）` |
| 随后 | 连接断开（**正常**，不是失败） |
| 约 2 秒后 | 开始扫描 |
| 扫描判据 | 日志/断点应看到按 **pid + dfuState==1** 命中，而不是靠广播名 |

**判失败**：10 秒内报「没发现升级模式设备」→
- 先确认锁真的重启进 DFU 了（原版 APK 能扫到吗？）
- 若不是：`parAdv` 的 `dfuState` 位（`frameCtrl & 0x20`）判断可能与固件不符
- 若是：`targetPid` 没传对（`kc.pid` 为 0 时会放行任意 pid，这可能误连别的锁）

### 3.4 传输状态机

按顺序应看到这些状态（与 APK 插件 `URLCSDfuPlugin` 的码一致）：

| 码 | 文案 | 说明 |
|---|---|---|
| 0 | 正在连接 DFU 设备 | |
| 1 | 升级进程启动 | |
| 2 | 正在切换到 DFU 模式 | |
| 4 | 正在校验固件 | Secure：CRC 阶段 |
| 5 | 正在断开 | |
| 6 | 升级完成 | **唯一成功判据** |
| 7 | 升级已中止 | 失败 |
| -1 | 连接事件 | 无独立码的中间事件 |

**判失败**：
- 卡在某个状态不动 → 看是不是 `waitAck` 15s 超时（Secure 的 PRN 流控不匹配）
- 报「锁端返回结果码 N」→ Nordic Secure 的错误码，2=操作码不支持 / 3=参数错 / 4=数据超限 / 6=操作失败
- 一直卡在 4 → `crcCheck` 发的命令锁端不认（Secure 是 `0x03`，Legacy 是 `0x02`）

### 3.5 完成

| 检查 | 期望 |
|---|---|
| 解锁后回读 | 设备页显示新版本号 |
| 门锁功能 | 开锁/密码/指纹都正常 |
| 若失败 | 锁可能停在 bootloader —— 用原版 APK 或 Nordic nRF Connect 救砖 |
