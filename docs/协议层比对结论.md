## 一、命令字节覆盖：零缺口（确认）

### APK 32 条声明，29 条有真实发送点

| 无发送点的 3 条 | 引用数 | 结论 |
|---|---|---|
| `0x02` ZKCCOMM_GETBLEMAC | **1 处（仅枚举声明）** | 死命令 |

### iOS 29 个构造器，字节级全覆盖

iOS 把 `0x0C`/`0x0D` 列进 `ZKProtocol.writeCmdsBlocked`（`:152`），**这是正确处理**（拒绝下发死命令）。

## 二、真实缺陷：cmd24（防尾随）载荷整体偏移 1，且多一档

### APK 侧

```js
// 档位数组：index 2 ↔ "2秒" ... index 6 ↔ "6秒"（无 7 秒档）
chooseBtnImgStrs = ["","","radio-button-off","radio-button-off",
                    "radio-button-off","radio-button-off","checkmark-circle"]

getCurrentChooseSecond()  // 返回索引本身，范围 2..6
execSetTailgate()         // new Hi(索引, mac) → intervalHexStr = 索引.toString(16)，不减 1
```

**wire 值 == 显示秒数。**

### iOS 侧

```swift
// SettingsView.swift:1044-1046
ForEach(2...7, id: \.self) { Text("\($0) 秒").tag($0) }   // 七档，含 APK 没有的 "7 秒"

// :1070
try await app.lock.setAutoLock(seconds - 1)               // 发 seconds - 1
```

### 后果

| 用户选 | APK 发 | iOS 发 |
|---|---|---|
| 2 秒 | 2 | **1** |
| 6 秒 | 6 | **5** |
| 7 秒 | **不存在此档** | 6（与 APK 的「6 秒」撞车） |

且 `DeviceHomeView.swift:736` 的倒计时按 `interval + 1` 反算 —— 本机自洽，与锁端不一致。

**这是本轮唯一确定的协议级真实缺陷。** 但仍需真机确认锁端把该字节解释为「秒」还是「档位」。

## 三、iOS 缺失的协议变体：未加密 0x88 包络（已核实）

### APK 同一 cmd 03 有两条路径

**路径 A（不加密）** —— `RominfoPage.getDeviceInfo` @374036：
```js
var t = new Ct(this.mac);                      // Ct 构造 0x88 包络（含 88 头）
var e = new yt(t.getBytes(), "").getParams();  // 直接塞进 KLV#01，无 AES
```

**路径 B（加密）** —— `getDeviceInfoLater` @414041：
```js
var o = Lt.enc.Hex.parse(i.getBytes());        // 同样先 getBytes()
var s = Lt.AES.encrypt(o, u, {...});           // 再 AES
var c = new yt(a, "").getParams();             // 然后塞进 KLV#01
```

`getBytes()` 的产物以 `dt`（帧头 87/88）开头，所以**未加密版 KLV#01 里放的是以 `0x88` 开头的明文包络**。

### iOS 只发加密形态

- `cmd03StatusWrap`（`ZKCmdBuilder.swift:110`）：`AESKit.encryptHex(buildEkey(...))` —— 强制 AES
- `wrapEnc`（`ZKProtocol.swift:173`）：`AESKit.encryptHex(env, keyHex: skeyHex)` —— 强制 AES

**全仓无任何路径产生 `0x88` 开头的明文包络。**

### 但这是「待实机终裁」的开放点，不是移植错误

vendor 自己标注（`cmds.js:4`）：
> 「⚠ 开放点 (G7 尾): 固件 0x2a860 对 value[0]==0x88 校验 vs 密文首字节 — 待实机终裁。」

**结论：变体确实缺，但是否必需未确定。列入「需真机验证」，本轮不改。**

## 四、构造器在、链路断（2 处，确认）

| 命令 | iOS 构造器 | 调用点 | APK 链路 |
|---|---|---|---|
| `0x30` GWGetDeviceName | `ZKCmdBuilder.swift:311` | **零** | 配网前 `getDeviceName` @612794 → checkDeviceBinding |
| `0x32` GWSetIot | `ZKCmdBuilder.swift:316` | **零** | 31 写 WiFi → **32 setIoTProfile** @614528 → 35 重启 |

`HardwareService.provisionGateway`（`:348-389`）只走 **38 → 31 → 35**，跳过 30 和 32。

iOS 注释自认（`ZKCmdBuilder.swift:303-305`）：「功能面仍不做，构造器只为 golden 对拍」。
原因：云端已停服，拿不到 IoT 三密钥。

**后果**：若目标网关仍需 IoT 档案，配网会**半途而废**（写入 WiFi 但登不上平台）。但至少 UI 要如实说明。

## 五、两项「未确定」（不猜）

### cmd13 的 orderIdx（KLV#04）

APK `ku` 类：
```js
if("04"==key){ i=value; t.orderIdxPri=parseInt(i,16) }                    // 直读，不反转
if("05"==key){ i=En.toNormalByteOrder(value); t.fPFeatureNumberPri=... }  // 反转
if("06"==key){ i=En.toNormalByteOrder(value); t.batchNumberPri=... }      // 反转
```

iOS `LockService.swift:713-714` 四个键**全用 `leHexToU32`**。

- 若 orderIdx 是 1 字节 → 两种读法等价
- 若 4 字节 → 不同

**无法从反编译确定线上长度，需真机抓包。**

### 广播门禁判据分歧

| 侧 | 判据 | 位置 |
|---|---|---|
| Java | `fc >= 0x0C` | `BLEAdData.java:40` |
| iOS | `(fc & 0x0c) == 0x0c` | `ZKProtocol.swift:306` |

对 `fc=0x10`/`0x30` 这类「高位有标志但 bit2/3 不全」的帧结论相反。**实际影响低**（这类帧罕见）。
