# iOS 界面重构 · 最终方案 v3（设备页锁能力行）

生成：2026-10-29
定位：**三份 v1 审核 + 三份 v2 审核意见的收敛结果**

---

## 一、结论先行

**最终方案 = 设备页直接放 5 项锁能力行，约 40 行代码，改 1 个文件。**

| 版本 | 改动量 | 审核结论 |
|---|---|---|
| v1 | 10,573 行 / 6 文件 / 16 新文件 | ❌ 三份审核打回（过度设计） |
| v2 | 35-75 行 / 3 文件（复用 `DeviceInfoView`） | ⏳ 审核中（预判：Hero 卡手势冲突 + DeviceInfoView 语义混乱） |
| **v3** | **约 40 行 / 1 文件** | **本文** |

---

## 二、为什么是 v3（而不是 v2）

v2 的两个被审核预判的问题：

1. **Hero 卡齿轮有手势冲突** —— `DeviceHomeView:364` 已有 `RSSIBars.onTapGesture`、`:380` 已有 `LinkPill.contextMenu`；同仓 `:863-866` 记录过「记在 NavigationLink label 上 → 次数记上了、页面没进去」的事故。
2. **`DeviceInfoView` 加「锁能力」后要滚 5 段** —— 它现有顺序是 信息卡(型号/固件/Boot/键盘/服役/MAC/绑定/链路验证/锁钟) → 连接环境 → 运行状态(电量/安全模式/锁内时间/容量) → 电池档案。**锁能力排在第 5 段之后**，用户找布防比现在「设置页第 3 行」更差。

**v3 绕开这两点：不碰 Hero 卡、不碰 `DeviceInfoView`。**

## 三、方案

### 3.1 改动：`DeviceHomeView.swift`（1 个文件）

在开锁圆盘下方（**替换现有 M2 的布防行**，位置 `:85-106`）：

```swift
// 2026-10-29：锁能力行 —— 从「设置 → 锁段」搬到设备页（用户主场景）。
// 只放「导航类」能力（点进子页）；静音（Toggle）与清空密码（破坏性）留在设置页。
// 设置页那条**保留**（双入口），不删 —— 老用户路径不打断。
if let kc = app.current {
    VStack(spacing: 0) {
        if PidMap.canDefend(kc.pid) {
            capabilityLink("布防", "shield.lefthalf.filled",
                           DefendKit.summary(DB.defend(kc.mac))) { DefendView() }
        }
        if PidMap.canTailgate(kc.pid, fw: kc.fw) {
            capabilityLink("防尾随入室", "figure.walk.arrival", "") { TailgateView() }
        }
        capabilityLink("安全模式 A/B", "lock.rotation", "") { SafemodeIntroView() }
        capabilityLink("校准门锁时间", "clock.arrow.circlepath", "") { SyncTimeView() }
        if PidMap.canDeviceUpgrade(kc.pid) {
            capabilityLink("固件升级", "arrow.up.circle", "") { DFUView() }
        }
    }
    .padding(.horizontal, DS.Space.gutter)
}
```

辅助（约 18 行）：

```swift
private func capabilityLink<D: View>(_ title: String, _ icon: String, _ detail: String,
                                     @ViewBuilder destination: @escaping () -> D) -> some View {
    NavigationLink { destination() } label: {
        HStack(spacing: DS.Space.s) {
            Label(title, systemImage: icon)
            Spacer(minLength: 0)
            if !detail.isEmpty {
                Text(detail).vkFont(.caption).foregroundStyle(DS.Palette.textSub)
            }
            Image(systemName: "chevron.right")
                .font(.system(size: 11, weight: .semibold))
                .foregroundStyle(DS.Palette.textSub)
        }
        .frame(minHeight: DS.Hit.min)
    }
    .buttonStyle(PressableButtonStyle())
    .accessibilityHint(accessibilityHintFor(title))
}
```

## 五、用户价值（诚实标注）

| 场景 | 现在（M2 已做） | v3 |
|---|---|---|
| 设备页想布防 | 点布防行 ✅ | 点布防行（不变） |
| 设备页想调防尾随 | **切设置 Tab → 锁段 → 防尾随** | **点「防尾随入室」** ✅ |
| 设备页想调安全模式 | 切 Tab → 设置 → 锁段 → 安全模式 | 点「安全模式 A/B」 ✅ |
| 设备页想校准时间 | 切 Tab → 设置 → 锁段 → 校准 | 点「校准门锁时间」 ✅ |
| 设备页想升级固件 | 切 Tab → 设置 → 锁段 → 固件升级 | 点「固件升级」 ✅ |
| 设置页老路径 | 7 项都在 | **7 项都在（不变）** ✅ |

**真实收益**：4 项能力（防尾随/安全模式/校准/固件）在设备页少一次 Tab 切换。
**不是收益**：导航层数不变；文件数不变；设置页不变薄。
**代价**：设备页多 4 行（+1 行布防已有）。

## 六、风险

| 风险 | 缓解 |
|---|---|
| 设备页变长 | 只 4 行；与 M2 布防行同组 |
| 5 个 `NavigationLink` 都在 `NavigationStack` 里，push 深度 | 都是一级 push，返回即回设备页 |
| `PidMap.canTailgate` 需要 `fw` | `kc.fw` 已有字段；读不到时 `canTailgate` 返回 false（现有逻辑） |
| 与 `moduleSlot(devOrder[1])` 的间距 | 用 `VStack(spacing: 0)` + 外层现有 `VStack(spacing: DS.Space.m)` |
| 无 UI 测试 | 人工点 5 条路径；`uicoverage` 27/27 不变（不新增 Destination） |

## 八、与 M2 的关系

**M2（`630e4de` + `9ca3462`）已经解决了「布防找不到」这个唯一有用户证据的抱怨。**

v3 是在 M2 基础上，把**其余 4 项导航类能力**也放上设备页。

**如果这 4 项也没有用户证据 —— 那就只保留 M2，v3 不做。**

**这是本方案最诚实的一句：v3 的价值取决于「防尾随/安全模式/校准/固件」这 4 项是否也有人在设备页找过。**
