# 设计决策记录

> 这份文件记的不是「改了什么」，而是**每个决定背后的依据、取舍，以及什么时候该推翻它**。
>
> 包括那些「决定了不改」的 —— 它们和改动一样需要理由，而且更容易被下一个人误当成遗漏。
>
> 每条格式：**背景 → 决定 → 依据 → 什么时候该推翻**

---

## 一、架构与导航

### D1 · 放弃三棱柱，收敛成单一控制台
- **背景**：B/D/F 三域旋转棱柱是 v1 的核心概念，但它要求用户先理解隐喻才能开门。
- **决定**：删掉棱柱，只留一个门厅（HomeConsole）。
- **依据**：门锁 App 的第一次交互必须是「按下去就开」，不能先教一个模型。
- **推翻条件**：如果产品重新定位成"多把锁、多地点"的设备管理台，那时才需要域划分。

### D2 · 管理面板保留 5 个分组，不做成一屏
- **背景**：20 个入口塞进一个抽屉会很乱。
- **决定**：5 组 × 3–5 项（钥匙 / 设备 / 成员 / 安全 / 数据与外观）。
- **依据**：每组 3–5 项是人一眼能扫完的数量。
- **推翻条件**：某一组涨到 8 项以上时就该再拆。

### D3 · 门厅与「本机设置」（MePage）保持两套并行入口
- **背景**：两者有重叠（备份 / 导出两边都能到），且 MePage 作为面板叶子又是一个完整设置页。
- **决定**：**不改**。
- **依据**：iOS 系统「设置」本身也是这种重复结构；合并是结构级改动，风险远大于收益。
- **推翻条件**：如果出现同一功能在两处行为不一致 —— 那时必须合并，不能靠"两边都改对"维持。

## 二、反馈与等待

### D4 · 开锁用长按 1.05s，不用拖拽
- **背景**：原来用 DragGesture 蓄力，与系统滚动/返回手势冲突。
- **决定**：`onLongPressGesture(minimumDuration:)`，松手即 `abortCharge` 归零。
- **依据**：门锁是金属/刚性的，「按住」比「拖动」更贴合物理直觉；且长按不与任何系统手势冲突。
- **推翻条件**：如果真机上长按被系统"触感反馈"抢先，需要改成自定义手势。

### D5 · 成功反馈必须先于状态刷新
- **背景**：`performUnlock` 里曾经先 await 刷新、再给触觉，网络慢时用户感知不到成功。
- **决定**：触觉与 toast 先发，`refreshStatusQuietly` 之后跑。
- **依据**：反馈延迟 100ms 就会让人觉得"没反应"。
- **推翻条件**：无。这条不应该被推翻。

### D6 · 同步/导出的进行中状态必须**在正文里**，不能只在菜单项文案上
- **背景**：`Button(syncing ? "同步中…" : …)` 在菜单里，点完菜单就关了，用户永远看不到。
- **决定**：正文加非阻塞常驻指示（胶囊 + ProgressView）。
- **依据**：任何"进行中"的文案，必须落在**菜单关闭后仍然可见**的位置。
- **推翻条件**：无。

### D7 · 忙碌标志一律用 `defer` 复位
- **背景**：`busy = true` 在各出口手写 `busy = false`，漏一处按钮就永久不可点。
- **决定**：全部改 `defer { busy = false }`。
- **依据**：把"记得复位"变成"不可能忘记"。
- **例外**：服务层由定时器/委托驱动的状态（如 `BLEService.scanning`），以及 `ExportCenter` 那种在 `MainActor.run` 里复位且 `self` 已释放的情况。
- **推翻条件**：无。

## 三、文案与词汇

### D8 · 用户可见文案统一说「钥匙」，不说「凭证」
- **背景**：同一个核心名词两个叫法，页面标题写「钥匙管理」而按钮写「添加凭证」。
- **决定**：125 处统一为「钥匙」（只在字符串字面量内替换，不碰标识符）。
- **依据**：用户不该为同一个东西维护两套词汇。
- **推翻条件**：如果产品转向"密码管理器"定位，「凭证」反而更准确。

### D9 · 但「删除 / 移除 / 停用」**不统一**
- **背景**：三个词看起来是同义漂移。
- **决定**：保留三种说法。
- **依据**：它们的行为确实不同 ——
  - **删除** = 本机删 + 锁端撤销（进队列）
  - **移除** = 只删本机记录（OTP 口令没有锁端状态）
  - **停用** = 停用但保留（可恢复）
- **推翻条件**：如果某天"移除"也开始走锁端撤销，那它就该并入"删除"。

### D10 · 失败提示必须给出原因或下一步
- **背景**：「保存失败」四个字，用户没法据此做任何事。
- **决定**：带 `ErrorText.human(e)`；拿不到错误时给下一步（「可改用「导出」保存到文件」）。
- **依据**：说不出原因时，至少说清下一步。
- **推翻条件**：无。

### D11 · 删除确认必须告诉用户「可以找回」——但只在真的能找回时
- **背景**：删除凭证其实进回收站保留 30 天，但确认框没讲。
- **决定**：补「本机这条会留在回收站 30 天，期间可以恢复」；而删本锁钥匙/删记录**不加这句**（它们真的找不回）。
- **依据**：不撒谎也包括不在找不回时说"能找回"。
- **推翻条件**：无。

## 四、视觉

### D12 · 间距要有层级，不能一律等距
- **背景**：门厅 8 个区块统一 32pt 间距 —— 等距等于没有分组。
- **决定**：按接近性原理分簇：簇内 16、簇间 24。
- **依据**：Gestalt 接近性；「小学生排版」最典型的特征就是所有东西一样远。
- **推翻条件**：无。

### D13 · hero 卡片内边距比 group 大 4pt
- **背景**：hero 与 group 内边距相同，只差阴影和描边，而阴影在深色模式下几乎不可见。
- **决定**：hero 用 20pt。
- **依据**：留白是层级信号，在任何主题下都成立。
- **推翻条件**：无。

### D14 · 深色/浅色两套令牌都要实测对比度，不能只验一套
- **背景**：`contrast` 闸门只验令牌对令牌，且浅色模式从没验过。
- **决定**：浅色 `textTertiary` 0x72727C→0x666670，`ok`/`warn` 各加深一档；分时柱 0.5→0.6。
- **依据**：叠透明度后实际对比度掉得比想象快（textSub×0.5 只有 2.68:1）。
- **推翻条件**：无。工具：`tools/rendercontrast.js`（矩阵 / `--scan` 反查代码 / `--stack` 两层叠加）。

### D15 · 装饰性的低对比度**不改**
- **背景**：扫描报出 10 处低于 3:1。
- **决定**：只改承载数据的分时柱；告警卡淡红底衬、1.5pt 连接线、4pt 占位点加 `@contrast-allow` 标注，不动。
- **依据**：只有承载信息的图形才受 3:1 约束。把装饰也"修"会让设计变硬。
- **推翻条件**：如果某个装饰被证实承担了状态语义。

### D16 · 动效一律不过冲
- **背景**：`XMotion` 有个 `lively` 档（damping 0.68 会回弹），但它永不可达。
- **决定**：删掉该档；`dampingFraction` 全部保持 0.85–1.0。
- **依据**：设定是金属刚性，回弹与它冲突。需要"更有活力"时改时长，不加回弹。
- **推翻条件**：如果产品改成"儿童/趣味"语气。

### D17 · 长句不用 11–12pt 排
- **背景**：85 字的说明用 footnote、84 字的用 caption2。
- **决定**：25 字以上的说明文字最低 footnote(13pt)，共调 60 处。
- **依据**：小字长文读起来吃力，而这正是"看起来很业余"的来源之一。
- **推翻条件**：无。

## 五、可点性与可发现性

### D18 · 可点元素文字不小于 footnote，可点区域不小于 44pt
- **背景**：9 处按钮用 caption2(11pt)，最坏的叠 0.75 缩放只有 8pt。
- **决定**：全部提到 footnote；唯一一处 42pt 按钮改 `XHit.min`。
- **依据**：HIG `accessibility.md`：iOS 默认 44×44，最小 28×28。
- **推翻条件**：无。

### D19 · 门厅上「看着就想点」的东西必须可点
- **背景**：成员卡写着「张三 今天 3 次」却点不动。
- **决定**：成员卡改成入口，直达成员详情（撤销权限从 4–5 步降到 2 步）。
- **依据**：用户看不出"只读展示"和"可点入口"的区别 —— 他只会试着点一下，点不动就以为卡了。
- **推翻条件**：无。**这条可以继续用**：分时图、三指标目前仍不可点，若用户反馈"想点"就该接上。

### D20 · 空态只在真正需要的页面加骨架屏
- **背景**：8 个有空态的页面没有加载骨架。
- **决定**：不改。只有告警/事件/统计三页异步读锁端日志，需要三态（骨架/空/内容）。
- **依据**：其余 8 页读本地同步数据（`DB.keychains` / `members` / `bin`），没有加载窗口。
- **推翻条件**：如果某页改成异步加载，必须同时补骨架 —— 加载中显示「还没有 X」是在说假话。

## 六、破坏性操作

### D21 · 四档递进，后果写在确认框里
- **背景**：删除、解除绑定、销毁等动作后果差异极大。
- **决定**：保留现有四档 ——
  1. 取消 + 红色按钮 + 具体后果（删除钥匙/记录/网关）
  2. 双选项 + 后果逐条解释（删除成员：「只移除档案」vs「连锁端一起收回」）
  3. 长按 2 秒（清空回收站）
  4. 勾选 + 输应用锁密码（彻底销毁）
- **依据**：每档都写**可核对的后果**（「删除后若不再配网将无法找回」「TA 仍能开门」），不是只说"确定吗"。
- **推翻条件**：如果某条动作的后果变得不可逆，必须上调一档。

### D22 · 清空回收站用长按 2 秒，不改成确认框
- **背景**：全仓只有它用长按，其他都用确认框，看起来不一致。
- **决定**：不改。
- **依据**：它是批量、不可逆、且作用在"已删除"数据上的操作；付出一点可发现性代价（行内已写明「长按 2 秒释放」）是值得的。
- **推翻条件**：如果真机测试显示用户根本不知道要长按。

## 七、我判断过、但没能验证的

这一节最重要 —— 它们看起来和上面一样可信，但**没有证据**。

| 判断 | 缺什么证据 |
|---|---|
| 所有视觉改动（间距/字号/内边距/配色）的实际观感 | **当前环境无法看到渲染结果**，全部依据代码与数值推算 |
| 长按开锁的手感、触觉反馈的强度 | 需要真机 |
| 日志同步的分页约定（`start += page.logs.count`）| 需要真机对协议 |
| 队列下发是否真的在连上锁时触发 | 需要真机走一遍"下令→回家→连接" |
| 44pt 触达是否够（有些行是系统托管控件）| 需要手指实测 |

**在这些被验证之前，"改好了"只等于"代码层面自洽"。**

## 八、已知不做的事（不是遗漏）

| 事项 | 原因 |
|---|---|
| 合并门厅与本机设置两套入口 | 结构级改动，风险大于收益（D3）|
| 统一「删除/移除/停用」 | 三者行为不同（D9）|
| 给装饰性低对比度加对比度 | 会破坏视觉意图（D15）|
| 给 8 个同步页面加骨架屏 | 没有加载窗口（D20）|
| 让 `confirmDestructiveTyped` 上岗 | 它的位置被"输应用锁密码"替代了，密码比键入一个词更难蒙混 |
| `XMetric.dial` / `XHit.dial` 等圆盘时代常量 | 已删（零引用，且它们读的 `kf_dial_size` 全仓没有写入方）|
