# 真实锁体 3D — 技术调研与状态映射

> 2026-10-21 起稿。这份文档记录 RealityKit 方案的**已知事实**与**待验证项**，
> 不记录愿望。每条断言后面要么有 CI 证据，要么明确标注"未验证"。

## 一、已验证的事实

### 1.1 `Model3D` 在 iOS 上不可用（CI 证据）

探针 `run #416` 的编译输出：

```
App/UI/RealityAPIProbe.swift:23:9: error: 'Model3D' is unavailable in iOS
```

`Model3D` 是 **visionOS 专属**。iOS 上做 3D 只有 `RealityView` 一条路。

> 这条如果没验证就动手写，会写出一大堆 `Model3D` 然后整批作废。
> 记录在此，避免下一个人再走一次。

### 1.2 协议能提供的物理状态（源码证据）

来自 `App/Core/StatusParser.swift` 的 `rcMsg` / `rcHint`：

| 错误码 | 物理含义 | 能否映射到 3D |
|---|---|---|
| 21 | 门锁处于反锁状态 | ✅ 反锁旋钮位置 |
| 26 | 门锁被撬 | ✅ 面板警示态 |
| 27 | 门锁处于布防状态 | ✅ 指示灯 |
| 20 | 指纹传感器错误 | ✅ 指纹头异常 |
| 23 | 无法获取有效指纹图像 | ✅ 指纹头提示 |
| 25 | 锁正忙 | ⚠️ 短暂态，慎用 |

### 1.3 协议**没有**的东西（决定了 3D 不能表现什么）

| 缺什么 | 出处 | 后果 |
|---|---|---|
| 门磁 / 开合状态 | `CAPABILITY.md §5`、`DoorFront.swift:12` | **不能**让 3D 门扇显示"开着还是关着" |
| 电压 / 充电态 | `BatteryCare.swift:6` | 只能显示百分比，不能做电压表 |
| 逐凭证身份 | `CAPABILITY.md §3` | 指纹头不能显示"是谁的手指" |
| 门锁朝向 / 安装位置 | 无 | 3D 模型不能声称"这是你家门的样子" |

**这一节比上一节重要。** 3D 越真实，越容易让用户以为 App 知道门真实的样子；
而协议明确没有门磁。所以 3D 锁体只能是**锁体本身**（面板/键盘/指纹头/把手），
不能是"你家的门"。

## 三、锁体形态的选型（未决，需要你拍板）

### 方案 A：纯代码几何（无资源文件）

用 `MeshResource.generateCylinder/Box` 拼一个抽象锁体：圆形面板 + 转轴 + 键盘格。

- ✅ 零资源、零体积、CI 一定能编译
- ✅ 配色/圆角可直接吃 `XPalette` 令牌，与全 App 一致
- ❌ 只是"像锁"，不是"真实锁体"

### 方案 B：usdz 模型 + RealityKit

需要一个真实锁体的 3D 模型文件（`.usdz`）。

- ✅ 真正的"真实锁体"
- ❌ **本仓没有任何 3D 资源**，我也无法在本机生成/验证 usdz
- ❌ 模型体积（通常 1–10 MB）、加载耗时、首帧空窗都是新问题
- ❌ 光照/材质要调，否则像塑料玩具

### 方案 C：照片级贴图 + 3D 变换（推荐先做这个）

用一张高质量锁体照片（或分层照片）做平面素材，
再用 `rotation3DEffect` + 视差做出"有厚度"的观感。

- ✅ 视觉上"真实"（因为它本来就是真实锁体的照片）
- ✅ 零 3D 资源管线，`rotation3DEffect` 已在 `DoorStage` 用过（7 处）
- ✅ 可以立刻验证效果
- ⚠️ 不是真 3D，大角度旋转会露馅

## 四、我的判断

**方案 C 先做，方案 B 后补。** 理由：

1. 你要的是"真实感"，而真实感的来源是**材质与光影**，不是多边形数量。
   一张好照片 + 正确的视差，比一个低模 usdz 更像真锁。
2. 方案 B 卡在资源上：我没有 3D 建模能力，也无法验证 usdz 在真机上的表现。
   硬上等于把一个无法验证的依赖塞进交付物。
3. 方案 C 的降级路径干净：照片换成 usdz 只是替换数据源，交互层不动。

## 五、和 BDF 三棱柱的关系

三棱柱切换与锁体 3D 是**两个独立的 3D 场景**，不要混在一起：

| | 三棱柱 | 锁体 |
|---|---|---|
| 目的 | 域间导航 | 状态呈现 + 交互 |
| 交互 | 滑动切换面 | 按压/旋拧 |
| 技术 | `rotation3DEffect`（2.5D 足够） | `RealityView` 或照片视差 |
| 风险 | 中（手势冲突） | 高（资源 + 性能） |

先做哪个？我建议**锁体先**，因为它是首屏，每天被看见；
三棱柱是导航改造，动的是骨架，风险更大。
