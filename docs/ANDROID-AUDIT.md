## 附：iOS ↔ Android 主屏功能级对照（第 69 轮）

| 功能 | iOS | Android | 判定 |
|---|---|---|---|
| 开锁交互 | 按住 1.05s 蓄力环 | 点击 UnlockDial | ✓ **各自忠实于各自原型**（iOS 原型=按住环，Android 原型=轻点胶囊）|
| 信号语言 | 胶囊 dBm + RingInfo | KfChip dBm + SignalMetric 状态词 | ✓ 同构 |
| 自动开锁规则 | AutoOpenKit 阈值 | AutoOpenKit 阈值 | ✓ 逐值相同 |
| 成功态 | 环转绿 + status | 环转绿 + 开锁回执卡 | ✓ Android 更丰富 |
| 设置入口 | 齿轮 → sheet | 齿轮 → 二级菜单 | ✓ 同构 |
| 后台防窥 | scenePhase 糊屏 | foreground 停扫 | ✓ 各自平台惯用 |

**结论：双端"同一功能、不同表达"的差异全部源自原型层的有意设计，实现零偏差。**

## 附二：错误文案策略（第 70 轮核查）

iOS 有 `ErrorText.human` 翻译层——因为 iOS 的失败来自**框架抛出的英文异常**
（"write failed" / "response timeout"），需要翻译。

Android 的 13 条失败文案（`BleUnlocker.kt` 的 `Outcome(false, …)`）**在源头就是人话**：
"没找到这把锁 — 靠近门锁，或确认门锁有电" / "蓝牙权限被收回了 — 到系统设置里重新允许后重试"……

→ **策略不同、结果等价**：双端用户都读不到工程术语。
→ Android **不需要**补一个 ErrorText 层——那会变成"为对称而对称"的空转。

## 附三：伪装模式与访客闸的双端差异（第 73 轮核查）

iOS 有完整的安全语义层：`decoyMode`（伪装模式，16 处）+ `guestAreaLocked`/`guestGate`
（访客闸，18 处）—— 多锁/多用户场景的产物。

Android 完全没有这两个功能（0 处）。**这不是实现遗漏**：
Android 的产品定位就是"一个人、一把门"的极简单机版（`LockStore` 注释明言，
只存一把锁），没有"给别人看假的"与"借手机给访客"的使用场景。

**判定**：双端功能面差异是**产品范围决策**，不是审美/入口问题。
若未来 Android 要加伪装/访客，需同步设计 UI（那是新目标，不属于本次对齐）。

## 附四：入口机制盘点（第 77 轮）

Android 的**唯一外部入口**是桌面图标（LAUNCHER intent-filter）。

| 机制 | iOS | Android |
|---|---|---|
| 桌面图标 | ✓ | ✓ |
| 深链（kf:// / intent VIEW）| 未接线（预留）| 未接线（对称）|
| 本地通知（生日/保养提醒）| ✓ CareReminders | 无 |
| Widget | 无 | 无 |

本地通知缺失与伪装/访客同类——**产品范围差异**（极简单机版没有提醒场景）。
若未来补，接线点是 NotificationCompat + CareReminders 的调度逻辑移植。
