# 解锁速度优化（iOS / Android）

> 目标：**自动 + 手动、iOS + Android，都做到最短、最极致、无感**。
> 本文件记录：延迟从哪来、已做了什么、还剩什么、怎么量。

## 一、延迟预算（iOS）

### 手动开锁（`requestUnlock → runUnlock → unlock`）

| 段 | 优化前 | 优化后 | 说明 |
|---|---|---|---|
| 防误触去重 | 0ms（首次） | 0ms | 1.2s 只拦**重复**点击，不加首次延迟 |
| 应用锁（30s 内重开） | 用户操作 | 用户操作 | 安全闸，不可去 |
| `ensureConnected` | 0ms（已预热）/ 0.5–2s（冷连）/ ≤8s（要扫描） | 同 | 受预热覆盖，见下 |
| 凭证构建（`DB.keychain` + ekey/PIN） | ~ms | ~ms | 本地，不是瓶颈 |
| **`cmd01` 刷会话令牌** | **1 次蓝牙往返 ≈100ms** | **0（20s 内复用）** | **本轮主要提速项** |
| `cmd04` 开门 | 1 次往返 | 1 次往返 | 协议必需，无法再省 |
| **合计（已预热）** | **2 次往返 ≈200ms** | **1 次往返 ≈100ms** | −50% |

### 自动开锁（`AutoOpen` F0–F6）

| 段 | 优化前 | 优化后 | 说明 |
|---|---|---|---|
| **到场判定（RSSI 采样）** | **最多 2s 滞后** | **最多 0.5s** | 连上后门锁停广播，只能主动读；tick 2s→0.5s |
| 门禁判定 F0–F6 | 纯计算，<1ms | 同 | 无 IO |
| `ensureConnected` | 0ms（预热已连） | 同 | |
| `cmd01` + `cmd04` | 2 次往返 | **1 次往返** | 同手动 |
| **合计（已预热）** | **2s + 200ms** | **0.5s + 100ms** | |

## 二、本轮已做（第 1 轮 / 2026-10-30）

### 1. 会话令牌有界复用 —— 省一次蓝牙往返

`LockServiceLink.ensureToken()` 原来**每次都刷 cmd01**。

历史：2026-10-27 曾把 45s 复用整个删掉，理由是「复用 + 不重试 rc=13」没有兜底。
现在 `exec` 已有 `rc=3 / rc=13 → 刷令牌重试一次`，**兜底补上了**。

所以恢复**短窗**复用：

- 只认 **20 秒内**取到的令牌（`tokenFetchedAtMs`）
- 且锁端 TTL 未到（`tokenExpiryMs > now + 2s`，保留 2s 余量）
- 且不是初始占位 `"0000"`

20s 远小于锁端常见 45s TTL ⇒ 不存在「拿快过期的令牌去发写命令」。
断链（`disconnect`）与探测链路（`probeEcho`）都会把 `tokenFetchedAtMs` 清零 ⇒ 重连后首条命令仍走完整刷新。

### 2. 自动开锁 RSSI 轮询 2s → 0.5s

门锁**一旦连上就停止广播**，`didDiscover` 不再产生样本 ⇒ 武装判定只能靠 `autoReconnectTick` 里的
`readLinkRSSI` 主动读。原来 2 秒一拍 = 到场判定最多滞后 2 秒。

现在：`AutoOpen.on` 时 0.5s 一拍（4×）；**关着时保持 2s**，不为没用到的功能付电量。

### 3. 分段耗时埋点

`LockServiceOps.unlock()` 记 `凭证构建 Xms · 下发+rc Yms` 到调试日志 —— **没有数就没有优化**。

## 三、Android 侧对照

Android APK（`jzzns22561_out` 反编译）的手动开锁：

| 环节 | Android | iOS（本轮后） |
|---|---|---|
| 位置权限 | **必需**（BLE 扫描系统限制） | 不需要 |
| 联网 | 分享钥匙**必需** | 不需要（全离线） |
| 连接 | 进页即 `didConnectPeripheral(keep:true)` 预热 | 同（预握手 + 冷启动预连） |
| 开锁往返 | 1 次（插件内部管会话） | **1 次**（本轮从 2 次降到 1 次） |
| 自动开锁 | **不存在** | F0–F6，0.5s 判定 |

> 结论：**手动档 iOS 本轮追平 Android 的 1 次往返**；自动档是 iOS 独有，Android 无可比对象。
> Android 本身不可重编译（只有反编译产物），所以「优化 Android」只能是**对照其做法、把等价优化落到 iOS**。

## 三·补 第 2 轮（2026-10-30）

### 4. 修了一个让自动开锁**完全失效**的 bug

`AppState.refreshStatusQuietly()` 成功读到状态后**只写 `status`，不写 `snapshot`**。
而 `snapshot` 只在 `select()` / 初始化时读过一次。

而 `AutoOpen.makeContext()` 的 **F6 判据用的是 `app.snapshot`**：

```swift
lockReady: snap != nil && snap?.rc != 25 && snap?.rc != 26
```

⇒ 若这把锁在本次启动里没被 `select()` 过一次（例如冷启动直接进设备页），
`snapshot == nil` ⇒ **F6 永远拒** ⇒ **自动开锁一次都不会触发**，而且审计里只会写「F6 锁态未知或忙」。

**已修**：每次成功读到状态同步 `snapshot = DB.readStatus(kc.mac)`。

### 5. 预热期预取会话令牌 —— 首次开锁也从 2 次往返降到 1 次

新增 `LockService.prefetchSession()`，在**三条预热路径**成功后调用：

| 路径 | 时机 |
|---|---|
| `LinkSense.refresh()` | 进页 / 回前台（135） |
| `LinkSense.preconnect()` | 冷启动 / 信号围栏触发（95/93） |
| `startupPreconnect()` | App 启动链路 |

预热发生在**用户还没点开锁**的时候，多做一次 cmd01 不占用户时间；
等真点开锁时令牌已在 20s 复用窗口内 ⇒ 首次开锁只剩 cmd04。

**并发安全**：调用前判 `waiter == nil` —— 用户若已在开锁，宁可跳过预取，也不去撞单槽 waiter 拖慢真实操作。

### 更新后的延迟预算

| 场景 | 第 1 轮后 | 第 2 轮后 |
|---|---|---|
| 手动（已预热，令牌命中） | 1 次往返 ≈100ms | 同 |
| **手动（首次/冷）** | **2 次往返 ≈200ms** | **1 次往返 ≈100ms** |
| **自动（已预热）** | 0.5s + 1 次往返 | 同 |
| **自动（从未读过状态）** | **永远不触发（F6 死门）** | **正常触发** |

## 三·补 第 3 轮（2026-10-30）

### 6. 手指落下就预热连接 —— 把建连耗时藏进按压时间里

原来 `UnlockDial` 的连接要等到 `fire()` 才开始，而 `fire()` 的触发条件是：

- 按住确认满 **1.2s**
- 或上滑越过 **-56pt** 阈值后松手
- 或关闭按住确认时的轻点（`onEnded`）

也就是说：**按住确认的那 1.2 秒里，链路完全是空的**。

新增 `UnlockDial.preconnectAction`，在 `pressing` 由 false→true 的**那一拍**（即手指落在圆盘内）
就发起 `ensureConnected`。

| 时机 | 优化前 | 优化后 |
|---|---|---|
| 手指落下 | 无动作 | **开始建连** |
| 按住 1.2s | 空等 | **建连进行中**（0.5–2s 的建连被这段吃掉） |
| 松手 fire() | 才开始建连 → 再 cmd04 | 链路多半已就绪 → **直接 cmd04** |

**放在 `pressing = true` 之后而不是 `onChanged` 开头**：要先过起手围栏（61）与误触围栏（62），
避免边缘误触也去建链。

**不会多下发任何指令**：只建链，不执行（96 铁律）。用户中途取消（松手回弹 / 拉回原点）时，
连接保留即可 —— 下次开锁更快。

### 更新后的延迟预算

| 场景 | 第 2 轮后 | 第 3 轮后 |
|---|---|---|
| 手动（按住确认 1.2s） | 1.2s 空等 + 建连 + 1 次往返 | **1.2s 内完成建连** + 1 次往返 |
| 手动（轻点档，已预热） | 建连 + 1 次往返 | 同 |
| 手动（轻点档，冷链路） | 建连 0.5–2s + 1 次往返 | 同（但落手到松手之间已抢跑一部分） |

> 注：轻点档（`holdConfirmOn == false`）里落手到松手只有几十 ms，抢跑收益小；
> 主要收益在**按住确认档**（默认档）—— 那 1.2s 现在不再是纯等待。

## 三·补 第 4 轮（2026-10-30）

### 7. 武装判据：单样本 → 3 样本中值

原来 `AutoOpenKit.rssiSample` 是**单样本**判定：

```swift
if prevArmed { return rssi > disarm }
return rssi >= arm
```

一个抖动样本就能翻转 armed：

- 走近时被一次 `-85` 尖峰打断 ⇒ **不武装**，用户要在门口多站一拍；
- 已武装后被一次假强信号维持 ⇒ 走开了还留着 armed。

现在 `rssiArmedByMedian` 取最近 **3 个样本的中位数**再判：

| 状态 | 判据 | 理由 |
|---|---|---|
| 已武装 → 解除 | **单样本**跌破解除线即解除 | 走开要快，不能被中值拖住 |
| 未武装 → 武装 | **3 样本中值** ≥ 武装线 | 抗单点尖峰 |

**不会变慢**：3 样本窗里只要 2 个达线，中位数就达线 ⇒ 真的走近时**1 个样本就能过**（与原来同快），
只是尖峰不再误拦。

### 8. 换锁清空样本窗

`feedRssi` 换锁时除了复位 `armed`，现在也 `rssiHistory.removeAll()`。
否则上一把锁的 RSSI 会参与中值判定 —— 用 A 锁的强信号把 B 锁武装起来（F3 是"这把锁够近"的判据，混锁 = 假武装）。

### 第 4 轮后的状态

| 项 | 值 |
|---|---|
| 协议往返（手动/自动） | **1 次（协议下限）** |
| 自动判定窗口 | **0.5s** |
| 建连 | 预热覆盖 + 落手抢跑 |
| 武装判据 | 中值滤波，抗尖峰且不变慢 |
