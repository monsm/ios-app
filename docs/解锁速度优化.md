# 解锁速度优化（iOS / Android）

> 目标：**自动 + 手动、iOS + Android，都做到最短、最极致、无感**。
> 本文件记录：延迟从哪来、已做了什么、还剩什么、怎么量。

## 一、延迟预算（iOS）

### 手动开锁（`requestUnlock → runUnlock → unlock`）

| 段 | 优化前 | 优化后 | 说明 |
|---|---|---|---|
| 防误触去重 | 0ms（首次） | 0ms | 1.2s 只拦**重复**点击，不加首次延迟 |
| 应用锁（30s 内重开） | 用户操作 | 用户操作 | 安全闸，不可去 |
| `ensureConnected` | 0ms（已预热）/ 0.5–2s（冷连）/ ≤8s（要扫描） | 同 | 受预热覆盖，见下 |
| 凭证构建（`DB.keychain` + ekey/PIN） | ~ms | ~ms | 本地，不是瓶颈 |
| **`cmd01` 刷会话令牌** | **1 次蓝牙往返 ≈100ms** | **0（20s 内复用）** | **本轮主要提速项** |
| `cmd04` 开门 | 1 次往返 | 1 次往返 | 协议必需，无法再省 |
| **合计（已预热）** | **2 次往返 ≈200ms** | **1 次往返 ≈100ms** | −50% |

### 自动开锁（`AutoOpen` F0–F6）

| 段 | 优化前 | 优化后 | 说明 |
|---|---|---|---|
| **到场判定（RSSI 采样）** | **最多 2s 滞后** | **最多 0.5s** | 连上后门锁停广播，只能主动读；tick 2s→0.5s |
| 门禁判定 F0–F6 | 纯计算，<1ms | 同 | 无 IO |
| `ensureConnected` | 0ms（预热已连） | 同 | |
| `cmd01` + `cmd04` | 2 次往返 | **1 次往返** | 同手动 |
| **合计（已预热）** | **2s + 200ms** | **0.5s + 100ms** | |

## 二、本轮已做（第 1 轮 / 2026-10-30）

### 1. 会话令牌有界复用 —— 省一次蓝牙往返

`LockServiceLink.ensureToken()` 原来**每次都刷 cmd01**。

历史：2026-10-27 曾把 45s 复用整个删掉，理由是「复用 + 不重试 rc=13」没有兜底。
现在 `exec` 已有 `rc=3 / rc=13 → 刷令牌重试一次`，**兜底补上了**。

所以恢复**短窗**复用：

- 只认 **20 秒内**取到的令牌（`tokenFetchedAtMs`）
- 且锁端 TTL 未到（`tokenExpiryMs > now + 2s`，保留 2s 余量）
- 且不是初始占位 `"0000"`

20s 远小于锁端常见 45s TTL ⇒ 不存在「拿快过期的令牌去发写命令」。
断链（`disconnect`）与探测链路（`probeEcho`）都会把 `tokenFetchedAtMs` 清零 ⇒ 重连后首条命令仍走完整刷新。

### 2. 自动开锁 RSSI 轮询 2s → 0.5s

门锁**一旦连上就停止广播**，`didDiscover` 不再产生样本 ⇒ 武装判定只能靠 `autoReconnectTick` 里的
`readLinkRSSI` 主动读。原来 2 秒一拍 = 到场判定最多滞后 2 秒。

现在：`AutoOpen.on` 时 0.5s 一拍（4×）；**关着时保持 2s**，不为没用到的功能付电量。

### 3. 分段耗时埋点

`LockServiceOps.unlock()` 记 `凭证构建 Xms · 下发+rc Yms` 到调试日志 —— **没有数就没有优化**。

## 三、Android 侧对照

Android APK（`jzzns22561_out` 反编译）的手动开锁：

| 环节 | Android | iOS（本轮后） |
|---|---|---|
| 位置权限 | **必需**（BLE 扫描系统限制） | 不需要 |
| 联网 | 分享钥匙**必需** | 不需要（全离线） |
| 连接 | 进页即 `didConnectPeripheral(keep:true)` 预热 | 同（预握手 + 冷启动预连） |
| 开锁往返 | 1 次（插件内部管会话） | **1 次**（本轮从 2 次降到 1 次） |
| 自动开锁 | **不存在** | F0–F6，0.5s 判定 |

> 结论：**手动档 iOS 本轮追平 Android 的 1 次往返**；自动档是 iOS 独有，Android 无可比对象。
> Android 本身不可重编译（只有反编译产物），所以「优化 Android」只能是**对照其做法、把等价优化落到 iOS**。

## 四、还剩什么（下一轮候选）

| # | 项 | 预期收益 | 风险 |
|---|---|---|---|
| 1 | **预热时预取令牌**（进页/前台预热成功后顺手 cmd01） | 首次开锁也从 2 次往返变 1 次 | 与用户点击并发时会撞 `waiter` 单槽 ⇒ 需要排队机制 |
| 2 | **预热时预取状态**（`getStatus`），顺带完成 F6 锁态门 | 省掉自动开锁对快照的依赖 | 多一次往返，需权衡 |
| 3 | **`DB.keychain` 内存缓存** | 省几 ms 的 JSON 解码 | 需失效策略 |
| 4 | **连接参数调优**（`CBConnectPeripheralOption` / 期望连接间隔） | 连接与往返更快 | CoreBluetooth 不暴露连接间隔，只能间接影响 |
| 5 | **Android 侧**：只能给建议，不可重编译 | — | — |

## 五、怎么量（真机）

1. 设置 → 诊断 → 蓝牙遥测：找 `开锁耗时: 凭证构建 Xms · 下发+rc Yms`
2. 自动开锁：`AutoOpen` 审计里看「拒开 F3 信号未达线」出现的频率 —— 若多，说明阈值/采样还需调
3. 关掉自动开锁做对照：tick 2s vs 0.5s 的电量与响应差异
