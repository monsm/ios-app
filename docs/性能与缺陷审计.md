# 性能与缺陷审计（地毯式 · 对抗式）

> 第 1 轮：2026-10-29。目标是找**真**问题（不是"看起来像问题"的清单），所以每条都要求能说出
> "谁在什么频率下调用它、原来的复杂度是多少、改完变成多少"。
> 本机是 Windows，没有 Swift 编译器 → 不能跑 Instruments；因此这里只做**可证明的复杂度/调用频率**分析，
> 编译正确性由 CI 的 iOS 构建兜底。

## 一、方法

1. **找数据源成本**：本仓的「数据库」是 `UserDefaults + JSON`。一次 `Store.get` = `data(forKey:)`
   + 新建 `JSONDecoder` + 全量解码。先确认这一点，后面所有"读 DB"都要按这个成本计价。
2. **找调用频率**：静态找出所有 `var body` / `xxx: some View` / `@ViewBuilder func` 区域里的 DB 访问，
   以及 `ForEach { ... }` 闭包体内的 DB 访问（后者是"每行一次"）。
3. **找隐藏常数**：`DateFormatter()` / `ISO8601DateFormatter()` / `DateFormatter.localizedString(...)`
   的初始化成本是 0.3–2ms，出现在循环里就是灾难。
4. **找笛卡尔积**：循环体内再对另一个集合做线性查找（`first(where:)` / `contains` / `filter`）。
5. **找无界增长**：数组 append 是否有上限、字典是否在每轮扫描前清空。

## 二、已修（按影响排序）

### P0-1 `Attribution.classify` 是 O(日志 × 临时码)，且每次迭代建 2 个 DateFormatter

```swift
return logs.map { e in
    ...
    let hits = temps.compactMap { p -> LedgerPwd? in
        guard let f = ms(p.from), let to = ms(p.to), f <= t, t <= to else { return nil }
```

`ms()` 原来每次调用**新建 2 个 DateFormatter**。100 条日志 × 20 条临时码 = 2000 次调用
⇒ **4000 个 formatter**。按 0.3ms 算就是 **1.2 秒**，而且这条路径在记录页每次刷新都走。

修法：时间窗先算一次（O(临时码)），`ms()` 的两个 formatter 改成线程级缓存。
→ O(日志 × 临时码) 的**字符串解析**消失，只剩整数比较。

### P0-2 全仓 `DateFormatter()` 新建：48 处 → **0 处**

新增 `App/Core/DateFormats.swift`：
- `DF.cached(format, timeZone:locale:)` —— `Thread.current.threadDictionary` 做线程级缓存
- `DF.stamp` / `DF.stampUTC` / `DF.minuteUTC` / `DF.day` / `DF.shortDayTime` / `DF.iso()`
- `DF.localTime` / `DF.localShort` / `DF.localDate`（`DateFormatter.localizedString` 的缓存版）

为什么不用 `static let`：Swift 6 语言模式下非 Sendable 全局会被判并发不安全；
`threadDictionary` 是线程私有，无锁无竞态，键里带时区标识（改时区自然重建）。

热点替换：
| 位置 | 调用频率 |
|---|---|
| `StatsKit.dayKey` | 记录分组 / 补缺口，按天循环 |
| `RecordSearchBuild.dateFromKey` | `fillGaps` 每对相邻日 2 次 |
| `RecordSearchBuild.localStr` | 按记录 |
| `ZKProtocol.localStr` | `parseLogEntry` 每条日志 1 次 |
| `Attribution.ms` | 见 P0-1 |
| `CredentialOrg.credFormatter` | 台账串解析，按行 |
| `FpDetailStudio.credDay` / `DongleView.shortTime` | 按行 |
| `HardwareService.log` / `DeviceHomeSupport` / `DeviceInfoView` | BLE 日志行 / 设备页每次 body |

### P0-3 `Store.get` 每次全量解码

视图 body 里有 ~70 处读 DB，记录页/成员页还会按行读。加 `valueCache`：
- 键 = 裸键，变体 = 类型名 / `"dict"`
- `set` / `setCodable` / `remove` 成功后**精确失效该键**
- 已核实：全仓无绕过 Store 直接写 `UserDefaults` 的地方

### P1-3 锁屏 1 秒定时器每次 body 重算都新建


## 三·补 第 2 轮新增（2026-10-29 晚）

### P0-4 成员活跃度：O(成员² × 锁 × 日志)

`MemberHub.activity(id)` 每调一次就要把**每把锁的全部日志**读一遍 + `Attribution.classify` 分类。
而成员中心里：

- `activityTable` 对每个成员调一次（排序用）
- `MemberRow.subLine` 每行调一次
- `MemberRow.staleTag` 每行又调一次

⇒ 10 个成员 × 2 把锁 × 100 条日志 ≈ **4000 次分类/渲染**。

修法：`MemberHub.activityBundle(ids:)` 一次遍历（外层走锁、内层按 who 累加），
顺带算出访客分组的「未归属临时码记录数 / 名下临时码数」。
`MemberCenterView` 改成 `@State` + `.task` / `.onChange(of: tick)` 刷新，
`MemberRow(member:act:)` 由父视图传入。

### P1-5 日志落盘：分页每页写一次 → 循环结束写一次

`RecordsRows.fetch` 是 pageSize 5 / 最多 20 页，原来每页都 `DB.writeLogs` ⇒
20 次「整份缓存解码 → 合并 → 整份编码 → UserDefaults 落盘」。
改成循环结束统一写一次；`catch` 分支也补一次（中途失败时已拉到的页不丢）。

> **更正**：我一度把 `writeLogs` 误读成「覆盖整个缓存」，据此得出"分页只留最后一页"的数据丢失结论 ——
> 实际源码是 `for l in (logs.map {...} + cache.logs)`，本来就有合并。那是性能问题，不是数据丢失。
> 保留这条是为了记住：**报 bug 之前必须看到完整表达式**，不能被截断的显示骗了。

### P1-6 记录页搜索每敲一个字全量重建

`onChange(of: searchText) { applyFilter() }`，而 `applyFilter` 每次都做
`buildRecs` + `classify` + `buildPool` + `groupByDay` + `fillGaps` + `damageDays`。
快速输入 10 个字 = 10 次全量重建。

改法：解析预览标签（`parsedTags` / `highlightTokens`）仍即时更新，
只把 `applyFilter()` 放进 **180ms 防抖 Task**，`onDisappear` 取消。

### P1-7 三个「只写不读」的 @Published

| 属性 | 谁读 |
|---|---|
| `LockService.logs` | **零** |
| `LockService.recentFrames` | **零**（只有自己的 count） |
| `HardwareService.logs` | **零** |

而 `DeviceHomeView` 观察 `LockService.shared` ⇒ **每写一行 BLE 日志都让设备页整页重算**。
去掉它们的 `@Published`（保留普通数组）。`connectedMAC` / `lastError` 仍发布（确实驱动 UI）。

### P1-8 `AppState.status` 每次轮询无条件赋值

`status` 是 `@Published` 且被 `RootView` 与设备页观察；绝大多数轮询读到的值与上次相同，
却仍然让整棵树重算 body。加 `LockStatus: Equatable` + `AppState.applyStatus(_:)`（值不变不赋值）。

（前者是一次 UserDefaults 整域拷贝）。当前 0 处。

## 三·补 第 3 轮新增（2026-10-29 晚）

### P0-5 诊断日志：每写一条 = 读一次文件 + 写一次文件

`DiagLogs.append` 的实现是：

```swift
var list = entries              // = DiagLogStore.load()：Data(contentsOf:) + JSONDecoder
list.append(...)
...
DiagLogStore.save(list)         // JSONEncoder + 原子写文件 + setResourceValues
```

而 `LockService.log()` **每写一行日志都调它**（info/warn/error 全走）。一次开锁十几行日志
⇒ **十几次文件读 + 十几次整文件写**（每次都是最多 500 条的全量编解码），全在主线程。
这是本轮 IO 最重的一处 —— 同时吃 CPU 和闪存寿命。

修法：`entryCache: Locked<[DiagLogEntry]?>` 内存缓存 + `append` 只标脏 +
`scheduleSave()` 1 秒防抖合并 + `flush()`（只在真脏时写，挂 `.background` 与 `.inactive` 两处）。
`all()` / `today()` 读内存。

> 为什么 Store 不做同样的事：`Store.set` 的调用点经常紧接着回读（新增后立刻 `DB.getPwd` 做快照），
> 批量落盘会造出读后写陈旧。诊断日志是"只追加、读侧只要展示"，1 秒延迟没有正确性代价。

### P1-9 又 4 个「只写不读」的 @Published

| 属性 | 读引用 |
|---|---|
| `LockService.lastError` | **0**（每条 warn/error 写入） |
| `LinkSense.lastReconnectAt` | **0** |
| `AppState.pendingMac` | 0（只在 AppState 内部落地） |
| `AppState.pendingCredPanel` | 0（`RootTabs` 注释已写明"全仓零读取方"） |

全部降级为普通属性。加上第 2 轮那三个，两轮共降级 **7 个只写不读的 @Published**。

### 自查回归修复：`writeStatus` 跳过写入会让「数据截至」不更新

第 1 轮给 `DB.writeStatus` 加了"字段全等就不写"，但信封里的 `at` 是 `statusTime()` 的展示基准
（断连时 UI 显示「数据截至 14:32 · 缓存」）。完全不写会让用户看到一条明明刚读过、却标着很旧时间的快照。

修法：字段全等 **且距上次落盘 < 60s** 才跳过；超过 60s 仍刷新一次 `at`。

### 第 3 轮新增闸门：	ools/dupscan.js

「按块替换」改代码时两次把旧函数留在原地（DiagKit 的 ll()/today()/append()），
本地全部静态闸门绿、CI 编译才报 invalid redeclaration。

dupscan 用大括号深度追踪 struct/enum/class/extension/protocol 与 unc 作用域，
只判「**同一类型作用域内**同签名出现 >1 次」—— 不会误报「不同 struct 各自实现 makeBody(configuration:)」
（初版就是那样误报了 7 组）。

正控已验证：注入两个 _dupProbe() → exit 1；还原 → 通过。
## 三·补 第 4 轮新增（2026-10-29 晚）

### P1-10 `toast` 挂在 AppState 上 —— 每条提示重算整棵树

`@Published var toast` 在 `AppState` 上，而 `RootView` + 43 个视图都观察它。
「保存成功 / 开锁失败 / 校验提示」这类提示高频出现，每次都要让整棵树重算 body。

修法：新增 `Core/ToastCenter.swift`（独立 `ObservableObject`），`AppState.showToast` 只转发；
UI 侧只有 `ToastBannerHost` 这个很小的视图观察它。

### BUG-1 `corruptDictKeys` 置位后永不清除

`Store.getDict` 解码失败 → `insert(k)`；`saveKeychain` 见标记就 `return`。
但**没有任何地方清除它** ⇒ 一次解码失败后，整个会话里所有钥匙串写入被静默拒绝：
用户配新锁时 `saveKeychain` 什么都不做，界面显示"添加成功"，下次启动锁就没了。

修法：`set`/`setCodable` 写成功后清除该键的标记；`remove` 也清除；
`corruptDictKeys` 换成 `Locked(Set<String>)`（原来是无同步 Set 读写）。

### BUG-2 `ledgerLock` 同一个病

`markLedgerCorrupt` 置位后，`saveLedger` 一律 `return` —— 包括**备份恢复时的凭证导入**
（内部走 `saveLedger`）。一次解码失败 = 整个会话里恢复的凭证全部静默丢失。

修法：
- 新增 `DB.clearAllLedgerCorrupt()`，只在**用户显式选择以备份为准**的 `BackupStudioKit.restore` 里调用；
- `saveLedger` 拒写时记一条 `BleTelemetry` —— 不再静默。

> 深层修法（下一轮）：给 `Ledger`/`LedgerPwd` 写容错解码（缺失字段回落默认值），
> 从根上避免"加一个字段就让老台账整表解不出"。

## 三·补 第 5 轮新增（2026-10-29 晚）

### BUG-3 合成 Decodable 的陷阱：加一个字段就让整份老数据解不出

第 4 轮修了两个「损坏标记永不清除」，但那只是症状。真正的触发源是 Swift 的合成解码规则：

> **合成的 init(from:) 只对 Optional 字段用 decodeIfPresent；非 Optional 字段的默认值
> 不参与解码 —— 键必须存在。**

而本仓的持久化模型（LedgerPwd / LedgerFp / Ledger / StatusSnapshotData / LogCache / CachedLog）
几乎全是「非 Optional + 带默认值」。于是：

| 模型 | 一次解码失败的用户可见后果 |
|---|---|
| Ledger 家族 | markLedgerCorrupt → 整个会话的凭证写入（含备份恢复导入）被静默拒绝 |
| StatusSnapshotData | readStatus 返回 nil → 设备页/锁设置所有读数变「—」 |
| LogCache / CachedLog | readLogs 返回空数组 → **记录页升级后突然一条都没有**（看起来像记录被删光） |

### 修法（两轮）

1. **第 4 轮**（症状）：corruptDictKeys / ledgerLock 写成功后清除；备份恢复可清台账标记；拒写不再静默。
2. **第 5 轮**（根因）：给上述模型全部手写 init(from:)，逐字段 decodeIfPresent + 默认值；
   数组用新增的 Lossy<T> 逐元素容错 —— 单条坏记录只丢那一条，不连累整份。

swiftshape 的 R3「合成 Codable 雷区」从 **8 → 6**（剩下 6 个是备份信封等非持久化模型）。

> 取舍：Lossy 会静默跳过解不出的单条。比「什么都读不出来」好，但确实会丢那一条 ——
> 所以保留 ledgerDiff 的变更流水，让「这次写入少了什么」仍可追溯。

## 五、限制（必须说清）

- 本机无 Swift 编译器 → **没有实测耗时**。上面所有数字都是从"调用次数 × 单次已知成本"推出来的量级，
  不是 Instruments 采样。
- 编译正确性由 CI（iOS 27 SDK 构建）兜底；本轮所有提交都跑过 44 道静态闸门 + CI 四作业。
- `DateFormatter` 线程级缓存的语义前提：`DateFormatter` 对格式化/解析是线程安全的（Apple 文档）。
  同一线程内复用同一个实例，不跨线程共享。
