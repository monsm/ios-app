触发：真机 rc13 现场（锁重置后一直配不上）+ 用户明确要求"不止查 rc13，把全部和锁交互的代码都查一遍，防止把锁变砖"。

口径（三条，缺一条就会变成自证）：

1. **只认原件**：`apk_raw/assets/www/build/main.js`（APK 的 JS 命令类与 0x88 包络类）、
   `jzzns22561_v2/sources/cn/zelkova/ZKurlcsPlugin/lockprotocol/*.java`（真正上线的字节：帧头 / 令牌注入 / 分片 / 重试）、

3. **说不清就说不清**：没有真锁验证的一律进 §9，不写成"已验证"。

## 1. 先把"砖"定义清楚：三种形态

| 形态 | 成因 | 能不能自己救 | 本轮结论 |
|---|---|---|---|
| **软砖** | 锁内密钥域被换成一份**本机读不懂**的钥 ⇒ App 配不上、也开不了 | 能：走到锁跟前做键盘重置（擦密钥域重新配） | 只剩 2 条成因，见 §2 |
| **硬砖** | 固件/引导区被写坏 ⇒ 键盘重置也没用 | 不能，只能返厂 | 只有 DFU 路径能造成，见 §4 |
| **假砖** | 台账与锁端不一致（屏上说"已添加/已删除"，锁里并不是） | 能：重读锁端对账 | 记账层已无"报成功但没生效"的口子，见 §5 |

---

## 2. 软砖面：密钥域的**唯二**写入点

锁内密钥域只有两条命令能碰，两条的唯一调用点都在 `LockService.pair` 的配网链里：

### 2.1 cmd 05（EXSECURITYKEY）—— 唯一会**擦**旧钥域的命令

- 固件行为（`REVERSE_REPORT.md` §5 / vendor `protocol.js:19-27` 注释）：擦 flash 域 7+8 后写入新 skey。**rc=0 就是"锁已经被改过"**。
- 前置门：目标 MAC 已有钥匙串 ⇒ 直接拒绝（`LockService.pair` 开头），不会把已有设备覆盖掉。
- 顺序纪律：23（免令牌）→ 01（取令牌）→ 05（带 KLV#0xEE）→ 尾链。与 APK 逐字一致（见 §7）。
- **重发纪律**：只有 `rc != 0` 才能重发（rc≠0 = 锁没执行）。`rc=0` 之后再发一帧 = 二次擦写密钥域 ⇒ 本机与锁端密钥错位。现实现里 05 只在 rc13 那一支重试一次，其余 rc 直接抛。
- **本轮修（关键）**：`rc=0` 之后**立即**把这套密钥落盘（系统 Keychain 存 skey/bkey/pins，plist 只留非密字段），尾链走完再提升为正式钥匙串（`DB.savePendingPair` / `DB.pendingPair` / `DB.clearPendingPair`，`LockService.finishPairing`）。
  于是"尾链任一步失败 / 断链 / App 被杀"不再需要键盘重置：**再点一次配网会先试续配**——用留存密钥直接走 08 → 21 → 03（跳过 05，不碰密钥域）。
  旧实现要等尾链全绿才落盘，任何一步失败就只剩"去锁跟前重置"一条路——那就是本仓最接近"变砖"的体验。

### 2.2 cmd 21（bkey）

- 只覆盖 bkey，不擦密钥域；**同值重发幂等**（锁端只是把同一个值再写一遍）⇒ 续配路径里重发安全。
- bkey 不是随手随机：APK 对相邻字节做了整形（`|a-prev| <= 2 ⇒ a+6`，>255 则取 6），本机 `KeyGen.genBkey` 与它逐行相同（否则可能撞 rc=18「不能设置重复的值」）。

### 2.3 剩余软砖成因（只剩这两条）

1. **换钥回显不匹配**：锁回显的 skey 与本机那份不同（本机读不懂锁里那份）⇒ 续配也无意义，只能键盘重置。文案已与"可续配"那一族**明确分开**（`pairWarning(false, …)` 不追加续配承诺）。
2. **本机留存也丢了**：系统 Keychain 写失败（后台首启未解锁）或用户卸载 App。写失败时日志显式记 `配网中断保护未能落盘 …`，并在尾链失败文案里不再给续配承诺（`resumable=false`）。

## 3. 重发纪律：逐命令（这是"别把锁玩坏"的主线）

判据两条：① **rc≠0 = 锁没执行**（协议语义）；② **结果未知（响应超时/写失败）时，非幂等命令一律不重发**（`ZKProtocol.writeCmdsBlocked` + `LockService.request` 的 `maybeExecuted` 分支）。

| 命令 | 写锁端 | 结果未知能否重发 | 现实现 |
|---|---|---|---|
| 01 / 12 / 23 / 03 / 16 / 30 / 38 / 43 / 44 | 否（读） | 能 | 传输层重试 3 次 |
| **04 开锁** | 是（电机） | **不能**（双开门） | 命中 writeCmdsBlocked ⇒ 超时/写失败即停；`retries: 2` 只对传输失败生效 |
| **05 换钥** | 是（擦密钥域） | **不能**（rc≠0 才行） | 见 §2.1 |
| 08 / 0A / 0B / 13 / 14 / 15 / 18 / 19 / 20 / 21 / 22 / 24 / 25 / 31 / 32 / 35 / 41 | 是 | 不能 | 命中名单 ⇒ fail-closed，报错让用户确认后重试 |
| 任意令牌命令 + `rc=3` | — | 能（锁没执行） | `exec()` 刷令牌后重试一次 |

配置类命令（18/19/20/24/25/22 等）本身同值幂等，但**仍不给自动重发**：宁可让用户再点一次，也不让"可能是残帧"的帧打在锁上。

## 4. 硬砖面：DFU（唯一能写坏固件的路径）

- **入口**：cmd 22（needToken）→ 锁重启进 bootloader（广播 `ZkDFU`、MAC+1），重启瞬间断链属预期（`enableDfu` 已容忍）。
- **包结构校验**（`App/Services/DFUKit.swift`）：zip 完整性 / 条目数 / 尺寸上限 / `manifest.json` 与 init packet 存在 / CRC / 固件尺寸区间 / **拒绝降级**（`versionLt`）。
- **没有签名校验**：原版从厂商云拿包（云已停服），本机改本机导入 ⇒ 离线拿不到可信来源。代码里已把这一点写明（`DFUKit.parse` 附近注释）。⇒ **只烧仓里的原厂包** `vendor/fixture/KX_V5.2.9_180503183402.zip`；别的来源（群友分享/改名）结构校验能过，但没人能证明它属于这把锁。
- **中断风险**：DFU 传输期间进程被杀 / 蓝牙断开 / 用户走远 ⇒ 引导区半写 = 真正的硬砖。缓解：本仓已在「检查固件更新」「添加指纹」两页置任务期屏幕常亮（`ScreenCare`）。
- **待核（§9）**：升级前的二次确认文案是否写清"传输中离开/断电可能导致设备无法使用"。

## 5. 假砖面：台账 ↔ 锁端一致性

| 路径 | 曾经的坑 | 现状 |
|---|---|---|
| 0A 添加密码 | 响应里没有 alias 时旧实现 `return 0` ⇒ 屏上报"已添加 (别名 #0)"、台账记成 0 号，而 0 是协议里"本次不删任何密码"的保留值 | **抛错不登记**，并让用户到锁端核对（fail-closed） |
| 0B 设置有效期 | 有效期解析失败时旧实现静默回落"现在" | 传了但解析不出 ⇒ 中止下发（0A/0B 同口径） |
| 13/14/15 指纹 | 14 需要 13 返回的 batch；batch 是 UInt32，台账是 Int | `batchU32` 拦截负值/越界（否则 `UInt32(-1)` 是 trap ⇒ 点删除即崩） |
| 16 日志 | 帧被截半条时静默吞掉 | 缓存原样入档 + 记"这一页有 N 条声明长度不符" |
| 演示数据 | 先删设备再写日志缓存 ⇒ 为不存在的锁重建空缓存，体检永远报孤儿 | 写缓存前判"锁还在台账里"（`DB.cacheWritable`），删设备走 `clearPendingPair` 一并对齐 |

## 6. 时间面：0E 校时（本轮第二大 bug）

- 旧实现 `target = now + (lockSec - now)` ≡ **把锁自己的钟原样写回去**（数学恒等），于是"同步成功"而锁钟一秒没动。
- 为什么它跟砖有关：锁的命令有效期判据就是它的钟——`rc=3`（命令过期，"请将手机时间同步到锁内"是 APK 自己的文案）与 `rc=13`（通讯过期）都从这里出。锁钟修不好 ⇒ 05 之后的每一步都可能被时间判据拒 ⇒ 用户反复重置 ⇒ **每次都擦一遍密钥域**（反复走在软砖边上）。
- **本轮修**：按原版 APK synctime 页的做法发**手机当前时间**（`new St(getNowTimeString(), mac)`）；先读锁钟只用来报告偏差，写完**回读**一次作为证据，偏差 >60s 直接报错（rc=0 只证明命令被接收）。

## 7. 令牌面：05 为什么必须带令牌（本轮第一大 bug）

- 原 APK 的 05 构造器 `Et`：`l.call(this, Jn.ZKCCOMM_EXSECURITYKEY, !0, "0000")` ⇒ `needSSToken = true`；
  Java `BleLockConnector.doExecute` 据此先发 01 取令牌，再由 `LockCommBase.getBytes(token)` 把令牌作为 **KLV#0xEE 追加在帧尾**。
- 真机真序因此是 **23 → 01 → 05（带令牌）→ 08/21/03**；裸发 05 会被锁回 `rc=13`（通讯过期 = 会话无效）
  并随即退出可配网态——与用户现场（同一秒内 rc13、反复如此）完全吻合。
- 全表见 `docs/PARITY-APK.md` §5b；iOS 侧除 05 外原本就与 APK 一致。
- 令牌生命周期：**每个令牌命令前无条件重取**（与 Java 一致）⇒ 不存在"用过期令牌"的残留。

## 8. 其余交互面（正确性检查，非砖，但一并过了一遍）

- **传输层**：连接就绪 = CCCD 写完成（= Java `onDescriptorWrite`）、20 字节分片（= Java `MAX_MTU`）、with-response 逐片等 ACK（= Android 默认写类型）；断链时清 waiter，不让调用方空等 8s。
- **探针**：12 回声走临时链路，不写 `DB.lastDevice`/`connectedMAC`，探完即撤（否则下次冷启动会去连一台没钥匙的设备）。
- **唯一写入口**：所有写命令都经 `LockService.request` ⇒ 演示模式拦写（`DemoKit.isOn`）、只读试验护栏（`kf_trial_guard` + `assertReadOnly`）、空帧拦截都在这一处生效。
- **钥匙串硬件**（41/43/44，目标不是门锁而是 ZKBBV1 钥匙扣）：41 空 ekey = 删除语义（`HardwareService:237` 是删除路径），写错钥的后果是那枚钥匙扣里的记录失效，**不伤门锁本身**；43/44 只读。
- **网关**（30/31/32/35/38）：31 写 WiFi 口令、35 重启网关，都不写门锁密钥域。
- **开锁凭证**：ekey 来自配对签发；空 ekey / PIN 解析失败一律拒绝下发（`cmd04Open` 空值闸 + `buildEkeyOpen` 返回 `""`）。

## 9. 残留风险与未验证项（不粉饰）

1. **真机未验**：本轮所有改动都没有在真锁上跑过（无设备）。下次配对的日志应当出现
   `TX 01 会话令牌 → TX 05 换钥 (needToken=true) → TX 08 ×4 → TX 21 → TX 03`；若仍失败，错误文案会带**步号 + rc + 回包 KLV 形状**（只键与长度，无值）。
2. **续配依赖系统 Keychain**：设备锁定/后台首启时写入可能失败，此时日志里会有 `配网中断保护未能落盘`，并且失败文案不再承诺续配。
3. **DFU 无签名校验**（离线无来源）：只烧仓内原厂包；传输中断仍有硬砖风险，属用户须知情的不可逆操作。
4. **回显不匹配那一支**只能键盘重置——协议决定，不是实现问题。
5. **待核**：(a) 锁端 0E 是否对"明显跳变"的写入做拒收（回读会告诉我们）；(b) 08 每批 16 vs APK 20 语义等价但没在真机上比过；(c) 升级前确认文案是否写清"中断可能变砖"。

## 10. rc=12「mac地址不正确」的两个含义（2026-10-17 真机，本轮第三大 bug）

现场：锁重置 → 23 探测通过 → 05 换钥 rc=0（锁内密钥已换、锁随即退出可配网态）→ 08 第一批回 rc=12，
此后这把锁只能靠键盘重置重来。rc=12 的字面意思是"包络里那 6 字节 MAC 不是我的地址"，但真机上有**两种**
成因会落成同一句：

1. **字节序取反**：0x88 包络里那 6 字节 MAC，两个参照实现各写了一种取法 ——
   原版 APK（`kt.getBytes`）的 TargetMAC 取 `BluetoothDevice.getAddress()`（**显示序**，也就是页面/台账里
   那个值），而 getBytes 自己会按字节对翻转一次 ⇒ 包络里落**线上序**；小程序旁支
   （`services/ble.js` 把 `adv.mac` 别名成 `macRaw`）TargetMAC 直接给**线上序**，翻转后包络里落**显示序**。
   两者都能自圆其说，谁也证明不了对方 —— 而锁只认一种。
2. **锁内 skey 与本机这份对不上**：05 的回包**不带 skey 回显**（只有 KLV#01=rc），所以 rc=0 只证明
   "锁执行了换钥"，不证明"锁内那份 = 本机这份"。

### 10.1 裁定只认「带 MAC 校验的写命令」—— 只读 03 探针已作废 (2026-10-17 夜)

**作废理由 (真机 + 代码证据)**：03 探针的整个前提是"读类命令也会判那 6 字节 MAC"。真机走下来不是这样——
锁重置后配对：`05` rc=0，接着 `03` 探针 **rc=0**（`calibrateMacOrder` 只在 `rc == 0` 时才认它，缺 rc KLV 时
`extractRc` 返回 -1 会直接抛错，所以那一次确实拿到了锁的 rc=0 判决），可紧接着 `08 批次 1` 回
**rc=12「mac地址不正确」**。⇒ 03 的 rc=0 证明不了字节序，它把"锁没校验 MAC"读成了"这个取法是对的"，
并把 `.display` 落盘到 `kf_macorder_<mac>` —— **一个错的取法被裁定成"已知"**，此后这条链上每条写命令都要吃 rc=12。
这正是"反复都失败、一次比一次更像变砖"的来源。

**现在的裁定点：`08` 批次 1**（真正被锁校验 MAC 的那条写命令）——

- 第一次用注册表里的取法发（默认 `.display` = 原版 APK 语义）；
- rc=12 ⇒ 换另一种取法**重发同一批**：rc≠0 的语义是"锁没执行"，所以这是安全重发而不是盲写两遍；
  换序后 rc=0 即落盘；rc=18「不能设置重复的值」说明原序其实已经写进去了（本批视为成功，顺序复原为原序）；
- 两种取法都被 rc=12 拒 ⇒ 成因 ②（锁内 skey 与本机这份对不上），**当场停手**，不再往下写 08/21。

只对**第一批**做：后面的批次若也 rc=12，说明不是字节序问题，换序同样白搭 —— 立刻停手，让用户少跑一趟锁跟前。
`ZKProtocol.buildEkey` 仍是包络 MAC 的唯一出口，注册表在那里生效，`cmdsshadow` 继续盯着"与金标逐字节一致"。

### 10.2 已配对钥匙串的自愈

老钥匙串是"没有这一层"的版本配下的，若它恰好是另一种取法，之后每条命令都会回 rc=12。
`LockService.exec` 对这一族命令做一次**换序重发**：rc=12 = 锁没执行 ⇒ 重发安全（与 rc=3 刷令牌那支
同一条纪律，且同样只做一次）；成功后把顺序落盘，下一帧起不必再试。两种都被拒则复原注册表，
并如实报"不是字节序问题，是锁内密钥与本机不一致"。

### 10.3 现场怎么读

- 日志里会出现 `PIN 批次 1 rc=12 (mac地址不正确) → 换一种包络 MAC 字节序 (raw) 重发本批`，成功时紧接着
  `包络 MAC 字节序裁定 = raw (08 批次 1 换序后 rc=0)`；两条都被拒时是
  `PIN 批次 1 两种字节序都被拒: 原序 rc=12 / 换序 rc=…`。
- 续配入口：05 回 rc=0 之后锁就不再广播重置位，因此扫描列表这一行**改为按"本机有没有未走完的配网记录"
  可点**（`待续配` 胶囊）。否则那句"再点一次配网会接着配完"在 UI 上根本进不去。
- **锁内密钥域仍然只在 05 被写一次**（本轮纪律未变）：换序重发与自愈都建立在 rc≠0 = 未执行之上。
