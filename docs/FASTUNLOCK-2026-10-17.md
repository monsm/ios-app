# 靠近秒开: 延迟账本与两端现状 (2026-10-17 第五轮)

口径: 把"从人到门口"到"锁执行 04"之间的每一段时间列出来, 标明哪一段是**代码可压的**、
哪一段是**协议逼出来的** (01 取令牌 → 04 必须两个往返, 压不掉)、哪一段是**安全门**
(不该压, 该由你决定)。取证全部对着 `App/**` (iOS) 与 `vendor/app/**` (APK 权威 JS 移植)。

## 0. 结论

| | 冷 (第一次/链路断了) | 热 (链路还在) |
|---|---|---|
| iOS | 扫描+建链+发现+订阅, 然后 01→04 | **只剩 01+04** (ensureConnected:75 零成本直接返回) |
| 安卓 (本轮前) | 每次都是冷: 扫描+建链+发现+订阅+认锁+01+04, **然后拆链** | 不存在热路径 |
| 安卓 (本轮后) | 冷路径一次; 之后复用 | **只剩 01+04**; 再往前 -62 dBm 就预热, 连冷路径也不付 |

体感差距的主因**不是协议, 不是锁, 也不是任何安全门**: 是旧安卓实现每次都把链路拆掉重连。
iOS 从一开始就没拆 (LockService.unlock:447 里没有任何 disconnect)。本轮把安卓对齐到同一口径。

## 1. 安卓本轮改了什么

1. **链路复用** (`BleUnlocker.kt`): 开锁成功后保留 `Session` (gatt/write/订阅/已核身份),
   下一次直接走 01+04。判定复用的四个条件都在 `pickWarm`: 同一把锁 / 链路没报断开 /
   write 句柄还在 / 没超过 `warmStaleMs = 60s` (超龄就重建 —— 半死链路比重建更慢)。
2. **预热** (`prewarm`): 信号越过 -62 dBm (比触发线弱 24 dB ≈ 功率 1/250, 约一两米) 就在后台
   把链路建好, 人站定之前链路已经是热的。**只建链, 一个命令都不发** —— 01/03/04 都不碰,
   这条由闸门 A8 直接钉住 (预热里出现 tokenFrame/unlockFrame/statusFrame 即判失败)。
3. **不再另起扫描**: 广播句柄缓存在 `seen` 里。安卓同时只跑一路扫描, 旧写法预热再发一次
   startScan 会顶掉监测流, 收尾那句 stopScan 又把监测一起停 (表现 = "当前信号再也不更新")。
   现在预热与冷路径都先吃缓存句柄, 拿不到才自己扫。
4. **撤监测的范围扩到预热在途**: `LaunchedEffect(proximity, lock?.mac, busy, warming)`
   —— 边扫边连是 GATT 133 的头号成因, 预热同样要避免。
5. **拆链出口** `release()`: 解绑、关开关、`onDestroy` 都会拆。热链路不拆 = 一直占着锁那一侧的
   GATT 接口位, 下一把锁要连还得先拆它。

删掉的一个最长 2 秒的白等: 旧 `onMtuChanged` 那条 `mtuOk.await()` (MTU 是纯优化, 分片恒 20B,
不该让冷路径等它的回调)。iOS 也没有这一步。

## 2. iOS: 真正的原因不是延迟, 是门

iOS 的链路本来就复用 (见上表), 协议耗时与安卓同一量级。靠近不开锁的原因是
`AutoOpen.swift:212-232` 那几道 **fail-closed 门**在按顺序否决, 而且拒开是静默的
(只写审计, 界面不显示)。逐个核实过:

| 门 | 判据 | 谁会被它挡住 |
|---|---|---|
| F1 面容 | 标准档要求 `lastFace` 在 60 秒内 | **所有人**: 见 §2.1 —— 本轮已修 |
| F2' 停留 | 静置 ≥3s (加速度计方差) | 走路中不放行 (堵"骑车路过"), 站定 3 秒即过 |
| F3 标定 | 必须做过 30 秒距离标定 | 没标定的人永远 `f3nocal`; 且 `feedRssi` 没有基准就 return, 连武装位都置不起来 |
| F4 布防 | `DB.defend(mac)?.control ?? 2` | **没进过布防页的人**: nil⇒2 且 start==end ⇒ 按"全天布防"⇒ 永久否决 |
| F5 冷却 | 距上次下发 >60s | 正常, 不影响首次 |
| F6 锁态 | 无快照 ⇒ 拒 | 实际不挡人: 进设备页的 `.task` 会 `refreshStatusQuietly` → `getStatus` → `DB.writeStatus`, 快照在开锁之前就有了 |

### 2.1 F1 是死门, 不是慢门 (本轮唯一改 iOS 代码的地方)

`AutoOpenKit.lastFace` 的唯一生产者原本只有 `promptFace()`, 而它**只在严格档**被调用
(`AutoOpen.swift:372`)。标准档 (默认档) 走的是 `silentRefresh()`, 那函数是空的 —— 里面写清了
理由 (2026-10-17 真机勘误"一直在请求 Face ID"): iOS 没有静默生物识别, 一调就弹模态窗。
注释承诺"只沿用最近一次真实验证的 60s 窗口", 但**全仓没有任何地方在真实面容成功时记这个时刻**。
结果: 默认档下 `lastFace` 恒 nil ⇒ `faceFresh` 恒 false ⇒ F1 恒拒 ⇒ 靠近自动开锁一次都不会触发。

修法就是把它承诺的那件事接上: `AuthKit.verifyBiometric` 与 `verifyBiometricAsync` 的
`ok == true` 分支各记一次 `AutoOpenKit.noteFaceSuccess()` (`AccessibilityKit.swift`)。
这两处覆盖 Siri 开锁、受限区复核、毁灭操作复核 —— 全是**真实的机主生物识别成功**。

这不是放宽门: 门照旧要求"60 秒内有过一次真实面容", 只是那一次现在记得下来了。
也没新增门。

### 2.2 剩下三道门我没有动 (该你拍板或该你在手机上做一次)

- **F3 标定**: 手机上做一次即可 (设置 → 靠近自动开锁 → 距离标定, 走近门锁站 30 秒)。
  这是按锁/按手机配对算武装线的, 不是形式主义 —— 用固定阈值会出现"隔着门/在客厅就开"。
- **F4 布防默认值**: `?? 2` 把"从没配过布防"读成"全天布防"。注释写明是 fail-closed 的取舍
  (缺事件源 = 门不过)。改成 `?? 0` (没配过 = 没布防) 功能立刻通, 但那是给门锁降安全强度,
  我不替你做这个决定。**现阶段的绕法**: 进 设置 → 一键布防 → 撤防 (会写 control:0, 门即通)。
- **F2' 停留 3 秒 / F5 冷却 60 秒**: 都是防误触发 (口袋里路过门口就开门)。压它们能更"秒",
  代价是安全语义, 同样需要你点头。

为了让这些拒开不再是"无声的失败", 本轮在设置页把**已有的审计拒因**显示出来
(`AutoOpen.swift` 的 AutoOpenSection, 读现成的 `AutoOpen.lastReject(mac)`, 不新增门不放宽门):
开关下面会直接出现"上一次没自动开：F4 布防时段内, 一票否决"那样的句子。
你在门口等半天却不知道为什么的那件事, 现在有答案了。

## 3. 协议下界 (两端一样, 谁都压不掉)

`01 取会话令牌 → 注入 KLV#EE → 04 开锁` 必须是**两个往返**: 锁端 0x253FE 对 KLV#0xEE 特判,
令牌只能现取 (`lock.js:580`: 裸发必回 rc=13), 且 `L08` 钉住"每条 needToken 命令都无条件先刷一次"
(Java 发送路径从不看 isExpire) —— 不许缓存令牌把这一趟省成一次往返。所以"秒开"只能做到
消灭连接层的浪费, 做不到一个往返开锁。
